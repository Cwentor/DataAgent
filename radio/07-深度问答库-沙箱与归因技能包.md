## 第一部分：为什么需要沙箱代码解释器

### Q7.1 — 有了 DSL 和编译器，为什么还需要让模型写 Python？

**答**：

因为**DSL 能表达的是"取数"，不能表达"分析"**。

举一个具体例子。用户问："为什么 6 月 GMV 下滑？"

分析这个问题需要：
1. 取当前期和对比期的 GMV；
2. 把 GMV 拆成 `买家数 × 人均订单数 × 客单价`；
3. 对每个因子做**对数分解**，算贡献占比；
4. 按省份下钻，用**信息增益**排序找出最值得追的维度；
5. 生成图表。

第 2~5 步是**算法**，不是"取数"。
你当然可以把这些算法都写进 DSL 契约（加一堆 `decompose: {...}` 字段），
但那样 DSL 就会变成一个**图灵完备的编程语言**——
而我们前面所有的安全论证，都建立在"DSL 的表达能力是有限的"之上。

**所以我们的分工是**：

| 层 | 负责 | 安全机制 |
| --- | --- | --- |
| DSL + 编译器 | **安全的取数** | 契约 + 白名单 + 只读 |
| 沙箱 Python | **灵活的分析** | AST 守卫 + 隔离执行 + 输出协议 |

**关键在于沙箱是"无特权"的**：
它**没有数据库连接**、**没有网络**、**只能读给定的 Parquet 文件**、
**输出行数有硬上限**。

> **面试话术**："沙箱不是'把危险的东西关起来'，而是'**给它一个不需要危险能力的环境**'。
> 沙箱代码想连数据库？没配。想发网络请求？`--net none`。
> 想读系统文件？AST 守卫 + 只读挂载。
> **不是防住它，而是让它无事可做。**"

### Q7.2 — 沙箱的执行流程是什么？从数据到产物要经过几步？

**答**：

`core/sandbox/api.py` 的 `run_code(...)`，一共 **9 步**：

```
1. 静态 AST 检查（ast_guard.check）
      └─ 违规 → 直接拒绝，把违规摘要作为自愈上下文返回
2. 准备 workspace（inputs/ scripts/ outputs/ 三个子目录）
3. 读 _bootstrap.py 模板，替换 __USER_CODE_B64__ 占位符
      └─ 替换失败 → RuntimeError("runner占位符替换失败")
4. 把完整脚本写到 {workspace}/scripts/{name}.py
      └─ 脚本名必须匹配 [A-Za-z_][A-Za-z0-9_]{0,63}
5. 用选定的后端执行（DockerBackend 优先，否则 SubprocessBackend）
      └─ 有超时（DEFAULT_TIMEOUT_SECONDS=15.0）
      └─ stdout/stderr 各截断到 MAX_STREAM_BYTES=256*1024
6. 协议校验 —— 必须产出 outputs/summary.json
      ├─ 缺失        → "未产出 summary.json"
      ├─ 超时        → "沙箱超时（{timeout}s硬上限）"
      ├─ JSON 非法   → f"summary.json非法: {exc}"
      ├─ 协议外键    → f"summary.json含协议外键: {sorted(unexpected)}"
      └─ 行数超限    → f"聚合矩阵 {n}行超出 100行上限（请先聚合）"
7. 可选产出 outputs/echarts_spec.json（必须是 dict）
8. 时间预算守卫（elapsed_budget_guard）
9. 组装 SandboxResult（stdout 尾部截断到 2000 字符）
```

**`_SUMMARY_ALLOWED_KEYS`**：
```python
frozenset({"title", "metrics", "table", "findings", "extra"})
```

**`MAX_SUMMARY_ROWS = 100`** —— 这是整套沙箱设计里最重要的一条规则。

**为什么是 100 行**：因为沙箱和分析层之间是**摘要通道**，不是数据通道。
分析层（LLM）要读的是**结论**，不是明细。
如果允许传 10 万行明细，会出现三个问题：
1. Prompt 塞爆（token 成本）；
2. 数据从摘要通道泄漏出去（绕过 PII 脱敏的意图）；
3. 说明沙箱没有做聚合——**"把明细丢给上游"是没做分析的表现**。

**报错文案的措辞值得注意**："请先聚合"——
它不只是说"你超限了"，而是**告诉模型该怎么做**。
这条消息会成为自愈的上下文。

### Q7.3 — AST 静态守卫具体拦截哪些东西？为什么黑名单不可能完备？

**答**：

`core/sandbox/ast_guard.py` 用 `_GuardVisitor` 遍历 `ast.parse` 的语法树，
维护三个黑名单：

**① `FORBIDDEN_MODULES`（导入黑名单）**

```
os, sys, subprocess, socket, ctypes, importlib, shutil, multiprocessing,
threading, signal, http, urllib, requests, ftplib, smtplib, telnetlib,
pickle, marshal, shelve, dbm, pathlib, tempfile, glob, platform,
resource, pty, tty, termios, fcntl, winreg, ...
```

**② `FORBIDDEN_CALLS`（调用黑名单）**

```
eval, exec, compile, __import__, globals, locals, vars, open, input,
breakpoint, exit, quit, help, memoryview, super, setattr, delattr
```

**③ `FORBIDDEN_ATTRS`（属性黑名单 —— dunder 逃逸向量）**

```
__class__, __subclasses__, __bases__, __mro__, __globals__, __builtins__,
__code__, __closure__, __dict__, __import__, __getattribute__,
__setattr__, __reduce__, __reduce_ex__, __loader__, __spec__, ...
```

**还处理两个微妙场景**：

```python
# 场景 1：相对导入
from . import x          # node.level > 0 → 违规

# 场景 2：字符串形式的 getattr 绕过
getattr(obj, "__class__")   # 字面量参数也要检查 → 违规
```

**为什么黑名单不可能完备**：

因为 Python 的对象模型太灵活了。举几个已知的绕过思路：

```python
# 思路 1：通过合法模块的合法属性找到危险对象
import numpy
numpy.__dict__["__builtins__"]        # ← 但 __dict__ 已被拦

# 思路 2：通过 MRO 找到 object 再 subclasses
type(1).__mro__[-1].__subclasses__()  # ← __mro__ / __subclasses__ 已被拦

# 思路 3：通过格式化字符串泄漏内建
f"{obj.__init__.__globals__}"         # ← __globals__ 已被拦
```

**注意**：上面三个思路**都已经被现有黑名单覆盖**。
但这恰好说明了黑名单的问题——**它能覆盖的是"我们想到的"**。

**所以我们的定位是**：

> **AST 守卫的目标不是"完备"，而是"提高攻击成本 + 拦截常见误用"。**
>
> 真正的隔离由**运行时限制**（模块白名单 import、受限 `open`、受限 builtins）
> 和**进程/容器隔离**（Docker `--net none --cap-drop ALL`、
> 非 root UID、只读 rootfs）承担。

**而且守卫的报错是可自愈的**：
`StaticGuardReport.summary()` 产出 `"L{行号} {类别}: {详情}"` 格式，
前 5 条用 `"; "` 连接，**直接作为 LLM 自愈的上下文**——
模型能看到"我第 12 行 import 了 os，这是被禁止的"，然后重写代码。

### Q7.4 — Docker 后端和子进程后端的能力差异是怎么暴露给上层的？

**答**：

关键在于 `BackendResult` 里的 **`limits_enforced` 字段**：

```python
@dataclass
class BackendResult:
    returncode: int
    stdout: str
    stderr: str
    duration_ms: int
    backend: str                 # "docker" / "subprocess"
    limits_enforced: bool        # ← 核心：限制是否真正生效
    timed_out: bool
```

**两种后端的真实能力**：

| 限制 | DockerBackend | SubprocessBackend (POSIX) | SubprocessBackend (Windows) |
| --- | --- | --- | --- |
| 网络隔离 | `--net none` ✅ | ❌ | ❌ |
| 能力裁剪 | `--cap-drop ALL` ✅ | ❌ | ❌ |
| 非 root | UID 10001 ✅ | `setuid` ✅ | ❌ |
| 只读文件系统 | 只读 rootfs ✅ | ❌ | ❌ |
| 内存限制 | cgroup ✅ | `setrlimit(RLIMIT_AS)` ✅ | **❌ 无法实现** |
| CPU 限制 | cgroup ✅ | `setrlimit(RLIMIT_CPU)` ✅ | **❌ 无法实现** |
| `limits_enforced` | **True** | **True** | **False（如实报告）** |

**Windows 上为什么做不到**：Python 标准库没有提供
Windows Job Object 的封装，`resource` 模块**在 Windows 上不存在**。

**"如实报告"为什么重要（这是我认为项目里最值得称道的一个设计）**：

子进程后端完全可以默默返回 `limits_enforced=True`——
反正没人会去验证。但它选择**诚实**。

**这个诚实有什么用**：
上层（比如未来的"生产环境准入检查"）可以据此判断
"当前环境的沙箱是否满足安全基线"。
如果 `limits_enforced=False`，就不应该允许在这个环境跑不可信的模型生成代码。

> **面试话术**："降级方案最常见的失败模式是'**假装自己很强**'。
> 一个降级后端如果谎报能力，会让上层做出错误的信任决策——
> 而这正是安全事故的温床。
> 我们把'我的限制没有生效'变成一个**显式的数据字段**，
> 让诚实成为架构的一部分，而不是依赖开发者的自觉。"

**`default_backend()` 的策略**：优先 Docker（运行时 `is_available()` 探测），
探测不到则回退子进程。

**`inspect()` 方法**：返回后端自描述（名称、可用性、能力），
用于 `/api/metrics` 或健康检查展示。

## 第二部分：归因技能包（这是"分析"的核心）

### Q7.5 — 技能包有哪些能力？为什么要求"零网络零 DB，只依赖 numpy 和标准库"？

**答**：

`core/skills/` 的四个算法模块（另加 `__init__.py`，共五个文件）：

| 模块 | 算法 | 行数 |
| --- | --- | --- |
| `drilldown.py` | 信息增益下钻排序 | 134 |
| `decomposition.py` | 乘法对数链式分解 + 加法差分分解 | 124 |
| `timeseries.py` | DTW + Holt-Winters 异常检测 | 141 |
| `shapley.py` | 精确 Shapley 值归因 | 101 |

**"零网络零 DB，只依赖 numpy + 标准库"的三重理由**：

**① 能在沙箱里跑**：沙箱没有网络和数据库，
所以技能包必须**自包含**——它同时也是**沙箱可执行脚本**（双形态设计）。

**② 可单测、可验证**：纯函数 + 纯数值计算，
可以用解析解做交叉验证（`tests/test_skills.py` 就是这么做的）。

**③ 依赖可控**：不引入 scipy / statsmodels / pandas，
避免了"一个库升级导致全部分析结果漂移"的风险。
**数值分析的复现性比便利性重要。**

**双形态设计**：
同一个算法既是**可 import 的库**（编排层直接调用），
也是**沙箱脚本模板**（把算法代码注入沙箱执行）。
这样保证了"库里的实现"和"沙箱里跑的实现"**不会漂移**。

### Q7.6 — "信息增益下钻"是怎么算的？为什么用它而不是方差？

**答**：

`core/skills/drilldown.py`（`MAX_OUTPUT_ROWS = 100`）。

**问题**：用户问"为什么 6 月 GMV 下滑？"，我们有一堆可能的维度
（省份、品类、品牌、渠道……）。**该先看哪个？**

**信息增益（Information Gain）的定义**：

```
对维度 D，把总体变化量按 D 的取值切分，得到每个取值的贡献 c_i（可正可负）

总变化量 T = Σ c_i

gain(D) = 1 - H(D) / log(n)     其中 n = 该维度的取值个数
H(D) = -Σ p_i · log(p_i)        其中 p_i = |c_i| / Σ|c_j|   （贡献度的分布熵）
```

**直觉解释**：如果 GMV 下滑**全部集中在某一个省**，
那这个省的 `|c_i| / Σ|c_j|` ≈ 1，其余接近 0，
分布熵 `H` 很低 → **信息增益接近 1**（这个维度"抓住"了变化）。

如果下滑**均匀分散在所有省**，
那 `p_i ≈ 1/n`，熵 `H` 接近最大值 `log(n)` → **信息增益接近 0**
（这个维度没有区分度）。

还有一个 `concentration` 指标（最大贡献占比），
和 `gain` 一起排序。

**实测输出**（真实运行结果）：

| 维度 | gain | concentration |
| --- | --- | --- |
| 省份 | **0.5313** | **0.4756** |
| 品类 | 0.2289 | 0.3373 |

→ 结论：**应该先追省份**（省份的信息增益是品类的 2.3 倍）。

**为什么不用方差**：

| 指标 | 问题 |
| --- | --- |
| 方差 | **不归一化**——省份 8 个、品类 6 个，取值数不同导致方差不可比；方差对极端值敏感，一个省的暴降会主导整个统计量 |
| 贡献绝对值之和 | 同样不归一化，维度取值数越多和越大 |
| **信息增益** | **归一化**（除以 `log(n)`），跨维度可比；基于分布形状而非量级，**对单个极端值的鲁棒性更好** |

**为什么除以 `log(n)` 而不是 `log2(n)`**：这只是单位选择（nat vs bit），
不影响排序。用自然对数是为了和 numpy 的默认实现一致。

> **面试话术**："下钻排序看起来是个小功能，但它决定了用户**先看到什么**。
> 如果排序错了，用户会去追一个不重要的维度，浪费一轮分析。
> 我们选择信息增益，是因为它是**少数几个能跨不同基数维度做比较**的指标。"

### Q7.7 — 乘法对数链式分解是怎么推导的？为什么用对数？

**答**：

`core/skills/decomposition.py`。

**业务问题**：`GMV = 买家数 × 人均订单数 × 客单价`。
GMV 从 669,327.93 降到 487,615.80（**−27.1%**）。
**三个因子各贡献了多少？**

**直接用差值法的问题**：

```
ΔGMV = B₁·O₁·P₁ - B₀·O₀·P₀
```

这个差值**无法唯一分解成三个因子的贡献**——
因为存在**交叉项**（`ΔB·O₁·P₁` 这种"两个因子同时变化"的项）。
交叉项怎么分摊？没有唯一正确答案。这就是指数分解里的经典难题。

**对数链式分解的解**：

对 `GMV = B · O · P` 两边取对数：

```
log(GMV) = log(B) + log(O) + log(P)
```

**乘积变成了求和！** 于是差值也可以分解：

```
Δlog(GMV) = Δlog(B) + Δlog(O) + Δlog(P)     ← 严格恒等式，无交叉项
```

各因子的**贡献占比**：

```
share(B) = Δlog(B) / Σ|Δlog(·)|
```

**实测输出**：

```
GMV: 669327.93 → 487615.80   (−27.1%)
买家数:    −22.4%   份额 −80.3%
客单价:     −4.7%   份额 −15.3%
人均订单数:  −1.4%   份额  −4.4%
```

**验证**：`−80.3% − 15.3% − 4.4% = −100.0%` ✅ 完美闭合。

**为什么用"对数增量"而不是"对数一阶近似"**：

严格的恒等式是 `Δlog(x) = log(x₁) − log(x₀)`，
代码里用的就是这个**精确值**，不是泰勒展开的一阶近似。

**为什么 `share` 要用 `Σ|Δlog|` 做分母而不是 `|Δlog(GMV)|`**：

因为 `Δlog(GMV) = Σ Δlog(因子)`，而这里面有正有负。
如果用 `|Δlog(GMV)|` 做分母，当有因子上升、有因子下降时，
分母会**远小于**分子绝对值之和，导致份额超过 100%。

用 `Σ|Δlog(因子)|` 做分母，保证 `Σ|share| = 1`，
每个 share 都在 `[-1, 1]` 区间内，**符号表示方向，绝对值表示强度**。

**加法差分分解**（同文件里的另一类）：

对于**加法关系**（比如 `总成本 = 采购成本 + 人力成本 + 其他`），
直接用差值分解：

```
ΔTotal = Δ采购 + Δ人力 + Δ其他
share(成本项) = Δ成本项 / Σ|Δ成本项|
```

**所以技能包里有两种分解**，由**指标间关系的类型**决定用哪种。

### Q7.8 — DTW 和 Holt-Winters 分别解决什么问题？为什么要两个都用？

**答**：

`core/skills/timeseries.py`（141 行），两者解决**不同层次**的异常检测。

**Holt-Winters：季节性预测 + 残差检测**

三重指数平滑：

```
水平 (level):      l_t = α(y_t − s_{t−m}) + (1−α)(l_{t−1} + b_{t−1})
趋势 (trend):      b_t = β(l_t − l_{t−1}) + (1−β)b_{t−1}
季节 (season):     s_t = γ(y_t − l_t) + (1−γ)s_{t−m}
预测:              ŷ_{t+h} = l_t + h·b_t + s_{t+h−m}
```

适合：**有稳定季节性 + 趋势的时间序列**（比如电商 GMV 有周末效应）。

**DTW（Dynamic Time Warping，动态时间规整）：形态相似度**

两个序列长度不同、有相位偏移时，欧氏距离会失效
（"这个月的曲线形状和上个月一样，只是整体后移了 3 天"）。
DTW 允许**时间轴非线性对齐**，计算最优匹配路径的累计距离。

适合：**形态比对**（"这周的波动形态和哪次历史异常最像"）。

**鲁棒异常判定（这是实现的关键细节）**：

```python
_robust_sigma = MAD × 1.4826
异常判定: |residual| > sigma_multiplier × _robust_sigma
sigma_multiplier = 3.0
```

**为什么用 MAD（Median Absolute Deviation，中位数绝对偏差）而不是标准差**：

因为**异常值本身会污染标准差**！

假设一个序列里有一个巨大的异常值：
- 用标准差：这个异常值会**显著抬高 σ**，
  导致阈值变宽，**异常检测不出来**（这是经典的"掩蔽效应 masking"）；
- 用 MAD：中位数不受极端值影响，`MAD × 1.4826` 是**一致的 σ 估计**
  （在正态分布下 `MAD × 1.4826 ≈ σ`），
  异常值不会污染它。

**`1.4826` 这个常数的来源**：
`MAD = median(|x_i − median(x)|)`，在正态分布下
`MAD ≈ 0.6745σ`，所以 `σ ≈ MAD / 0.6745 ≈ MAD × 1.4826`。

**为什么两个都要**：

| 场景 | 用哪个 |
| --- | --- |
| "这个月的销售额异常吗"（单序列、有季节性） | **Holt-Winters** |
| "这个月的波动形态像历史上的哪次事故"（多序列比对） | **DTW** |

> **面试金句**："异常检测的关键不是'算法多先进'，
> 而是'**阈值怎么定**'。
> 用标准差定阈值会在有异常值的场景下失效——
> 这就像用一把被异常值撑变形的尺子去量异常值。
> MAD 提供了一把不受污染的尺子。"

### Q7.9 — Shapley 值是怎么算的？为什么限制"最多 8 个因子"？

**答**：

`core/skills/shapley.py`（101 行）。

**Shapley 值**来自合作博弈论，用于**公平分配"团队合作的成果"**。
在归因场景里：多个因子共同影响了结果，每个因子的边际贡献是多少？

**定义**：

```
φ_i = Σ_{S ⊆ N\{i}}  [ |S|! · (|N|−|S|−1)! / |N|! ] · ( v(S ∪ {i}) − v(S) )
```

其中：
- `N` 是全部因子集合；
- `S` 是**不含 i 的子集**；
- `v(S)` 是"只有 S 中因子生效时"的结果值；
- 权重 `|S|!·(|N|−|S|−1)!/|N|!` 保证**所有排列顺序等概率**。

**直觉**：把所有可能的"因子加入顺序"都枚举一遍，
看这个因子每次被加入时带来了多少增量，取平均。

**为什么 Shapley 值"公平"**（四条公理）：

1. **有效性**：所有因子贡献之和 = 总效应；
2. **对称性**：贡献相同的因子得到相同的值；
3. **虚拟性**：不产生任何影响的因子得到 0；
4. **可加性**：多个独立博弈的贡献可以相加。

**为什么限制 ≤ 8 个因子**：

**因为精确 Shapley 需要枚举所有子集，复杂度是 O(2^n)。**

```python
# 实现：用 itertools.permutations 枚举所有排列
```

| 因子数 n | 子集数 2^n | 可行？ |
| --- | --- | --- |
| 5 | 32 | 秒级 |
| **8** | **256** | **可接受** |
| 12 | 4096 | 慢但勉强 |
| 20 | 1,048,576 | 不可行 |

**为什么不用蒙特卡洛采样近似**（Kaggle 上常用的 `shap` 库做法）：

因为我们的场景里**因子数天然很小**（业务上很少超过 8 个驱动因子），
而**精确性比性能重要**——归因结果会直接写进报告给业务方看，
一个"大约贡献了 30%"的数字不如"精确贡献 28.6%"可信。

**超过 8 个怎么办**：拒绝并提示。
这符合我们的整体原则——**明确的能力边界好过模糊的近似结果**。

### Q7.10 — 技能包的算法怎么验证正确性？

**答**：

`tests/test_skills.py` 的核心方法是**交叉验证（cross-validation against analytic solutions）**。

**具体做法**：

**① 构造有解析解的场景**

比如乘法分解：构造 `GMV = B × O × P`，
取 `B₀=100, O₀=2, P₀=50` → `GMV₀=10000`；
`B₁=80, O₁=2, P₁=48` → `GMV₁=7680`。

手算：`Δlog(GMV) = log(0.768)`，`Δlog(B) = log(0.8)`，
`Δlog(O) = 0`，`Δlog(P) = log(0.96)`。

算法输出必须和手算值**在浮点误差范围内一致**。

**② 恒等式验证**

- `Σ share(因子) ≈ 1.0`（份额闭合）；
- `Σ Δlog(因子) == Δlog(总值)`（对数分解的严格恒等式）。

**③ 边界场景**

- 因子有增有减时，份额符号是否正确；
- 单个因子变化时，其他因子份额是否为 0；
- 零值/负值输入是否被正确处理或明确拒绝。

**④ Shapley 的公理验证**

- 构造一个"某因子完全无影响"的场景，验证其 Shapley 值为 0（虚拟性公理）；
- 构造两个贡献相同的因子，验证得到相同的值（对称性公理）。

> **面试话术**："数值代码最难的是'看起来对'。
> 一个算错的分解算法也会输出一组加起来等于 100% 的漂亮数字。
> 所以我们不测'输出看起来合理'，而测'**和解析解一致**'——
> 这是我们能想到的最强验证方式。"

### Q7.11 — `core/retrieval/` 的"取数门面"是什么？为什么要多一层？

**答**：

`core/retrieval/tools.py` 的 `execute_dsl_query` ——
把 DSL 查询包装成一个 **typed Tool**，输出 `ParquetRef` 而不是原始行。

**"门面（Facade）"的价值在于统一出入口**：

```
所有数据查询路径
   ├─ Web 主链路 → execute_dsl_query
   ├─ 编排链路   → execute_dsl_query
   └─ 工具调度   → execute_dsl_query
             ↓
      [统一在这里做]
      · 权限守卫（apply_policy）
      · 编译（compile_sql）
      · 执行（execute_sql）
      · 结果断言（DataQA 四类）
      · 审计发现挂载（ParquetRef.audit = {guard, qa}）
      · 结果物化为 Parquet（带 sha256）
      · PII 脱敏
```

**为什么输出 `ParquetRef` 而不是行数据**：

| 维度 | 直接返回 rows | 返回 ParquetRef |
| --- | --- | --- |
| 大数据集 | 全进内存 | 落盘，按需读 |
| 沙箱使用 | 需要序列化传递 | 沙箱直接读文件（只读挂载） |
| 审计 | 无 | 带 sha256，可校验完整性 |
| 多轮复用 | 需重新查询 | 文件可复用 |

**`ParquetRef.audit = {guard, qa}`** 是关键设计：
**权限守卫的记录和质检的发现跟着数据走**。
无论下游是"SSE 事件"、"critic 反思"、"报告质检小节"还是"日志"，
都能拿到同一份审计信息——**编排与 Web 双链路同源**。

**`tools/builtins/_query_core.py` 的 `run_guarded_query(...)`**：
**每一个数据查询工具都必须走它**，
而且它**对"外部传入的 DSL"也强制 `apply_policy`**——
防止"工具调用方绕过权限"。

### Q7.12 — DataQA 的四类断言分别是什么？为什么是 WARNING 而不是拒绝？

**答**：

`core/retrieval/quality.py`，四类**确定性**断言（无 LLM）：

| 断言 | 触发条件 | 级别 | 业务含义 |
| --- | --- | --- | --- |
| `empty_result` | 结果 0 行 | warning | 可能是合法空集，也可能是口径错误 |
| `null_rate` | NULL 占比 > `NULL_RATE_THRESHOLD=0.5` | warning | 可能有 JOIN 未命中或数据质量问题 |
| `negative_metric` | 非负指标的聚合值为负 | warning | 数据异常或口径错误 |
| `dimension_uniqueness` | 聚合维度组合不唯一 | **error** | **分组逻辑有 bug**（同一组出现了两行） |

**`negative_metric` 的两个精细约束**（这是实现里很有意思的细节）：

**约束 1：只对特定聚合函数检查**
```python
_NON_NEGATIVE_AGGS = {"sum", "count", "count_distinct"}
```
`avg`/`min`/`max` 不检查——因为对可能为负的原始字段（比如利润、退款额）
求平均，负值是合法的。

**约束 2：只对 `kind == "aggregate"` 检查**
**`ratio` 和 `window` 派生指标不做负值断言**。

为什么——比率指标的分子分母可能有负数（比如"负增长占比"），
窗口指标的累计和也可能为负（累计退款）。
**对派生指标做"非负"断言会产生大量误报。**

**为什么四类里只有 `dimension_uniqueness` 是 error**：

因为它**不是数据问题，是代码问题**。
如果 `GROUP BY province, category` 的结果里
`(广东, 数码)` 出现了两行，那一定是分组表达式写错了——
**这是一个必须被看见的确定性 bug**，
所以用 error 级别（触发 `logger.error`，进入告警通道）。

而前三类都可能是**合法的业务现象**：
- 空结果可能是"北京真的没有店铺"；
- NULL 率可能来自 LEFT JOIN 的正常未匹配；
- 负值可能来自退款冲销。

**为什么"不自动否决执行"（这是最重要的设计决策）**：

```python
# 发现随 ParquetRef.audit 输出，不抛异常，不阻断
```

**理由**：
1. **自动否决会误杀合法答案**：空结果是常见且合法的；
2. **否决后用户拿不到任何信息**，而"给数据 + 附警告"用户能自己判断；
3. **真正的阻断责任在执行层**（超时、扫描行数、只读），
   QA 层的职责是"**标注**"，不是"**裁决**"。

> **面试金句**："质检的价值在于'**让人知道该怀疑什么**'，
> 而不是'替人做决定'。
> 一个把警告升级成拒绝的系统，最后会被用户绕过——
> 因为它挡住了合法的用法。"

### Q7.13 — 动态 profiling 是干什么的？为什么限制"最多 30 个枚举值"？

**答**：

`core/retrieval/profiling.py` —— 在**规划前**动态读取字段的实际枚举值，
注入规划上下文。

**流程**：

```python
DEFAULT_MAX_DISTINCT = 30

for field in semantic.catalog.COLUMNS:            # 只看 dtype == "str" 的字段
    rows = SELECT DISTINCT "{col}" FROM "{table}" ORDER BY 1 LIMIT ?
           # 参数 = max_distinct + 1  ← 多取一个用来判断是否超限
    if 实际基数 <= max_distinct:
        保留这个字段的枚举值
    else:
        跳过（防止 Prompt 爆炸）
```

**解决什么问题**：模型不知道数仓里**实际有哪些值**。

用户问"华东的 GMV"，模型可能生成 `province = '华东'`——
但数仓里只有 8 个原子省份。如果规划上下文里带上
"province 的取值有：广东、浙江、江苏、北京、上海、四川、湖北、山东"，
模型就能正确选择展开或用 `IN`。

**这就是 `REGION_PROVINCE_MAPPING` 想解决的问题的"动态版本"**：
静态映射解决的是"华东→哪些省"（业务知识），
动态 profiling 解决的是"数仓里到底有哪些省"（数据事实）。

**为什么 `LIMIT max_distinct + 1`**：

这是一个经典的**"基数探测"技巧**：
多取一个值，如果取回来 `> max_distinct` 行，
就说明这个字段的基数超过了阈值——**不需要 COUNT 一遍全表**
（COUNT DISTINCT 在大表上代价很高）。
**用一次 LIMIT 查询同时完成"探测基数"和"取值列表"两件事。**

**为什么是 30**：

| 阈值 | 效果 |
| --- | --- |
| 太小（10） | 品牌（24 个）会被跳过，模型看不到品牌取值 |
| **30** | 覆盖省份（8）、性别（2）、类目（6）、品牌（24）；跳过商品名（60）、店铺名（20+ 且会增长） |
| 太大（100） | 商品名会被包含，Prompt 里塞进 60 个商品名，token 成本上升，且对模型帮助有限 |

**为什么只处理 `dtype == "str"`**：数值字段的"枚举值"没有业务意义
（订单金额有几千个不同值），且会污染 Prompt。

**并发与缓存**：
- 用 `exec.pool.default_pool().acquire()/release()` 拿连接；
- 进程级 `_ENUM_CACHE`（带 `_ENUM_CACHE_LOCK` 保护）；
- 单个字段查询失败**静默跳过**（不影响其他字段）；
- 连接获取失败返回 `{}`（profiling 是**增强**，不是**必需**）；
- `clear_profile_cache()` 提供手动清理。

**只在 LLM 路径启用**：确定性兜底路径不需要（它用静态词汇表）。

## 第四部分：本主题高频压力追问速答

| 追问 | 一句话应答 |
| --- | --- |
| "15 秒超时够吗？复杂的分析脚本怎么办？" | `DEFAULT_TIMEOUT_SECONDS=15.0` 是针对"聚合分析脚本"设定的——因为输出被限制在 100 行，脚本**必须做聚合**，而聚合脚本通常很快。真需要长计算的场景应该走异步任务。 |
| "沙箱代码能不能读别的用户的数据？" | 不能。workspace 是**每次执行独立**的目录（`logs/workspaces/{principal}/{task_id}/`），inputs 只有本次查询产出的 Parquet。 |
| "如果模型写的脚本死循环呢？" | 超时 15 秒硬上限 + 进程/Docker 隔离。超时后返回 `"沙箱超时（15.0s硬上限）"`，并触发自愈（模型会得到"你的代码超时了"的反馈）。 |
| "技能包的结果会不会和查询结果对不上？" | 不会。技能包的输入**只能是** `ParquetRef` 指向的文件，两者是同一份数据。而且 `ParquetRef` 带 sha256，可以做完整性校验。 |
| "为什么不动用 pandas？" | pandas 会引入大量传递依赖，且它的隐式类型转换会让数值结果在不同版本间漂移。我们的分析逻辑简单到 numpy + 标准库足够。**依赖越少，复现性越好。** |
| "profiling 会不会拖慢启动？" | 它是**懒加载 + 缓存**的，且单个字段失败会跳过。1000 个字符串字段的场景需要重新评估——当前设计假设低基数字段数量可控。 |
| "DataQA 能发现'数字算错了'吗？" | 不能。DataQA 只能发现**结构性异常**（空、NULL 多、负值、维度不唯一）。数值正确性由**编译器的确定性**和 **Golden 评测的预期结果哈希**来保证。**不要指望质检层发现逻辑错误。** |

## 第一部分：意图路由（最前置的一层）

### Q6.1 — 为什么要做意图路由？直接把所有问题都送给模型不行吗？

**答**：

不行，有三个硬理由：

**① 成本**：一句"你好"如果走完整链路，会消耗
一次意图理解调用 + 一次规划调用 + 一次总结调用。纯浪费。

**② 安全**：`删除所有订单记录` 这句话，如果直接进模型→DSL→编译器链路，
我们要依赖**每一层都正确工作**才能拦下来。
而意图路由在**最前面**就把它拦住了——**不触达引擎**。

**③ 审计清晰度**：如果所有请求走同一条链路，审计日志里就分不清
"用户真的查了数"和"用户只是打了个招呼"。
QPS 统计、意图分布、成功率都会被污染。

**实测的路由行为**：

| 输入 | 结果 |
| --- | --- |
| `你好` | `chitchat`，confidence 1.0，reason `fast_path:greeting` |
| `删除所有订单记录` | **blocked**（`destructive_instruction`） |
| `DROP TABLE fact_orders` | **blocked**（`destructive_instruction`） |
| `打印所有员工的薪资表` | **blocked**（`sensitive_entity`），回复被限定在"数据目录范围"内 |
| `GMV的口径是什么？` | `glossary_explain`，confidence 0.95，"已检索到 2 条口径文档" |
| `高活用户有多少？` | `clarify:undefined_metric` |
| `GMV是多少？` | `clarify`（缺时间范围） |

### Q6.2 — 路由的三级决策是怎么设计的？为什么要有 Fast-Path？

**答**：

```
第一级：Fast-Path（纯字符串匹配，零成本、零延迟、零模型调用）
   ├─ 空输入              → CLARIFY
   ├─ 破坏性指令正则       → UNSAFE_ACTION
   ├─ 敏感实体正则         → UNSAFE_ACTION
   ├─ 精确系统指令         → SYSTEM_ACTION
   └─ 精确问候             → CHITCHAT
        │ 未命中
        ▼
第二级：LLM 分类（单次 JSON 输出，带最近几轮历史）
   · 要求返回单个 JSON 对象
   · confidence < ROUTER_MIN_CONFIDENCE → 视为失败
   · 任何异常（LLMError / ProviderError / ValueError /
     JSONDecodeError / KeyError / TypeError）→ 视为失败
        │ 失败
        ▼
第三级：规则兜底（正则 + 关键词）
   · RAG 模式        → GLOSSARY_EXPLAIN  (0.95)
   · 闲聊模式        → CHITCHAT          (0.95)
   · 指标 + 时间/分析信号 → DATA_QUERY   (0.9)
   · 有 last_dsl     → DATA_QUERY        (0.85, rule:contextual_followup)
   · 模糊信号        → CLARIFY           (0.8)
   · 都不匹配        → CLARIFY           (0.5)
```

**Fast-Path 的价值**：

1. **安全指令必须零延迟拦截**：等一次 LLM 调用（可能 3 秒）再拒绝破坏性指令，
   在安全审计上不可接受；
2. **打招呼是高频事件**：用户在对话里会有大量寒暄，
   每次都花 token 和延迟去分类是浪费；
3. **确定性**：同样的话永远得到同样的分类，便于测试与审计。

**为什么 Fast-Path 里的"精确问候"要用精确匹配而不是模糊**：
因为 `_EXACT_CHITCHAT` 是**精确匹配集合**。
如果用 `in` 模糊匹配，"你好，帮我查一下上月 GMV" 会被误判为闲聊。
这是个真实存在的经典 bug 模式。

### Q6.3 — 为什么路由层"永不抛异常"？

**答**：

```python
def route(query, ...):
    try:
        ...各种判定...
    except Exception:
        logger.exception("意图路由异常")
        return RouteDecision(intent=IntentType.CLARIFY, confidence=0.1,
                             reason="router_fallback")
```

**因为路由是整条链路的最前面一环**。

如果它抛异常，会发生什么？
- Web 层最外层 catch 会返回一个通用错误；
- 用户看到"系统内部错误"而不是"请补充时间范围"；
- **即使是一个正常的问题，用户也得不到任何有效反馈**。

而 `CLARIFY` 兜底的行为是：**反问用户补充信息**。
这个行为在语义上是"安全"的——它不会给出错误答案，只是多问一句。

**对比另一种设计**：兜底成 `DATA_QUERY`（按最可能的意图走）。
风险是：如果用户其实在问口径（`glossary_explain`），
系统会去数据库查一个不存在的指标，然后报一堆技术错误。

**所以兜底的选择原则是：兜底到"最不会造成伤害"的意图，而不是"最可能"的意图。**

### Q6.4 — 破坏性指令的识别会不会有遗漏？比如"请把订单表清空一下"？

**答**：

**会有遗漏，这是必然的**——只要用正则就一定有绕过空间。

**但关键在于：路由不是唯一防线。**

看这条防线链：

```
意图路由（正则，可能漏）
   ↓ 漏了
契约层（extra="forbid"，SQL 没地方放）
   ↓ 想绕过但表达不了
执行层四层只读校验（AST 级，覆盖所有 SQL 变体）
   ↓ 万一
DuckDB 只读连接（物理上写不了）
```

**路由漏掉的只是"提前给用户一个友好提示"，不会造成实际破坏。**

**至于 `_UNSAFE_CN_COMMAND_RE` 的一个刻意细节**：

中文的"修改"、"更新"**被有意排除**在这个正则之外。
为什么——因为用户会说"我想修改一下时间范围，改成上个月"，
这里的"修改"是**对话修正**，不是**数据修改**。
如果把"修改"当破坏性指令，会有大量正常查询被误伤。

**这是"精确率 vs 召回率"的取舍，我们选择了精确率**——
因为下一层防线能兜住召回率的缺口。

> **面试话术**："安全系统里没有'完美的一层'。
> 我们的做法是让每一层**只在它擅长的地方发力**：
> 路由层负责'常见恶意的快速拦截和友好提示'，
> 执行层负责'穷尽所有 SQL 变体'。
> 在路由层追求 100% 召回率会毁掉用户体验，在表达层追求 100% 精确率会漏掉变体——
> **每一层做自己该做的事。**"

## 第二部分：六节点编排（StateGraph）

### Q6.5 — 讲讲编排器的六个节点和它们之间的边。

**答**：

`core/orchestrator/`：

```
                    ┌──────────┐
        ┌──────────►│ clarify  │  澄清（HITL 中断点）
        │           └────┬─────┘
        │                │ 信息充足
        │                ▼
        │           ┌──────────┐
        │           │   plan   │  规划（LLM JSON 计划 + 启发式兜底）
        │           └────┬─────┘
        │                ▼
        │           ┌──────────┐
        │           │  query   │  受控取数（走 DSL → 编译 → 守卫 → 执行）
        │           └────┬─────┘
        │                ▼
        │           ┌──────────┐
        │           │ analyze  │  沙箱分析（跑生成的 Python）
        │           └────┬─────┘
        │                ▼
        │           ┌──────────┐
        └───────────┤ critique │  反思（确定性三检 + 可选 LLM Reflector）
        重规划≤3次   └────┬─────┘
                         │ 充分
                         ▼
                    ┌──────────┐
                    │synthesize│  综合报告（四段式 + 质检小节）
                    └──────────┘
```

- `StateGraph` 是自研的**极简图执行器**，`max_iterations=24`（防死循环的硬上限）；
- 状态 `AgentState` 是 `extra="forbid"` 的 Pydantic 模型，
  `apply(**updates)` 返回**不可变副本**；
- HITL 中断：`phase == "clarify"` 时设置 `_interrupted_at`，
  外部通过 `resume(human_reply)` 恢复。

**实测**：

- 简单问句 `2024年6月各品类GMV是多少？` → `phase=done`，**1 步**，
  报告"查询答案：199.95万元"；
- 复杂归因 `为什么6月GMV下滑？请定位到地区和品类。` → `phase=done`，**3 步**，
  产出 `['summary', 'summary', 'echarts']` 三个 artifact。

### Q6.6 — 为什么不用 LangGraph？自研的代价是什么？

**答**：

**自研的收益**：

| 维度 | LangGraph | 自研 StateGraph |
| --- | --- | --- |
| 依赖 | 需跟随框架大版本升级 | 零框架依赖 |
| 状态结构 | 框架约定 | 完全可控（`extra="forbid"`） |
| 事件总线 | 需适配 | 直接对接 SSE 九类事件 |
| HITL 中断恢复 | 框架机制 | 我们自己的 `_interrupted_at` + `resume()` |
| 调试 | 需要理解框架 | 就是普通的 Python 函数调用 |
| 代码量 | — | **核心逻辑约几百行** |

**核心判断**：我们的图需求很**克制**——
6 个节点、2 条条件边（`plan→query` 的循环、`critique→plan` 的重规划）、
一个中断点。这不是"通用工作流引擎"的需求，
用框架引入的抽象成本（学习、升级、调试、依赖）超过了收益。

**自研的代价（诚实说）**：
- 没有框架生态（可视化调试、追踪集成要自己写）；
- 并发/并行执行需要自己实现（当前是串行）；
- 如果未来节点数增长到几十个，自研的维护成本会超过框架。

**所以这不是"自研更好"，而是"在当前规模下自研更合适"**。
我在设计文档里留了迁移路径：`StateGraph` 的接口
（`add_node` / `add_edge` / `run`）刻意保持了与主流框架相近的语义，
未来要迁移时替换的是执行器，不是节点逻辑。

> **面试话术**："技术选型的关键不是'哪个更先进'，而是'**当前约束下哪个总成本最低**'。
> 6 个节点的图用框架是杀鸡用牛刀；60 个节点的图自研就是自找麻烦。
> 我们判断的依据是**需求规模**，不是**技术偏好**。"

### Q6.7 — `AgentState` 为什么要做成不可变的？

**答**：

```python
class AgentState(BaseModel):
    model_config = ConfigDict(extra="forbid")
    def apply(self, **updates) -> "AgentState":
        return self.model_copy(update=updates)
```

**三个理由**：

**① 事件溯源的前提**：整个编排过程通过 SSE 推送九类事件。
如果状态对象被就地修改，那么"事件推送时状态是什么"就无法确定——
你推的可能是修改后的状态，也可能是修改前的。

**② 多消费者安全**：HITL 恢复、critic 反思、synthesize 报告都要读状态。
共享可变状态意味着需要锁，而锁会引入死锁风险。

**③ 调试友好**：每一步的状态快照都是独立对象，
出问题时可以对比"第 2 步的状态"和"第 3 步的状态"到底哪里变了。

**`extra="forbid"` 同样重要**：防止某个节点往状态里塞一个计划外的字段，
然后下一个节点读不到（或者读到旧值）。**契约约束的不只是 LLM，也包括我们自己的节点。**

**`prune_tool_history(budget_chars=TOOL_HISTORY_BUDGET_CHARS=60_000)`**：
工具调用历史会不断累积，超过 6 万字符时裁剪。
**为什么要裁剪**：因为这些历史会被拼进下一次 LLM 调用的 Prompt，
不裁剪的话 token 消耗会随步数线性增长，且很快超出上下文窗口。

### Q6.8 — `critic_node` 的"三检"是什么？为什么需要反思层？

**答**：

`critic_node` 做两件事：

**① 确定性检查（不依赖 LLM，永远执行）**

三个短路条件，命中即跳 synthesize：
1. 有明确的 `no_data_reason`（如时间超域）→ 无数据可追，重规划无意义；
2. 所有数据集 0 行 → 空集是合法答案；
3. 无数据且预算耗尽 → 诚实地失败。

**② 可选的 LLM Reflector（受门控）**

- 只有在**没有触发短路**、且**有可用模型**时才调用；
- 返回 `verdict == "insufficient"` 时，必须通过 `_insufficient_is_actionable` 检查：
  **反思必须给出"具体该查什么"，否则不允许重规划**；
- 重规划后记录 `last_replan_fingerprint`，指纹相同则不再重试。

**为什么反思层必须是"可选 + 受门控"的**：

反思本身是一次 LLM 调用，有延迟和成本。
如果每次编排末尾都无条件反思一遍，会让简单查询也变慢。
门控逻辑保证：**只在"可能真的不充分"的情况下才反思**。

**为什么反思结论必须"可执行"**：

这是防"空转"的关键。LLM 很容易给出"数据看起来不够充分，建议进一步分析"
这种**没有信息量**的反思。如果允许这种结论触发重规划，
系统会进入"反思→重规划→还是不够→反思"的循环，烧光预算。

`_insufficient_is_actionable` 的作用就是：
**把"我觉得不够"和"我建议再查 X"区分开，只有后者才能触发重规划。**

## 第三部分：多工具调度（ToolAgent）

### Q6.9 — ToolAgent 的调度范式是什么？为什么限制 `max_steps` 在 3~5？

**答**：

范式是经典的三段式：**Plan & Select → Execute & Guard → Replan & Synthesize**。

```python
class ToolAgent:
    def __init__(self, registry=None, planner=None, synthesizer=None,
                 max_steps=5, reflector=None):
        if not 3 <= max_steps <= 5:
            raise ValueError("max_steps必须在3~5之间（受控调度，杜绝无限循环）")
```

**为什么是 3~5 这个范围**：

| 值 | 效果 |
| --- | --- |
| 1~2 | 做不了跨步综合（对比型问题需要至少 2 次查询 + 1 次综合） |
| **3~5** | 覆盖绝大多数分析场景（查询 → 补充查询 → 综合） |
| ≥ 10 | 延迟和 token 成本失控，且**边际收益迅速递减** |

**"3 是下界"的业务理由**：对比型问题（"华东和华南哪个更好"）
本质需要 **查两次 + 综合一次** = 3 步。少于 3 步做不了。

**"5 是上界"的产品理由**：用户等待心理学上，
一个交互式分析请求超过 5 个思考步骤就会开始焦虑。
而且我们有流式事件反馈，用户能看到进度——
但 10 步的进度条本身就是一种焦虑源。

**`ValueError` 而不是 `assert`**：这是**构造参数校验**，
用异常比断言好（断言在 `-O` 优化模式下会被剥离）。

**实测的 4 个注册工具**：

| 工具 | 作用 |
| --- | --- |
| `query_metric` | 指标查询（受控 DSL 链路） |
| `trend_analysis` | 趋势分析（时间维度 + 窗口） |
| `export_report` | 导出报告（PII 脱敏 + Parquet 物化） |
| `explain_glossary` | 口径解释（RAG 检索） |

**注意这个数字：4 个工具**。刻意保持少——
**工具越多，模型选错的概率越高**。这是"能力广度 vs 选择准确率"的取舍。

### Q6.10 — `ToolResult` 和 `ToolContext` 为什么要分开？

**答**：

```python
@dataclass
class ToolContext:
    conn: ...            # 数据库连接
    principal: str       # 权限主体
    executor: ...        # 执行器
    rewriter: ...        # 自愈重写器
    request_id: str      # 追踪 ID
    prior: ...           # 前序结果
    base_dsl: ...        # 基底 DSL（多轮继承用）
```

**关键设计：`ToolContext` 是"注入"给工具的，不是"LLM 声明"的。**

工具的函数签名（暴露给 LLM 的 `tool_definitions()`）里**不包含 `ToolContext`**。
也就是说，**模型永远无法指定"用哪个 principal 执行"、"用哪个连接"**。

这是防止"工具层权限绕过"的关键：
如果 `principal` 是工具参数，模型就可以传 `principal="admin"`。

**`ToolResult` 的 `DisplayType(StrEnum)`**：标记结果的展示形态
（table / chart / text / number / …），让前端知道怎么渲染，
**而不需要在前端里写 if-else 判断业务逻辑**。

**`BaseTool.run()` 永不抛异常**：

```python
def run(self, args, ctx) -> ToolResult:
    try:
        ...
    except Exception as exc:
        return ToolResult(ok=False, error=f"{type(exc).__name__}: {exc}")
```

**为什么**：工具是"被执行"的，一旦抛异常会中断整个调度循环。
而调度器需要知道"这个工具失败了"，然后决定"重试 / 换工具 / 放弃"。
**把失败变成返回值，是让上层能做决策的前提。**

**`validate_args` 拒绝未声明的键**：
和 DSL 的 `extra="forbid"` 同一个思路——
模型不能往工具参数里塞计划外的东西。

### Q6.11 — 工具注册中心为什么要保证"注册顺序 = 确定性"？

**答**：

`tools/registry.py`（165 行）：

- `UnknownToolError(KeyError)` / `DuplicateToolError(ValueError)`；
- **线程安全的注册**，且**注册顺序 = 定义顺序 = `tool_definitions()` 的返回顺序**。

**为什么顺序重要**：

`tool_definitions()` 返回的是 OpenAI Function Calling 格式的工具列表，
它会**按顺序**拼进 Prompt。而 LLM 对 Prompt 里的顺序**是敏感的**——
同样的工具集，换个顺序可能让模型的工具选择概率分布发生变化。

**如果不保证顺序**（比如用 `set` 或 `dict` 的哈希序），
就会出现：**同一份代码，不同进程启动得到不同的工具顺序，
同一个问题得到不同的工具选择。**

这就是"不确定性从哪来"的经典来源——**你以为无关紧要的数据结构选择，
实际上决定了系统的可复现性。**

**`DuplicateToolError` 的价值**：重名工具会让 `registry.get(name)` 的结果取决于注册顺序，
从而产生**难以排查的行为漂移**。注册时直接报错，把问题消灭在启动阶段。

## 第四部分：会话记忆与多轮继承

### Q6.12 — 多轮对话的"继承"是怎么做的？"那华南呢？"怎么理解？

**答**：

`agent/memory.py` 的 `resolve_context(query, session_id, owner)` 决策顺序：

```
1. no_history      → fresh     （没有历史，全新问题）
2. topic_switch    → fresh     （话题切换，不继承）
3. reset_intent    → fresh     （用户说"重新开始"）
4. no_delta        → fresh     （没有增量信息，不继承）
5. drilldown_dim   → drilldown （"按品类展开" → 加维度）
6. drilldown_trend → drilldown （"看下趋势" → 加时间维度）
7. 其他            → inherit   （"那华南呢？" → 改过滤条件）
```

返回 `(mode, dsl, summary)`，`summary` 是给用户看的中文说明
（"已继承上一轮的指标与时间范围，仅调整地区过滤条件"）。

**"那华南呢？"的处理流程**：

1. 检测到这是**指代性追问**（没有新指标、新时间，只有地区变化）；
2. 从历史取 `last_dsl`（假设是"上月华东 GMV"）；
3. `_apply_deltas` 应用增量：
   - **先移除**已存在的 `province` 过滤（华东展开的 4 个省）；
   - **再追加**新的 `province IN (广东)`；
4. 区域展开时与数仓省份取交集（跳过空 `IN`）；
5. `normalize_filters` 规范化；
6. 重新 `apply_policy`（重注入 RLS）。

**实测验证**：问"上个月华东地区的GMV是多少？"
区域被正确展开为 `[上海, 江苏, 浙江, 山东]`，返回 1 行 `gmv = 1281392.14`。

### Q6.13 — 会话记忆为什么要用 `(session_id, user_id)` 双键？

**答**：

```python
key = (session_id, owner)   # owner = user_id
# 跨用户读取 → 返回 None（fail-closed）
```

**如果只用 `session_id` 做键会怎样**：

`session_id` 是客户端生成的（或者来自 cookie），它是**可猜测/可枚举**的。
攻击者只要构造一个别人的 session_id，就能：
- 读到别人的历史提问（**信息泄露**：知道老板在查什么）；
- 接着别人的上下文提问（**语义混淆**：继承别人的 DSL）。

**这是"会话穿越"（session bleeding / IDOR）漏洞。**

**双键的设计保证**：即使 session_id 完全泄露，
A 用户的请求也**读不到** B 用户的历史——因为 owner 对不上，
`get()` 返回 `None`，系统按"全新问题"处理。

**注意这里是 fail-closed**：`None` 意味着"当作没有历史"，
而不是"回退到用 session_id 单独查"。

**其他保护**：
- `SESSION_MEMORY_TTL=1800`（30 分钟无活动清理）；
- `SESSION_MEMORY_MAX_SESSIONS=1000`（防内存无限增长）；
- `SESSION_MEMORY_HISTORY_TURNS=5`（滚动窗口，只保留最近 5 轮）。

### Q6.14 — `strip_rls_filters` 是干什么的？为什么必须有？

**答**：

**这是多轮对话里最隐蔽的一个 bug，值得完整讲一遍。**

**问题的产生**：

1. 第一轮：用户问"广东的 GMV"。DSL 被 `apply_policy` 注入了
   `province IN ('广东')`；
2. 这个**已经注入过的 DSL** 被存进 `state.last_dsl`；
3. 第二轮：用户说"那浙江呢？"，系统取出 `last_dsl` 作为基底；
4. 合并新条件 → `province IN ('广东') AND province IN ('浙江')`；
5. **结果恒假 —— 永远返回空。**

**而且这个 bug 极其隐蔽**：它不是崩溃，不是报错，
而是**永远返回正确答案"0"**。用户会以为"浙江真的没有数据"。

**修复**（`agent/memory.py`）：

```python
def strip_rls_filters(dsl, principal):
    """剥离该主体已被注入的 RLS 过滤器。"""
    policy = resolve_policy(principal)
    ...
    # 从 dsl.filters 中移除与 policy.row_filters 匹配的过滤器
# 使用：合并前剥离，合并后重新注入一次
clean = strip_rls_filters(dsl, principal)
merged = _apply_deltas(clean, delta)
final = apply_policy(merged, principal)   # 恰好注入一次
```

**设计原则（面试金句）**：

> "**注入和剥离必须是一对函数，并且在同一个测试里互相验证。**
>
> 只要系统里存在'给对象加上某约束'的操作，
> 而这个对象会跨请求持久化，就必然需要对应的'去除约束'操作——
> 否则约束会在多次传递中**复合**。"

**为什么不让 `_apply_deltas` 自己去重**：

因为去重需要判断"哪个 filter 是系统注入的、哪个是用户提的"。
而用户**完全可能合法地**自己写一个 `province = '广东'`。

"剥离-合并-注入"的顺序让语义边界清晰：
**用户条件归用户，系统条件归系统，两者在流水线里各走各的路。**

### Q6.15 — 会话记忆存在哪？重启会丢吗？

**答**：

存储是**分层**的：

| 数据 | 存储 | 重启后 |
| --- | --- | --- |
| 会话历史 / `last_dsl` | 进程内 `SessionStore` + 可选 SQLite（`STATE_STORE_DB`） | 配了 SQLite 就不丢 |
| 澄清槽位 | 进程内 dict + `SqliteKVStore(table="clarify_slots")` | 同上 |
| 登录限流计数 | SQLite | 不丢 |
| 编排运行状态（SSE） | **进程内**（`RunRegistry`） | **丢失** |

**为什么编排运行状态不持久化**：

SSE 运行状态包含事件缓冲（有界队列）、游标、暂停状态。
它的生命周期是**一次交互**（几十秒到几分钟）。

持久化它的成本（序列化开销、磁盘 I/O、恢复逻辑）
远高于收益（用户刷新页面的概率不高，且我们已经有 `?after=<seq>` 断点续传）。

**如果真的要持久化**，正确的做法是：
把事件流写进消息队列（Kafka/Redis Stream），SSE 端点变成消费者。
这样还能支持"多实例部署 + 任意实例处理重连"——
这是我们架构演进路线图上的一项。

## 第五部分：澄清与槽位回填（HITL）

### Q6.16 — 系统怎么决定"该反问"还是"直接给答案"？

**答**：

`agent/clarify.py` 的 `detect_clarifications(query)` 返回两类澄清：

| kind | 触发条件 | 问题文案 |
| --- | --- | --- |
| `missing_time_window` | 有指标但没时间范围 | "请补充时间范围，例如'上个月'或'最近30天'" |
| `undefined_metric` | 出现了无法识别的指标词 | "您说的'高活用户'不在现有指标口径中，请从以下口径中选择：……" |

**为什么这两类必须反问**：

**① 缺时间范围**：
"GMV 是多少"——今天？本月？累计？**三个答案差几个数量级**。
猜错的代价是用户不信任系统。

**② 未定义指标**：
"高活用户"是个业务黑话，不同公司定义完全不同
（7 天登录？30 天有订单？）。
按字面猜一个，**产出的数字看似合理但口径错误**——
这比报错危险得多。

**实测**：`高活用户有多少？` → `clarify:undefined_metric`；
`GMV是多少？` → `clarify`。

**决策的顺序很重要**：
先检查 `undefined_metric` 再检查 `missing_time_window`。
因为如果指标本身就是错的，问时间范围也没有意义。

### Q6.17 — 反问之后用户回答了，系统怎么把答案接回去？

**答**：

这就是**槽位回填（Slot Filling）**，`agent/slotfill.py`（187 行）：

```python
@dataclass
class ClarifyContext:
    original_query: str
    pending: list[str]          # 待填槽位，如 ["missing_time_window"]
    created_at: float
    def expired(self, ttl_seconds=None) -> bool:
        ttl = ttl_seconds or settings.CLARIFY_SLOT_TTL   # 1800 秒
        ...

class ClarifySlotStore:
    def __init__(self, ttl_seconds=None, db_path=None):
        self._mem: dict[str, tuple[str, ClarifyContext]] = {}   # key → (owner, ctx)
        self._db = SqliteKVStore(db_path, table="clarify_slots")
```

**回填流程**：

1. 系统反问后，把 `ClarifyContext(original_query="GMV是多少", pending=["missing_time_window"])`
   存进槽位存储，key 是 `(session_id, user_id)`；
2. 用户回答"上个月"；
3. `attempt_fill(ctx, answer)` 判断这个答案**是否满足待填槽位**：
   - 满足 → 返回 `f"{ctx.original_query} {answer}".strip()`
     = `"GMV是多少 上个月"`，然后**当作一个完整的新问题**重新走链路；
   - 不满足 → 返回 `None`，**当作全新问题处理，旧上下文丢弃**。

**四个关键设计**：

**① TTL（1800 秒 = 30 分钟）**：
用户反问后去开个会，一小时后回来说"上个月"，
不应该被接到一小时前的问题上。**过期的槽位必须失效。**

**② 属主绑定**：
`get()` 时校验 owner，不匹配返回 `None`（fail-closed）。
防止 A 用户填 B 用户的槽位。

**③ 双层存储**：
内存 dict（快）+ SQLite（跨重启）。读时先查内存，miss 再查 SQLite。

**④ 失败即放弃**：
回填失败**绝不硬套**。宁可当作新问题重新理解，
也不能把"上个月"错误地接到一个别的上下文上。

> **面试话术**："槽位回填的价值是让反问变成一次**真正的对话**，
> 而不是让用户重打一遍完整问题。
> 但它的风险是**上下文错配**——把一个回答接到错误的问题上，
> 会产出一个用户完全没问过的答案。
> 所以我们给它加了 TTL、属主校验，并且规定**失败必须放弃，绝不能猜**。"

### Q6.18 — HITL（Human-in-the-Loop）在编排层是怎么实现的？

**答**：

`core/orchestrator/graph.py`：

```python
# 中断：clarify 节点判断信息不足
if need_clarification:
    state = state.apply(phase="clarify", clarification=question)
    self._interrupted_at = current_node      # ← 记录中断位置
    return state                             # 提前返回，不继续执行

# 恢复：外部带着人类答复调用
def resume(self, human_reply: str):
    state = self._state
    state = state.apply(history=[...human_reply...])   # 把答复并入状态
    self._interrupted_at = None
    return self.run(from_node=...)
```

**要点**：

1. **中断不是异常，是正常返回**：状态里 `phase="clarify"`，
   运行器看到这个就停止推进。用异常做流程控制会让栈难追踪。
2. **`_interrupted_at` 记录断点**：恢复时从断点继续，不重跑前面的节点
   （避免重复计费、重复副作用）。
3. **`resume()` 是幂等的入口**：外部调用者只需要知道
   "我有个 token，我带一个答复回来"，不需要理解图的结构。

**实测**：编排运行 `2024年6月各品类GMV是多少？` → `phase=done`，1 步完成。

## 第六部分：SSE 流式协议（并行会话的难点）

### Q6.19 — SSE 为什么要做成"运行对象 + 游标订阅"？直接流不行吗？

**答**：

**直接流的三个致命问题**：

1. **刷新页面 = 全部重来**：浏览器刷新断开 SSE 连接，
   如果编排绑定在连接上，任务就死了，用户得重新提问；
2. **多标签页 = 重复计费**：用户开两个标签看同一个会话，会触发两次编排；
3. **慢消费者阻塞生产者**：如果直接往 socket 写，一个慢客户端会拖住编排线程。

**我们的设计**（`web/runs.py`，521 行）：

```
编排线程（后台）  ──写入──►  Run 对象
                              ├─ 有界事件缓冲（seq 从 1 开始）
                              ├─ 状态：running | paused | done | failed
                              └─ HITL 暂停状态

SSE 连接 ──订阅──► Run 对象（游标订阅者）
   · 客户端断开 = 取消订阅（编排继续跑）
   · 重连用 ?run_id=<id>&after=<seq> 续传（不重新编排）
   · 心跳保活（AGENT_RUN_KEEPALIVE_SECONDS）
   · 游标空洞检测 → 提示重新发起
```

**关键机制**：

**① `_append_locked`**：
```python
def _append_locked(self, event):
    event["seq"] = self._next_seq
    self._next_seq += 1
    self._events.append(event)
    overflow = len(self._events) - settings.AGENT_RUN_MAX_EVENTS
    if overflow > 0:
        del self._events[:overflow]        # 丢弃最旧事件
```

**② 游标空洞检测**：
```python
def _cursor_hole_locked(self, cursor):
    return cursor < self._events[0][0] - 1
```
如果客户端要的 `seq` 比缓冲区里最旧的还旧，说明**中间的事件已经被丢弃**，
无法续传——此时发一个 error 事件："事件缓冲已溢出，游标段落缺失，请重新发起提问"。

**为什么不扩大缓冲区**：内存是有限的，而一个跑了 20 分钟的多步编排
可能产生上千个事件。**明确地告诉用户"接不上了"，比静默地给一段有缺口的流要好。**

**③ HITL 状态在 Run 上，不在连接上**：
```python
def set_paused(self, state, token):
    with self._lock:
        self._state = "paused"
        self._append_locked({"type": "hitl_request",
                             "hitl": {"question": state.clarification or "请补充分析需求",
                                      "resume_token": token}})

def take_resume_state(self, human_reply):
    with self._lock:
        if self._state != "paused":
            return None                       # 只有 paused 状态能恢复
        baseline = self._next_seq - 1
        ...
        return state, baseline
```

**④ 幂等守卫**：
```python
find_active(owner, session_key, question)
```
同一个用户、同一个会话、同一个问题，如果已经有一个 run 在跑，
**直接返回那个 run 而不是新建一个**。

**为什么需要**：用户等不及了连点三次提交按钮 → 三次 LLM 编排 → 三倍费用。
这是**成本安全**问题，不只是体验问题。

**⑤ `orch_session_id` 的路径净化**：
```python
orch_session_id = re.sub(r"[^A-Za-z0-9._-]", "_", session_key)
```
把 session_key 里的非法字符替换掉。**具体原因很具体**：
session_key 里可能包含冒号（`user:session`），
而**冒号在 Windows 路径里是非法的**，
用它拼工作区路径会直接抛 `OSError`。

### Q6.20 — 九类事件为什么要这么分？

**答**：

| 事件 | 语义 | 前端消费 |
| --- | --- | --- |
| `plan_created` | 计划生成（DAG 步骤清单） | 任务时间线骨架 |
| `step_start` | 某步开始 | 进度指示 |
| `tool_start` | 工具调用开始 | 手风琴展开（输入） |
| `tool_end` | 工具调用结束 | 手风琴（输出 + 耗时 + 错误） |
| `reflection` | 反思/重规划结论 | 反思节点 + 原因 |
| `hitl_request` | 需要人工澄清 | 交互卡（可点击回复） |
| `artifact_emit` | 产物产生（报告/图表/代码/表格） | 顶部 Tab 徽标计数 |
| `done` | 正常结束 | 状态灯复位 + 报告 |
| `error` | 异常结束 | 错误提示 |

**分类的两个原则**：

**① 按"前端要做什么"分，而不是按"后端发生了什么"分。**
`tool_start` 和 `tool_end` 分开，是因为前端需要**先渲染一个正在运行的行**，
结束后再填充输出。如果合成一个 `tool_call` 事件，前端必须自己维护状态机。

**② `artifact_emit` 独立出来**：
因为产物是**增量产生**的（一个编排可能产出 summary、echarts、code 多个产物），
而前端需要**按会话持久化 + 顶部 Tab 徽标计数**。
把产物塞进 `tool_end` 会让"产物"这个概念耦合在工具实现里。

**异常处理原则**：编排异常**收敛为 `error` 事件**，不中断 HTTP 流。
为什么——因为流中断后前端拿不到任何信息，
而一个 `error` 事件至少能展示"哪一步失败了、为什么"。

## 第七部分：本主题高频压力追问速答

| 追问 | 一句话应答 |
| --- | --- |
| "六节点编排会不会太重？" | 两条链路：`/api/query` 走轻量 ToolAgent 调度；`/api/agent/run` 走六节点编排。**重活走编排，轻活走调度。** |
| "多轮继承会不会传错上下文？" | 有 4 个 fresh 判定（无历史/话题切换/重置意图/无增量）+ 剥离-合并-注入三段式 + TTL + 属主校验。**宁可重新理解，不能错配。** |
| "工具只有 4 个，能力够吗？" | 4 个工具覆盖了"取数/趋势/导出/口径"四类原子能力，复杂分析通过**编排**组合工具，而不是靠增加工具数量。工具越多，模型选择错误率越高。 |
| "HITL 中断后进程重启怎么办？" | 中断状态在编排器的内存状态里，**重启会丢失**。这是已知限制——生产上应该把 HITL 状态外置（Redis/DB）并支持从持久化的断点恢复。 |
| "SSE 事件协议怎么保证前后端一致？" | 事件类型定义在后端 `events.py` 的 `NODE_TITLES` / 类型常量，前端 `web/static/js/protocol.js` 与之对齐。**当前是手工同步的**，这是一个可以改进的点（生成式 schema 共享）。 |
| "怎么防重复提交？" | `find_active(owner, session_key, question)` 幂等守卫：同人同会话同问题返回已有 run。 |
| "编排最长能跑多久？" | `max_iterations=24` + `MAX_RETRIES=3` + `AGENT_RUN_IDLE_TIMEOUT_SECONDS` 空闲超时。空闲超时触发时发 error 事件并终止连接。 |

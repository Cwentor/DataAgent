# 02 · 架构全景与数据流走查

> **适用场景**：技术面开场。面试官说"你先介绍一下这个项目的架构"。
> **使用方式**：先画图（口述或白板），再按 12 步走一遍数据流，最后点出 5 个设计决策。

## 二、12 步数据流走查（面试金句来源）

以问题 **"上个月华东地区的 GMV 是多少？"** 为例，逐层走一遍。

### Step 1 — 入口与身份绑定

```
POST /api/query  {"query": "上个月华东地区的GMV是多少？"}
```

- HTTP 网关先做认证：`Authorization: Bearer <JWT>` 或 `session` Cookie（`auth/gateway.py`）。
- **关键设计**：`principal`（数据权限主体）**永远由服务端从身份库重新映射**，
  客户端就算在 body 里塞 `"principal": "admin"` 也不会被读取。
- 关闭鉴权时（`AUTH_ENABLED=False`）也不信任客户端，而是返回**服务端默认主体**——
  这条不变式在"关鉴权"和"开鉴权"两种模式下都成立。

> **面试话术**："身份和权限是分开的两件事。认证解决'你是谁'，
> 授权解决'你能看什么'。我们把授权主体固定绑在服务端，
> 客户端只有一个 token，永远无法自证权限。"

### Step 2 — 会话上下文装载

- 用 `(session_id, owner)` 去会话存储取上一轮状态（`agent/memory.py`）。
- **跨用户读取返回 `None`**（fail-closed）：A 用户拿着 B 的 session_id 也读不到 B 的历史。
- 拿到上一轮的 `last_dsl` 和滚动历史（默认保留 5 轮）。

> **考点**：为什么用 `(session_id, user_id)` 双键？——因为 session_id 是可枚举/可猜测的，
> 只用它做键会产生**会话穿越（session bleeding）**。

### Step 3 — 澄清槽位回填

- 如果上一轮系统反问过（比如"请补充时间范围"），这一轮用户的回答会被尝试**合并回原问题**。
- 例：上轮问"GMV 多少"→ 系统反问 → 用户答"上个月" → 实际执行的是"**上个月** GMV 多少"。
- 回填失败怎么办？**当作全新问题处理，旧上下文丢弃**——绝不硬套。

> **面试话术**："槽位回填的价值是让反问变成一次真正的对话，而不是让用户重打一遍问题。
> 但失败时必须放弃上下文，宁可重来也不能错配。"

### Step 4 — 意图路由（六分类分流）

`agent/router/intent_router.py`，三级决策：

```
Fast-Path（零成本、纯字符串）
   ├─ 空输入 → CLARIFY
   ├─ 破坏性指令（DROP/DELETE/TRUNCATE…）→ UNSAFE_ACTION（拦截）
   ├─ 敏感实体（薪资/身份证/病历…）→ UNSAFE_ACTION（拦截）
   ├─ 系统指令（退出/重置/我的权限/数据源状态）→ SYSTEM_ACTION
   └─ 精确问候（你好/hello/谢谢）→ CHITCHAT
        │ 未命中
        ▼
LLM 分类（单次 JSON 输出，带历史）
        │ 失败 / 置信度 < ROUTER_MIN_CONFIDENCE
        ▼
规则兜底（正则 + 关键词，永不抛异常）
```

六种意图：`chitchat` / `data_query` / `glossary_explain` / `system_action` / `clarify` / `unsafe_action`。

> **两个设计要点必须讲**：
> 1. **路由层永远不抛异常**——最外层 try/except 兜底为 `CLARIFY`，置信度 0.1。
>    理由：这是最前置的一层，一旦它炸了，用户连一句人话都收不到。
> 2. **路由耗时被结构化记录**（`routing_latency_ms` 字段落到审计），
>    用来做"分流漏斗"分析——哪个意图占比高、哪个原因触发得多、P95 延迟多少。

### Step 5 — 生成前作用域收窄（守卫前移）

`security/scope.py`：

```python
scoped_tables(principal)   # 你可查的物理表集合
scoped_fields(principal)   # 你可引用的逻辑字段集合
scoped_field_listing(p)    # 注入 Prompt 的字段白名单字符串
```

- **这是"守卫前移"**：不在生成后拒绝越权字段，而是**让越权字段根本不进入模型视野**。
- 例：`restricted` 主体看不到 `refund_amount`，它的 Prompt 里就没有这个字段名，
  模型连"猜到"的机会都没有。

> **面试话术**："传统做法是'生成后校验'——模型可能写出越权字段，我们再拒绝。
> 我们多做了一步'生成前收窄'：喂给模型的目录本身就是按权限裁剪过的。
> 这叫**最小权限注入**，从源头降低攻击面。"

### Step 6 — 意图分派到不同处理分支

`web/service.py` 的五个物理隔离分支：

| 意图 | 处理 | 是否触达数据库 |
| --- | --- | --- |
| `chitchat` | 固定话术回复 | **否**（省一次查询） |
| `unsafe_action` | 明确拒绝 | **否** |
| `system_action` | 白名单动作（重置会话/查权限/看数据源状态/退出） | **否** |
| `glossary_explain` | 检索口径词典（2 条文档） | **否**（走 RAG） |
| `clarify` | 反问 + 写澄清槽位 | **否** |
| `data_query` | 进入 Multi-Tool Agent 调度 | **是** |

> **考点**：为什么闲聊/拒绝也要单独分流？——**成本和审计**。
> 闲聊走一次完整的 LLM + 编译 + 执行链路，是纯粹的浪费；
> 更重要的是，如果闲聊也进数据库链路，审计里就分不清"用户真查了数"和"用户只是打了个招呼"。

### Step 7 — NL → DSL（双路径）

`agent/pipeline.py`：

```
run_pipeline_with_status(query, principal)
  ├─ 有可用模型 → LLMNL2DSL（严格校验 + 失败重试）
  │      └─ 失败 → 记录日志 → 降级
  └─ 无模型 / 降级 → DeterministicNL2DSL（纯规则，零模型依赖）
        └─ 再失败 → 透传**原始错误**（不吞错）
  最终两条路径都要过 apply_policy(dsl, principal)
```

> **必须讲的两点**：
> 1. **降级不是静默的**——落一条 `degraded=True` 标记，一路透传到响应和审计。
> 2. **降级失败要透传原始错误，而不是降级后的错误**——
>    否则排障时你会看到一堆无意义的规则解析错误，找不到真正的根因。

### Step 8 — DSL 契约校验（Pydantic V2）

`semantic/dsl_schema.py`，**这是整个系统的心脏**：

```python
class QueryDSL(BaseModel):
    model_config = ConfigDict(extra="forbid")   # ← 多一个字段直接报错
    metrics: list[Metric]
    dimensions: list[Dimension]
    filters: list[Filter]
    time_filter: TimeFilter | None
    order_by: list[SortField]
    limit: int = Field(default=100, ge=1, le=10000)  # ← 硬范围
    fill_gaps: bool = False
    top_n: TopN | None = None
```

`extra="forbid"` 的含义：模型想加一个 `"raw_sql": "DROP TABLE..."` 字段？
**校验直接失败**。它连表达这个意图的语法都没有。

> **面试金句**："契约的价值不在于'允许什么'，而在于'**没有地方放坏东西**'。
> `extra="forbid"` 是这句话的技术实现。"

### Step 9 — 权限守卫（表级/列级/行级）

`security/guard.py:apply_policy(dsl, principal)`：

1. 收集 DSL 引用的所有逻辑字段（指标分子分母、维度、过滤条件）；
2. **表级**：字段所属物理表必须在 `policy.allowed_tables`；
3. **列级**：字段不得在 `policy.forbidden_columns`；
4. **行级 RLS**：把策略里的 `row_filters` **追加**进 `dsl.filters`。

RLS 用**参数化模板**：

```json
{"field": "province", "operator": "in", "param": "principal.provinces"}
```

运行时按主体解析成实际值。实测 `bob`（restricted）生成的 SQL：

```sql
SELECT SUM(f.order_amount) AS "gmv"
FROM fact_orders f
JOIN dim_user u ON u.user_id = f.user_id
WHERE f.pay_status = 'SUCCESS'
  AND u.province IN ('广东')                    -- ← 系统强制注入，用户/模型都改不了
  AND f.order_time >= TIMESTAMP '2024-06-01 00:00:00'
  AND f.order_time <  TIMESTAMP '2024-07-01 00:00:00'
```

> **面试话术**："行级权限的关键是**改权限不用改代码**——加一个省份、加一个主体，
> 只改 `config/policies.json`。而且 RLS 是**注入**不是**校验**：
> 不是'检查你有没有加条件'，而是'我直接帮你把条件写死'。"

### Step 10 — 确定性编译（从 DSL 到 SQL）

`compiler/sql_compiler.py`，811 行，**纯函数，零 LLM，零随机**。

它做三件事：
1. 校验字段都在语义目录（`catalog.COLUMNS`）里；
2. 按目录声明的连接规则组装 `FROM / JOIN`（星型模型 + 1:1 第二事实表）；
3. 按受限操作符、聚合枚举、字面量转义生成 SQL。

**五种查询形态**（互斥，编译器显式报错）：

| 形态 | 触发条件 | 编译产物 |
| --- | --- | --- |
| 普通聚合/比率/窗口 | 默认 | 单层 SELECT + GROUP BY + LIMIT |
| 同比/环比 | `time_filter.comparison != none` | `cur` / `prev` 双 CTE + JOIN/USING |
| 分组 Top-N | `top_n != None` | 内层 `ROW_NUMBER() OVER (PARTITION BY …)` + 外层 `__rn <= n` |
| 日期补零 | `fill_gaps = True` | `generate_series` spine LEFT JOIN 聚合 + `COALESCE(…, 0)` |
| （窗口指标） | `WindowMetric` | `SUM(...) OVER (ORDER BY 时间维度)` / `AVG(... ROWS BETWEEN n-1 PRECEDING AND CURRENT ROW)` |

> **细节加分点**：编译器对 `comparison`/`top_n`/`fill_gaps`/`window` 的**互斥组合显式抛
> `CompileError`**，而不是生成一个语义模糊的 SQL。
> 例如"同比 + 补零"会直接报错——因为两套窗口语义叠加没有明确定义。

### Step 11 — 执行前审计 + 执行治理

进入 `exec/guards.py:execute_sql()`，按顺序过五关：

```
1. assert_read_only_sql(sql)      ← 四层只读校验（详见 04 文档）
2. assert_guardrails(sql)          ← GuardrailAgent 静态审计
      · readonly_structure   REJECTED
      · cartesian_product    REJECTED
      · unbounded_output     WARNING
3. EXPLAIN ANALYZE 预检扫描行数    ← 超 MAX_SCAN_ROWS 熔断（带缓存）
4. 线程看门狗 + conn.interrupt()   ← 超 QUERY_TIMEOUT_MS 强制取消
5. 结果行数上限                    ← 超 MAX_RESULT_ROWS 报错
```

> **必须能讲出**：超时为什么用**线程 + `conn.interrupt()`**？
> 因为 DuckDB 的 Python 客户端是同步的，`execute()` 一旦开始就阻塞当前线程；
> 我们把它丢进一个 daemon 线程，主线程 `join(timeout)`，
> 超时后调用 `conn.interrupt()` 从外部打断查询——这比"杀掉整个连接"温和，也不会让进程泄漏。

### Step 12 — 结果断言 + 展示 + 审计

- **DataQA 四类断言**（`core/retrieval/quality.py`）：空结果 / NULL 率 / 负值 / 维度唯一性。
  发现随 `ParquetRef.audit` 一路带到 SSE 事件、critic 反思视野、报告"数据质检"小节。
  **不自动否决执行**——空集可能是合法答案，误杀比放过更糟。
- **确定性解释**（`present/explain.py`）：把 DSL 翻译成中文话术，纯字符串拼接，**零 LLM**。
- **图表推荐**（`present/viz.py`）：确定性规则 → number / line / bar / pie / pivot / table。
- **审计落盘**（`audit/store.py`）：JSONL + DuckDB 双通道，带跨进程文件锁。

## 三、五个必须点出的设计决策

面试官问"你这个项目最有技术含量的地方在哪"，答这五个：

### 决策 1：LLM 只产 DSL，不产 SQL

| 维度 | 直接产 SQL | 产受控 DSL（本项目） |
| --- | --- | --- |
| 字段幻觉 | 可能引用不存在的字段 | 契约层直接拒绝 |
| SQL 注入 | 需额外防护 | 压根没有 SQL 字符串入口 |
| 越权 | 靠审查 SQL 文本 | 字段级白名单 + RLS 注入 |
| 可测试性 | 断言 SQL 文本极其脆弱 | 断言结构化 JSON 稳定 |
| 方言迁移 | 提示词里说明方言，易漂移 | 换编译器即可，Prompt 不变 |

### 决策 2：安全审计用确定性代码，不用 LLM

`exec/audit.py` 的 GuardrailAgent 有三项检查，全部是 sqlglot AST 静态分析，
**没有任何 LLM 参与**。

> **面试金句**："让 LLM 去审查 LLM 的输出，是把不确定性叠加在不确定性上。
> 安全裁决必须是可复现、可单测、零幻觉的——所以这部分我们交给代码。"

### 决策 3：编排层自研 StateGraph，不引入 LangGraph

- 六个节点 + 条件边 + HITL 中断恢复，**核心逻辑约几百行**；
- 好处：零框架依赖、状态结构完全可控（`AgentState` 也是 `extra="forbid"`）、
  事件总线与 SSE 直接对接、不随第三方框架大版本变更而重构。

### 决策 4：降级路径是"一等公民"

- `DeterministicNL2DSL`、`DeterministicPlanner`、`DeterministicSynthesizer`、`DeterministicReflector`——
  一整套不依赖模型的实现；
- 模型不可用时系统**功能退化但语义不退化**：能查的照查，不能查的**如实说不能**。

### 决策 5：一切防护都留"第二道防线"

| 主防线 | 第二道防线 |
| --- | --- |
| DSL 层 `IDENTIFIER_PATTERN` 校验别名 | 编译器 `_quote_ident()` 双引号包裹转义 |
| 生成前作用域收窄 | 生成后 `apply_policy` 表/列/行校验 |
| 编译器保证必有 LIMIT | 执行层 `MAX_RESULT_ROWS` 硬上限 |
| 自愈后 DSL 重新编译 | 自愈后**重新 `apply_policy`**（防权限逃逸） |
| 沙箱 AST 静态守卫 | runner 的模块白名单 + Docker 隔离 + 进程隔离 |

> **面试金句**："纵深防御不是说'我有很多层'，而是说'**每一层单独失效，系统仍然安全**'。
> 检验方法是问自己：如果这一层被绕过，会发生什么？如果答案是'会出事'，那就还缺一层。"

## 四、面试官可能追问的三个架构问题

### Q：六节点编排会不会太重？简单查询也要走全流程吗？

> 不会。编排器有**短路优化**：
> - `critic_node` 发现"本轮无数据"且原因明确时，直接跳到 synthesize，不做无谓重规划；
> - 所有数据集 0 行 → 直接 synthesize，走"诚实的失败报告"；
> - 单步可完成的查询，`query` 节点一次调用就把结果拿到，`analyze` 节点不做多余沙箱计算；
> - 实测简单问句 1 步完成、phase=done，复杂归因问题 3 步完成。
>
> 另外，Web 主链路（`/api/query`）走的是**轻量的 Multi-Tool Agent 调度**，
> 不走六节点编排器；六节点编排器服务于 `/api/agent/run` 这类**重分析**请求。
> 两条链路共用同一套 DSL/编译器/执行守卫。

### Q：为什么是 DuckDB？生产该用什么？

> DuckDB 是**单机嵌入式分析型数据库**，选它的原因是：
> 零部署、列式存储、对聚合与窗口函数支持好、非常适合做**确定性 mock 数仓**与本地演示。
>
> 生产替换路径是清晰的：编译器产出的 SQL 是**标准分析 SQL**（`date_trunc` / `ROW_NUMBER` /
> `generate_series` 有方言差异），只需要替换 `exec/guards.py` 中的连接与执行适配层，
> 以及语义目录的物理表映射（`catalog_loader` 已经是从 `information_schema` 读的）。
> 真正的迁移成本在**方言适配**和**EXPLAIN 扫描行数预检的等价实现**。

### Q：这套东西的瓶颈在哪？

> 三层瓶颈，从近到远：
> 1. **LLM 调用延迟**——一次问答可能触发 2~4 次模型调用（路由/规划/总结/反思）。
>    缓解：Fast-Path 分流掉不需要模型的请求；请求级模型切换让用户自己选快的；
>    继承轮跳过 LLM 规划。
> 2. **编排串行执行**——多工具调度目前是顺序执行，`max_steps` 3~5。
>    真正的并行需要解决"步骤间依赖"问题，这是下一步。
> 3. **单机 DuckDB**——并发上限 `MAX_CONCURRENT_QUERIES=4`，连接池 `DB_POOL_SIZE=4`。
>    生产上换分布式引擎 + 连接池外置。

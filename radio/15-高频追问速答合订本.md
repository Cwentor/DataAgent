## 索引 A：模型与契约（最高频）

| # | 面试官可能问 | 一句话答 | 出处 |
| --- | --- | --- | --- |
| A1 | "模型会不会绕过契约写 SQL？" | 结构上不可能：`extra="forbid"` 让契约里**没有地方可以放 SQL**。 | 03 |
| A2 | "模型幻觉字段怎么办？" | 字段必须命中 `catalog.COLUMNS` 白名单，否则 `CompileError: 未登记的字段`；且错误信息会作为自愈上下文喂回模型。 | 03 |
| A3 | "为什么用 Pydantic 不用 dataclass？" | 需要递归校验、`extra="forbid"`、字段级约束（正则/范围）三样，dataclass 都要手写。 | 03 |
| A4 | "契约 DSL 不就是把 Prompt 里的表结构换成 JSON 吗？" | 不是。区别是**约束在哪一端执行**：Prompt 是软约束（模型可以不听），契约是硬约束（模型说了不算）。 | 08 |
| A5 | "如果模型能力再强十倍，还需要契约吗？" | 需要。契约解决的不是"模型会不会做错"，而是"**系统错了会怎样**"。能力越强，一次错误的影响面越大。 | 08 |
| A6 | "DSL 表达力够吗？" | 覆盖企业高频查询的 80%+：六种聚合、比率、窗口、分组 Top-N、同环比、日期补零、多维多轮。剩下 20% 走沙箱或固化成新能力。 | 03 / 08 |
| A7 | "用户问了一个 DSL 表达不了的怎么办？" | 四条路径：换问法引导 / 沙箱算法 / 固化为新算子（走完整工程流程）/ 明确不支持。 | 08 |
| A8 | "契约的代价是什么？" | 四个：能力增长需工程介入、目录要与数仓同步、编译器测试负担重、长尾问法容忍度低。**这是刻意的取舍**。 | 08 |
| A9 | "怎么保证语义目录和数仓不脱节？" | `catalog_loader` 从 `information_schema` 读物理元数据，与 `config/semantic.json` 交叉校验，不一致时**启动失败**而非静默降级。 | 03 / 08 |
| A10 | "契约改版本了，历史 DSL 怎么办？" | **这是当前缺口**：`QueryDSL` 没有版本字段。应加 `schema_version` + 迁移函数，否则会话记忆和审计里的历史 DSL 会失效。 | 03 / 10 |
| A11 | "你现场加一个字段试试？" | 只改 `semantic/catalog.py` 的 `COLUMNS` 一处，编译器/权限/作用域/Prompt 全部自动生效——**SSOT 的实际价值**。 | 11 |

## 索引 B：编译器与确定性

| # | 面试官可能问 | 一句话答 | 出处 |
| --- | --- | --- | --- |
| B1 | "编译器 811 行是不是过度设计？" | 近一半代码在做防守——**每一条 `CompileError` 都对应一个实际踩过的坑**。 | 03 / 10 |
| B2 | "为什么要 8 种操作符/6 种聚合，不能开放更多？" | 每加一种就要补一整套互斥组合检查和测试；**组合空间是指数级增长的**。 | 03 |
| B3 | "浮点数怎么处理的？" | `repr()` 保证往返精度，且**显式拒绝 NaN/Inf**——它们拼进 SQL 会让查询行为不可预测。 | 14 |
| B4 | "字符串转义为什么不用反斜杠？" | 反斜杠是 MySQL 扩展；DuckDB 遵循标准，加了反而改变数据语义。**但换引擎必须跟着改，这是引擎耦合点**。 | 10 / 14 |
| B5 | "编译器出 bug 会怎样？" | 分三类：生成的 SQL 危险 → 审计独立拦截；含注入 → 执行层四层独立校验；**算错数字 → 只有 Golden 评测能发现，这是真实薄弱点**。 | 10 |
| B6 | "怎么测编译器？" | 字符串级断言。`assert 'COALESCE(SUM(r.refund_amount), 0) / NULLIF(...)' in sql` —— 能捕获**具体实现回归**，而不只是"结果对不对"。 | 09 |
| B7 | "同一份 DSL 在不同机器上结果一样吗？" | 一样。编译器无随机性 + `AS_OF_DATE` 固定 + 种子 42 —— **这是 Golden 评测用结果哈希做断言的前提**。 | 09 |
| B8 | "时间窗为什么用半开区间？" | `BETWEEN` 在时间戳精度下会**漏掉区间最后一天**；半开区间 `[s, e)` 首尾相接、不重不漏。 | 14 |
| B9 | "窗口函数的帧为什么显式写 `ROWS BETWEEN`？" | 不写会用引擎的隐式默认帧，**不同引擎/场景可能不同**；移动平均"含不含当前行"是两个不同的业务概念。 | 14 |
| B10 | "五个查询形态能组合吗？" | **明确禁止某些组合**：`comparison` / `top_n` / `fill_gaps` / `WindowMetric` 的互斥组合会显式抛 `CompileError`，而不是产生歧义结果。 | 03 |

## 索引 C：安全与权限（面试官最爱深挖）

| # | 面试官可能问 | 一句话答 | 出处 |
| --- | --- | --- | --- |
| C1 | "权限怎么防绕过？" | **注入式而非校验式**：编译器输出之后无条件 AND 上 RLS 条件。校验式要穷尽所有写法（不可能），注入式不需要。 | 04 / 14 |
| C2 | "三级权限分别是什么？" | 表级（能看哪些表）、列级（能看哪些列）、行级（RLS，能看哪些行）。`bob` 三级全受限。 | 04 |
| C3 | "用户说'忽略之前的权限要求'会怎样？" | 没用。**权限不在 Prompt 里，在编译器之后的注入环节**——模型说什么都改变不了那一段 SQL。 | 04 |
| C4 | "怎么防 SQL 注入？" | 三层：契约层别名正则 / 编译器 `_quote_ident` 转义 / `_literal` 只转义单引号。**而且 `_check_scalar_type` 保证了值的 Python 类型**。 | 04 / 14 |
| C5 | "四层只读校验分别防什么？" | 语句类型白名单 / AST 节点扫描 / 危险函数检测 / **连接级只读（物理不可能写）**。前三层给精确错误，第四层是真保证。 | 04 / 14 |
| C6 | "推断攻击（多次查询反推）怎么防？" | 简单的减法攻击无效（RLS 无条件注入，系统从没真算过全国数）。**但频率限制与异常模式检测我们没做**，这是明确缺失。 | 10 |
| C7 | "审计里存了 SQL，会不会泄露敏感信息？" | 会。正确做法是审计存储加密 + 访问控制。**当前是本地 JSONL + DuckDB，这一层完全没有**——生产必须补。 | 09 / 10 |
| C8 | "PII 脱敏怎么做的？" | 哈希掩码（`sha256` 截断）而非顺序编号——保证**跨查询一致性**（可关联分析）同时不可逆。租户加盐是已知待补项。 | 14 |
| C9 | "权限改了要重启吗？" | 当前是启动时加载 + 显式 `refresh_policies()`。**没有运行时热加载**——权限变更是低频、需审计的操作，"改配置→重启"本身带有审批留痕意味。 | 11 |
| C10 | "非管理员能不能提权？" | 不能。`principal` 由**服务端**从 JWT/Session 绑定，**不在任何客户端可传的参数里**；`ToolContext` 里的 principal 也不是工具的参数。 | 04 / 06 |

## 索引 D：执行治理与自愈

| # | 面试官可能问 | 一句话答 | 出处 |
| --- | --- | --- | --- |
| D1 | "查询跑太久怎么办？" | 三道保险丝：`QUERY_TIMEOUT_MS=30000` / `MAX_SCAN_ROWS=10M` / `MAX_RESULT_ROWS=20000`。 | 05 |
| D2 | "超时怎么实现的？" | worker 线程 + `join(timeout)` + `conn.interrupt()` + `join(2.0)`。**捕获 `BaseException` 而非 `Exception`**，否则 `KeyboardInterrupt` 会静默杀死线程，表现为一个无关的 `KeyError`。 | 05 / 14 |
| D3 | "扫描行数怎么预检？" | `EXPLAIN ANALYZE` 取**真实行数**（不是估算），用规范化 SQL 的 sha256 做缓存（`MAX_SCAN_CACHE_SIZE=512`）。 | 05 |
| D4 | "`EXPLAIN ANALYZE` 不是把查询跑完了吗？" | **是，这是真实缺陷**。首次出现的重查询要付两倍代价；缓解手段是缓存。更好的方向是混合：先估算，边界附近才 ANALYZE。 | 10 |
| D5 | "三层 LIMIT 为什么这么设计？" | DSL `limit` ≤10000（业务）< `MAX_RESULT_ROWS=20000`（防御，给 top_n/fill_gaps 放大留余量）< `MAX_SCAN_ROWS=10M`（成本）。 | 05 |
| D6 | "自愈会不会丢掉权限过滤？" | 修过了。`rewrite_dsl` 最后**无条件** `apply_policy(new_dsl, principal)`——因为 `model_copy` 出来的新 DSL 不带原来注入的 RLS。 | 05 |
| D7 | "什么错会重试，什么不会？" | 永久性错误短路：`SecurityError` / `UnknownToolError` / `PermissionError` **不重试**（重试也不会变好，只会烧钱）。 | 05 |
| D8 | "自愈重试几次？" | `SQL_SELF_HEAL_MAX_RETRIES=3`。从 1 提到 3 是因为 `order_by` 别名类修复常需第二轮。 | 05 |
| D9 | "兜底模式会静默吞错吗？" | 不会。确定性兜底模式下**透传原始报错**，而不是包装成规则解析错误——否则排障时找不到根因。 | 05 / 11 |
| D10 | "执行前审计为什么要有？" | 它是**独立于编译器的第二意见**。编译器说"我生成的 SQL 是安全的"，审计用自己的 AST 解析再验一遍——**不变的检查必须由独立代码承担**。 | 05 |
| D11 | "审计会不会误报？" | 会。已知案例：标量同环比生成 `FROM cur, prev` 被判笛卡尔积。**这个误报其实抓到了真实隐患**（一旦维度逻辑变动就会变成真笛卡尔积）。 | 10 / 11 |
| D12 | "结果缓存为什么默认关？" | `QUERY_CACHE_ENABLED=0`。数据分析场景里"看到过期数字"的伤害大于"查询慢 500ms"。**能力提供，默认关闭**。 | 05 |
| D13 | "缓存 key 为什么要带 principal？" | 不带就是**缓存导致的越权绕过**——A 用户的结果会被 B 用户命中。 | 05 |

## 索引 E：编排、多工具与记忆

| # | 面试官可能问 | 一句话答 | 出处 |
| --- | --- | --- | --- |
| E1 | "六节点编排会不会太重？" | 两条链路：`/api/query` 走轻量 ToolAgent；`/api/agent/run` 走六节点编排。**重活走编排，轻活走调度**。 | 06 |
| E2 | "为什么不用 LangGraph？" | 需求很克制（6 节点、2 条条件边、1 个中断点）。**技术选型看当前约束下的总成本，不看技术偏好**；接口刻意保持相近语义，留了迁移路径。 | 06 |
| E3 | "AgentState 为什么要不可变？" | 事件溯源的前提（推事件时状态是什么必须确定）+ 多消费者安全（不用锁）+ 调试友好（每步快照独立）。 | 06 |
| E4 | "为什么要限制 `max_steps` 在 3~5？" | 3 是下界（对比型问题需要"查两次+综合一次"），5 是上界（超过 5 步的进度条本身就是焦虑源）。**用 `ValueError` 而非 `assert`**（`-O` 会剥离断言）。 | 06 |
| E5 | "为什么只有 4 个工具？" | **工具越多，模型选错的概率越高**。复杂分析靠**编排**组合工具，而不是靠增加工具数量。 | 06 |
| E6 | "工具能不能自己决定用哪个用户身份？" | 不能。`ToolContext`（含 principal）是**注入**的，不在工具的参数签名里——模型传不了 `principal="admin"`。 | 06 |
| E7 | "工具抛异常怎么办？" | `BaseTool.run()` **永不抛异常**，把失败变成 `ToolResult(ok=False, error=...)`。**让上层能做决策的前提是失败是返回值而不是异常**。 | 06 |
| E8 | "多轮对话怎么理解'那华南呢'？" | `resolve_context` 七级决策：无历史/话题切换/重置意图/无增量 → fresh；下钻 → drilldown；其他 → inherit（改过滤条件）。 | 06 |
| E9 | "会话记忆为什么用双键？" | 只用 `session_id` 会 IDOR（可枚举、能读别人历史、能继承别人上下文）。双键 + 跨用户读返回 `None`（fail-closed）。 | 06 / 14 |
| E10 | "多轮继承会不会传错上下文？" | 有 4 个 fresh 判定 + 剥离-合并-注入三段式 + TTL + 属主校验。**宁可重新理解，不能错配**。 | 06 |
| E11 | "SSE 为什么做成运行对象 + 游标订阅？" | 直接流有三个致命问题：刷新页面全丢、多标签页重复计费、慢消费者阻塞生产者。 | 06 |
| E12 | "事件缓冲溢出了怎么办？" | 游标空洞检测 → 发 error 事件"事件缓冲已溢出，游标段落缺失"。**明确告诉用户接不上，好过静默给一段有缺口的流**。 | 06 |
| E13 | "用户连点三次提交会怎样？" | `find_active(owner, session_key, question)` 幂等守卫返回已有 run。**这是成本安全问题，不只是体验问题**。 | 06 |
| E14 | "意图路由为什么永不抛异常？" | 它是链路最前面一环，抛异常会让正常问题也得不到反馈。兜底到 `CLARIFY`——**兜底到"最不会造成伤害"的意图，而不是"最可能"的意图**。 | 06 |
| E15 | "破坏性指令识别有遗漏吗？" | 必然有（正则一定有绕过空间）。但**路由只是第一道**，后面契约/只读/只读连接还在。刻意**不匹配"修改"**（用户会说"修改一下时间范围"）。 | 06 |

## 索引 F：沙箱与分析

| # | 面试官可能问 | 一句话答 | 出处 |
| --- | --- | --- | --- |
| F1 | "有了 DSL 为什么还要沙箱？" | DSL 表达"取数"，沙箱表达"算法"。**沙箱不是把危险的东西关起来，而是给它一个不需要危险能力的环境**。 | 07 |
| F2 | "沙箱输出为什么限制 100 行？" | 沙箱和分析层之间是**摘要通道，不是数据通道**。10 万行明细会塞爆 Prompt、绕过脱敏、且说明脚本没做聚合。 | 07 |
| F3 | "AST 黑名单能穷尽吗？" | **不能，这是必然的**。目标是"提高攻击成本"而非"完备"；真正的隔离靠运行时限制 + 容器隔离。 | 07 |
| F4 | "沙箱代码能读别的用户的数据吗？" | 不能。workspace 每次执行独立，inputs 只有本次查询产出的 Parquet。 | 07 |
| F5 | "Windows 上沙箱限制生效吗？" | **不生效**，后端如实返回 `limits_enforced=False`。**降级方案最常见的失败模式是'假装自己很强'**——谎报能力会让上层做出错误的信任决策。 | 07 |
| F6 | "为什么不用 pandas？" | pandas 引入大量传递依赖，且隐式类型转换会让数值结果跨版本漂移。**依赖越少，复现性越好**。 | 07 |
| F7 | "归因算法为什么用对数分解？" | 乘积取对数后变成求和，差值**严格可分解、无交叉项**。直接用差值法无法唯一分摊交叉项。 | 07 |
| F8 | "为什么下钻排序用信息增益不用方差？" | 方差**不归一化**，不同基数维度不可比，且对极端值敏感。信息增益除以 `log(n)` 后跨维度可比。 | 07 |
| F9 | "异常检测为什么用 MAD 不用标准差？" | **异常值本身会污染标准差**（掩蔽效应），阈值被撑宽反而检测不出来。`MAD × 1.4826` 是抗污染的一致 σ 估计。 | 07 |
| F10 | "Shapley 为什么限制 8 个因子？" | 精确 Shapley 是 O(2^n)：n=8 是 256 个子集（可接受），n=20 是 104 万（不可行）。**明确的能力边界好过模糊的近似结果**。 | 07 |
| F11 | "算法怎么验证正确？" | **解析解交叉验证**——构造有手算答案的场景，断言浮点误差内一致；再加恒等式验证（`Σshare ≈ 1`）和公理验证（虚拟性/对称性）。 | 07 / 09 |
| F12 | "DataQA 能发现数字算错吗？" | **不能**。它只发现结构性异常（空/NULL 多/负值/维度不唯一）。数值正确性靠编译器确定性和 Golden 评测。**不要指望质检层发现逻辑错误**。 | 07 |

## 索引 G：工程化、成本与运维

| # | 面试官可能问 | 一句话答 | 出处 |
| --- | --- | --- | --- |
| G1 | "测试覆盖率是多少？" | **没有统计**——这是诚实的空缺。策略是"关键路径 + 安全边界"全覆盖，而非追求覆盖率数字。 | 09 / 12 |
| G2 | "文档写 622 个测试，你说 678？" | **文档滞后于代码**（我实测 678）。主动指出差异反而证明真跑过。 | 09 / 12 |
| G3 | "Golden 评测 25 个用例够吗？" | 作为**回归保护**够，作为**能力评估**不够。25 个是"最小可行的回归锚点"。 | 09 |
| G4 | "为什么用结果哈希做断言？" | 避免浮点比较；防止部分匹配（只断言行数会漏掉算错金额）；哈希不一致本身就是"确定性被破坏"的信号。 | 09 |
| G5 | "agent 模式才 9/25，是不是有问题？" | 分两类：11 个是"结果正确但 SQL 结构不匹配"（断言偏严 + 模型不稳定）；2 个是**供应商订阅失效的环境问题**——依据是 oracle 模式跑同一批用例 23/25 通过。 | 09 |
| G6 | "一次问答成本多少？" | 闲聊/拦截 **0 次** LLM 调用；简单点查 1~2 次；完整归因编排 3~5 次。**成本控制不是优化出来的，是设计出来的**（每个循环都有硬上限）。 | 09 |
| G7 | "延迟瓶颈在哪？" | ① LLM 往返（1~3 秒/次）② 沙箱环境启动（1~3 秒固定开销）③ `EXPLAIN ANALYZE` 预检。**优化感知延迟（流式反馈）比优化绝对延迟收益大**。 | 09 |
| G8 | "出了线上问题怎么定位？" | 拿 request_id 查审计 → 看 `dsl` 和 `sql`（通常这一步就定位了）→ 看指标确认影响范围 → 看 `routing_reason` 判断路由。**确定性带来的收益是"可重放"：审计里的 DSL 能直接重放出完全相同的 SQL**。 | 09 |
| G9 | "指标系统为什么不用 OpenTelemetry？" | 项目定位是可独立运行的原型，不引入外部基础设施。接口是干净的 `name → value` 映射，替换成 OTel/Prometheus 是局部改动。 | 09 |
| G10 | "104 秒的测试怎么加速？" | xdist 并行 / 内存 DuckDB / `slow` 标记。**但真正该优化的是"单次反馈速度"**（`pytest -k`），不是总时长。 | 09 |
| G11 | "上过生产吗？" | **没有。这是原型**。上线前必须补：正确性双跑验证、统一连接池、状态外置、审计加密、第三方安全评估。 | 10 |

## 附：三分钟急救包（面试前最后看这个）

**如果只有三分钟，按顺序默念这五句**：

1. **一句话**：大模型从头到尾没有写过一行 SQL，它只能填一张受约束的表单。
2. **核心机制**：契约 `extra="forbid"` → 白名单 `catalog.COLUMNS` → 确定性编译器 → **编译器之后强制注入权限**。
3. **四个必背数字**：**678** 个测试 / **104.46** 秒 / **23-25** 评测 / **28,594** 行。
4. **三个必说缺陷**：标量同环比被审计误判、双连接池、SSE 状态在进程内。
5. **收尾金句**：**"一个工程师最重要的能力，不是'能做出什么'，而是'知道自己做的东西在什么位置'。"**

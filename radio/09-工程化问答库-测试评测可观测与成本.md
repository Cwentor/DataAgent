### Q9.2 — 测试里最有价值的几类是什么？

**答**：

**① 编译器的字符串级断言（`test_compiler.py`，421 行）**

```python
# 断言的是 SQL 的具体结构，不是执行结果
assert 'COALESCE(SUM(r.refund_amount), 0) / NULLIF(SUM(f.order_amount), 0)' in sql
assert 'ROW_NUMBER() OVER (PARTITION BY u.province' in sql
assert 'NULLIF(prev."gmv", 0)' in sql
assert 'generate_series' in sql and 'COALESCE(a."gmv", 0)' in sql
```

**价值**：这些断言能捕获**具体的实现回归**。
如果某次重构把 `NULLIF` 改成了 `CASE WHEN`，或者忘了 `COALESCE` 分子，
测试立刻失败并指向那一行。

**② 契约的"非法输入必须被拒绝"测试**

这类测试比"合法输入能通过"更重要——**安全的价值在于拒绝**：

- 未登记字段 → `CompileError`
- `extra` 字段 → Pydantic 校验失败
- 别名含非法字符 → `IDENTIFIER_PATTERN` 失败
- `limit` 超范围 → 校验失败
- 互斥组合（comparison + fill_gaps）→ `CompileError`

**③ 权限矩阵测试**

三个主体（`admin` / `analyst` / `restricted`）× 三级权限（表/列/行），
形成矩阵化断言。实测：

- `restricted` 查 `refund_amount` → `SecurityError: 主体 'restricted' 无权访问字段: ['refund_amount']`
- `analyst` 的 SQL 必然包含 `province IN (...)` 且 ∈ 5 省集合

**④ 多轮记忆的回归测试**

包括那个 `strip_rls_filters` 的 bug：
**必须有一致的测试覆盖"注入后剥离再注入"的完整路径**。
不然这个 bug 会悄悄回来。

**⑤ 沙箱的对抗性测试**

- 危险 import（`os` / `subprocess`）被拒；
- dunder 逃逸（`__subclasses__`）被拒；
- `getattr(obj, "__class__")` 字符串绕过被拒；
- 输出超 100 行被拒；
- 协议外键被拒；
- 超时被正确处理。

**⑥ 技能算法的解析解交叉验证（`test_skills.py`）**

见 07 文档 Q7.10。

**⑦ CI 里的 RLS 对抗矩阵（nightly）**

`.github/workflows/ci.yml` 的夜间任务额外跑一组**行级权限对抗性矩阵**——
这是"权限是安全底线，要单独加强验证"的体现。

### Q9.3 — 678 个测试跑 104 秒，怎么保证还能更快？

**答**：

**先说明：104 秒对于一个 2.8 万行、678 用例的项目是合理的**，
不需要为了"跑得快"牺牲覆盖。但如果要进一步优化，路径是清晰的：

| 手段 | 预期收益 | 代价 |
| --- | --- | --- |
| `pytest-xdist` 并行 | 3~5 倍 | 需要确保测试间无共享状态（DuckDB 文件是共享的，要先解决） |
| 用内存 DuckDB（`:memory:`）替代文件 DB | 大幅减少 I/O | 需要在 fixture 里重建 schema |
| 把慢的端到端测试标记为 `slow`，默认跳过 | 主套件快 | 需要 CI 分两个 job |
| 复用 DuckDB 连接 fixture（session 级） | 中 | 测试隔离性下降 |

**当前的实际选择**：**保持单进程、全量跑**。
理由：CI 里 104 秒完全可以接受，
而"并行/隔离带来的调试复杂度"在项目这个阶段不划算。

**真正该优化的是"测试的反馈速度"而不是"总时长"**：
开发时用 `pytest -k <关键词>` 只跑相关测试，
`python -m pytest -q tests/test_compiler.py` 只要几秒。

## 第二部分：Golden 评测

### Q9.4 — Golden 评测是什么？和单元测试有什么区别？

**答**：

**Golden 评测 = 端到端的"考试"**：25 道真实业务问题，
每题有**预期的结果哈希**，跑完比对。

| 维度 | 单元测试 | Golden 评测 |
| --- | --- | --- |
| 粒度 | 函数级 | 端到端（自然语言 → 结果） |
| 输入 | 构造的 DSL | 真实自然语言问题 |
| 断言 | SQL 字符串 / 异常 | **结果哈希** |
| 覆盖 | 每个分支 | 25 个真实场景 |
| 速度 | 快 | 慢（每题编译+执行） |
| 变红意味着 | 某段代码坏了 | **某个用户场景坏了** |

**两种运行模式**：

```bash
python -m eval.eval_runner              # oracle 模式：跳过 LLM，直接用标准 DSL
python -m eval.eval_runner --pipeline agent   # agent 模式：完整 NL → DSL 链路
python -m eval.eval_runner --print-sql        # 打印生成的 SQL
```

**实测结果（本机复现）**：

| 模式 | 结果 |
| --- | --- |
| **oracle** | **23/25 通过** ✅ |
| agent | 9/25 通过（16 个失败：11 个 `result_ok=True` 但 SQL 不匹配、3 个窗口指标 Q16/Q17/Q23、2 个多轮 M1/M2） |

**两个失败用例（M1/M2）的诚实说明**：

```
M1: 上个月华东地区的GMV是多少？
M2: 上个月的GMV是多少？
→ AssertionError: 第1轮执行失败:模型服务调用失败，请稍后重试
```

**这是环境问题，不是代码问题**：当前仓库配置的唯一模型供应商
（`config/providers.json` 里的火山引擎 `ark.cn-beijing.volces.com/api/coding/v3`）
返回 `InvalidSubscription`——**订阅失效**。
oracle 模式不依赖模型，所以 23/25 通过；
agent 模式依赖模型，所以失败。

> **面试话术（这一点必须讲清楚）**：
> "这 2 个失败用例我要说明白：**它失败在'模型服务调用'这一步，
> 不在我们的编译或执行链路**。原因是仓库里配置的那个模型供应商
> 返回了 `InvalidSubscription`（订阅失效）。
> 我的判断依据是：**oracle 模式（跳过模型，直接用标准 DSL）跑的是同一批用例，
> 23/25 通过**——如果是代码问题，oracle 模式也会失败。
>
> 这个区分很重要：**一个工程师在排障时最容易犯的错，
> 是把环境问题当成代码问题**，然后去改一个本来是对的模块。"

### Q9.5 — 25 道用例是怎么设计的？为什么用"结果哈希"做断言？

**答**：

**用例设计覆盖六个维度**：

| 维度 | 用例举例 |
| --- | --- |
| 基础点查 | "2024 年 6 月成功订单的 GMV 是多少？" |
| 分组分布 | "各品类的销售额分布？" |
| 趋势 | "最近 30 天每天的订单量" |
| 对比 | 同比 / 环比 |
| 窗口 | 累计求和 / 移动平均（Q16/Q17/Q23） |
| 多轮序列 | M1/M2（连续追问，测上下文继承） |

**为什么用结果哈希**：

1. **避免浮点比较**：GMV 是浮点数，`==` 比较不可靠。
   哈希提供了"要么完全一致，要么不一致"的二元判定。
2. **防止部分匹配**：如果只断言"行数对不对"，
   一个算错金额的查询也能通过。
3. **可复现性验证**：确定性系统应该在**任何机器**上产出相同的哈希。
   哈希不一致 = 确定性被破坏了，这本身是一个重要的信号。

**哈希的前提是确定性**：
- `AS_OF_DATE = 2024-06-30` 固定（相对时间可复现）；
- 随机种子 42（mock 数据可复现）；
- 编译器无随机性；
- 因此同一个 DSL **在任何机器上都产出相同结果**。

**"为什么不人工标注期望值"**：
hash 是自动生成的（首次通过时记录），人工标注 25 个用例的完整结果集
既费时又容易出错。而**"首次通过时快照"**的做法，
配合 code review 检查快照 diff，是工业界（如 snapshot testing）的成熟实践。

### Q9.6 — 评测和审计报告里的评分体系是怎么回事？

**答**：

`docs/reviews/` 里有一套**基准评测（Benchmark Judge）**，
用六个加权维度打分：

| 维度 | 权重 | 我们当时的得分 |
| --- | --- | --- |
| Schema（语义与结构） | 0.25 | 60 |
| 执行安全 | 0.20 | 85 |
| 自愈能力 | 0.20 | 60 |
| PII 保护 | 0.15 | 80 |
| 可视化 | 0.10 | 85 |
| **透明度与解释性** | 0.10 | **45** |
| **加权总分** | — | **69 / 100（FAIL）** |

验算：`0.25×60 + 0.20×85 + 0.20×60 + 0.15×80 + 0.10×85 + 0.10×45 = 69`。

**判 FAIL 的原因是加权总分未达阈值**（阈值通常是 70）。

**评审指出的具体缺陷（这些都是真问题）**：

1. **"华东"未展开** → 生成 `province = '华东'`，空结果；
2. **空结果无反思** → 没有触发重规划；
3. **虚假确认** → `web/service.py:120` 对不支持的指令回复"系统操作已完成。"；
4. **答案层缺行值** → 报告只有结论没有支撑数据；
5. **比率 NULL 语义** → 无退款记录的品类退款率是 NULL 而非 0；
6. **Q22 非确定性**；
7. **导出上限由 LLM 决定**。

**我的处理方式（这是面试的高价值内容）**：

> "这份 FAIL 的评测报告被我**保留在仓库里**（`docs/reviews/20260910-...md`），
> 没有删掉，也没有重写。
> 因为我认同一句话：**评审报告的价值在于它记录了什么，而不是它给了多少分**。
>
> 而且这些缺陷的修复串起来，恰好是这个项目最有说服力的一段演进史：
> - '华东'展开 → 促成了 `DIMENSION_MEMBERS` + `REGION_PROVINCE_MAPPING`
>   以及'展开必须与数仓成员取交集'的规则；
> - 空结果无反思 → 促成了无数据诚实守卫 + 数据域边界判断；
> - 虚假确认 → 促成了意图路由的 `unsafe_action` 分支与拒绝话术；
> - 比率 NULL 语义 → 促成了 `COALESCE(分子, 0) / NULLIF(分母, 0)` 的写法。
>
> **每一个 bug 修复之后，我们都补了一条回归测试锚点。**"

**同时还有两份更早的评审**：
- `20260905-production-readiness-audit.md`：80/100；
- `20260906-readiness-final-signoff.md`：**92/100，结论"准予上线"**，
  基线 commit `f70f4e3`。

**这个 80 → 92 → 69 的曲线值得讲**：
不是"退步了"，而是**评测标准不同**——
前两份是"生产就绪度审计"（工程完备度），
第三份是"基准评测"（端到端能力）。
**同一份代码在不同标准下得到不同分数，这本身是一个关于"如何度量软件"的好话题。**

## 第三部分：可观测性

### Q9.7 — 系统的可观测性是怎么做的？三条通道分别是什么？

**答**：

`docs/architecture.md` 明确了**三条可观测性通道**：

**通道 1：结构化 JSON 日志**（`audit/logging.py`）

```python
class JsonFormatter(logging.Formatter):
    # 输出 JSON 行，包含 request_id / session_id / principal / path 等上下文字段
```

- 上下文字段用 **contextvars** 传递——
  这样在**异步/多线程**场景下，日志也能自动带上正确的 request_id，
  不需要把 request_id 一路当参数传下去；
- `setup_logging` 是**幂等**的（重复调用不会重复添加 handler）。

**日志级别的语义约定**（这是团队级的知识资产）：

| 级别 | 语义 | 具体事件 |
| --- | --- | --- |
| `error` | 需要人介入 | **熔断**、**审计拒绝**、**自愈额度耗尽**、QA 的 error 级发现 |
| `warning` | 系统自愈/降级 | 可自愈的报错、降级路径触发、HITL 暂停 |
| `info` | 正常里程碑 | HITL 触发、编排完成、自愈成功 |

**为什么这个约定重要**："什么该用 error"如果没有约定，
每个开发者的标准都不一样，最后所有东西都是 error，**告警就失效了**。
我们把"需要人介入"作为 error 的判据，这是一个**可操作的**标准。

**通道 2：SSE 九类事件**（面向用户与前端）

`plan_created` / `step_start` / `tool_start` / `tool_end` /
`reflection` / `hitl_request` / `artifact_emit` / `done` / `error`。

**通道 3：审计快照 + 指标**

- `AuditRecord`（`audit/record.py`）：
  `request_id` / `prompt` / `principal` / `dsl` / `sql` / `latency_ms` /
  `error` / `steps` / `detected_intent` / `routing_latency_ms` / `routing_reason`；
- 双通道落盘（`audit/store.py`）：**JSONL 文件 + DuckDB 表**，
  用 `_CrossProcessLock` 保证多进程写入安全，`_migrate_schema()` 处理表结构演进。

**为什么双通道**：
- **JSONL**：追加写、无需数据库、方便采集到 ELK/Loki，**故障时的兜底**；
- **DuckDB**：可 SQL 查询、可做聚合分析（比如 `audit/analysis.py` 的漏斗报告）。

**一个细节**：写审计失败**不能影响主流程**——
所以记录的代码包在 try/except 里。**审计可用性低于查询可用性**，
这个优先级是可接受的（丢日志比丢查询好）。

### Q9.8 — 指标系统有哪些指标？怎么暴露？

**答**：

`audit/metrics.py` 的 `MetricsRegistry(latency_window=1000)`：

| 类别 | 指标 |
| --- | --- |
| 请求计数 | 总请求数、按意图分布、按 action 分布 |
| 错误 | 按错误类型计数、按错误类分组的计数器 |
| **熔断器** | `query_timeout` / `scan_rows` / `result_limit` / `unsafe_sql` |
| **自愈** | `_self_heal_success` / `_self_heal_failures` |
| **延迟** | P50 / P95（用 `deque(maxlen=1000)` 做滑动窗口） |
| 路由 | `routing_latency_ms` 的分布 |

暴露方式：`GET /api/metrics`，由 `default_registry()` 单例提供。

**为什么延迟用 deque 滑动窗口而不是直方图**：

因为我们对分位数的精度要求不高，**内存可控**比精度重要。
`deque(maxlen=1000)` 保证内存恒定，P50/P95 用排序算（1000 个数的排序是微秒级）。
工业级方案（Prometheus Histogram / t-digest）在这里是过度设计。

**为什么用进程内注册表而不是直接接 Prometheus**：

因为项目定位是**可独立运行的原型**，不引入监控基础设施依赖。
但接口是干净的——`MetricsRegistry` 暴露的就是 `name → value` 的映射，
替换成 Prometheus client 是**局部改动**。

**路由漏斗分析**（`audit/analysis.py`，196 行）：

`routing_funnel_report()` 做**只读**的漏斗分析：
- 各意图占比；
- 各 `reason` 的触发频次（`fast_path:greeting` / `rule:contextual_followup` / `router_fallback`…）；
- 路由延迟分布；
- **被拦截的意图**（`unsafe_action` 的数量与原因）。

**这个报表能回答"系统好不好用"**——比如：

> "如果 `router_fallback` 的数量突然上升，说明 LLM 分类器开始不稳定了；
> 如果 `clarify` 占比过高，说明用户的问法或者我们的澄清话术需要优化。"

### Q9.9 — 出了线上问题，你怎么定位？

**答**：

**用一个真实的排障流程来回答（这是面试官最想听的）。**

**场景**：用户反馈"我问'上个月华东 GMV'，返回 0"。

**第 1 步：拿 request_id 找审计记录。**

```sql
-- audit/store.py 把审计写进了 DuckDB，可直接查
SELECT request_id, prompt, dsl, sql, latency_ms, error, detected_intent, routing_reason
FROM audit_records
WHERE request_id = '...'
```

**第 2 步：看 `dsl` 和 `sql`——这一步通常就能定位。**

假设看到：

```json
{"filters": [{"field": "province", "operator": "eq", "value": "华东"}]}
```

→ **立刻定位**：区域没被展开。
→ 根因：`REGION_PROVINCE_MAPPING` 的展开逻辑没生效，
或者模型产出的 operator 是 `eq` 而不是期望的展开后 `in`。

**第 3 步：如果没有 DSL 问题，看执行层。**

- `latency_ms` 正常但 0 行 → 数据问题，不是代码问题；
- `latency_ms` 异常高 → 看是否触发了熔断；
- `error` 非空 → 看错误类型（`_friendly_error` 的映射会告诉你是哪一类）。

**第 4 步：看指标确认影响范围。**

```bash
curl http://localhost:8000/api/metrics
```

看 `query_timeout` / `scan_rows` 计数是否异常上升——
**"这个用户的问题"还是"所有人的问题"，定位完全不同。**

**第 5 步：如果是模型问题，看路由与降级标记。**

`routing_reason` 字段会告诉你意图是怎么判定的：
- `fast_path:greeting` → 被 Fast-Path 误判了；
- `router_fallback` → LLM 分类器挂了；
- `rule:contextual_followup` → 走了上下文继承分支。

**第 6 步：参数化复现。**

```python
from semantic.dsl_schema import QueryDSL
from compiler.sql_compiler import compile_sql
from exec.guards import execute_sql

dsl = QueryDSL.model_validate({...})   # 从审计里的 dsl 字段复制
sql = compile_sql(dsl)
print(sql)                              # 肉眼验证 SQL
```

**因为编译器是确定性纯函数，审计里的 DSL 可以直接重放出完全相同的 SQL。**
这是"确定性"在运维上的直接收益。

> **面试话术**："确定性带来的运维收益是**可重放**。
> 一个非确定的系统，你在本地永远复现不出线上的那条 SQL；
> 我们的系统里，审计记录里的 DSL 就是完整的问题现场——
> **不需要'尝试复现'，直接就能重放。**"

## 第四部分：成本与性能

### Q9.10 — 一次问答的成本是多少？怎么优化？

**答**：

**先拆解一次典型问答的 LLM 调用次数**：

| 场景 | 调用次数 | 明细 |
| --- | --- | --- |
| 闲聊 | **0** | Fast-Path 直接判定 |
| 破坏性指令 | **0** | Fast-Path 拦截 |
| 简单点查（无历史） | 1~2 | 意图路由（可选）+ NL→DSL |
| 简单点查（有历史，走继承） | 1 | 仅 NL→DSL |
| 完整编排（归因分析） | 3~5 | 路由 + 规划 + （反思）+ 总结 |

**四层成本优化**：

**① 路由 Fast-Path 分流**
实测 `你好` → confidence 1.0，reason `fast_path:greeting`，
**零 LLM 调用**。这类请求在实际使用中占比不低。

**② 上下文继承跳过规划**
多轮追问（"那华南呢？"）走 `inherit` 模式，
从历史 `last_dsl` 合并增量，**不需要重新规划**。

**③ Prompt 裁剪**
- `SESSION_MEMORY_HISTORY_TURNS=5`（只带最近 5 轮）；
- `prune_tool_history(budget_chars=60_000)`（工具历史超 6 万字符裁剪）；
- **动态 profiling 限制 30 个枚举值**（防止低基数字段把 Prompt 撑爆）；
- `_ANSWER_MEMORY_CHARS = 2000`（跨轮传递的答案摘要长度）。

**④ 请求级模型切换**
`providers/context.py` 用 contextvars 支持**请求级指定模型**：
用户可以在 UI 上选"用便宜的小模型"还是"用强模型"。
`_resolve` 的优先级是：请求上下文 `(provider_id, model_id)` → 默认适配器。

**成本可控性**：
- `max_steps` 3~5 限制了单次请求的最大工具调用数；
- `MAX_RETRIES=3` 限制了重规划次数；
- `SQL_SELF_HEAL_MAX_RETRIES=3` 限制了自愈次数；
- **所有循环都有硬上限**。

> **面试话术**："Agent 系统最大的成本风险是**失控的循环**——
> 一次请求触发十几次模型调用。我们的做法是**给每一个循环加硬上限**，
> 并且用'可执行性门槛'（比如反思必须给出具体建议）减少无效循环。
>
> **成本控制不是优化出来的，是设计出来的。**"

### Q9.11 — 延迟分布大概是怎样的？瓶颈在哪？

**答**：

**分场景的延迟构成**（基于本地实测）：

| 场景 | 主要耗时 | 量级 |
| --- | --- | --- |
| 闲聊/拦截 | 无 | **毫秒级** |
| 简单点查（确定性路径） | 编译 + DuckDB 查询 | **几十毫秒**（实测 `scan_rows=2633`，6 行结果） |
| 简单点查（LLM 路径） | LLM NL→DSL（1 次） | **1~3 秒**（取决于模型和网络） |
| 完整归因编排 | 3~5 次 LLM + 多次查询 + 沙箱执行 | **10~30 秒** |

**瓶颈分析（按贡献排序）**：

1. **LLM 往返延迟**（最大项）：一次调用 1~3 秒，编排场景叠加 3~5 次；
2. **沙箱执行**：Docker 启动 + Python 启动 + numpy import，
   固定开销约 1~3 秒（比起算法本身，**环境启动是主要成本**）；
3. **`EXPLAIN ANALYZE` 预检**：首次出现的 SQL 要跑双倍；
4. **DuckDB 查询本身**：mock 数据只有 3000 行，可忽略；
   生产环境这个会是主要项。

**优化手段（已做与可做）**：

| 手段 | 状态 |
| --- | --- |
| 流式 SSE 反馈（**感知延迟**大幅降低） | ✅ 已做 |
| Fast-Path 分流 | ✅ 已做 |
| 扫描行数预检缓存 | ✅ 已做 |
| 查询结果缓存（默认关闭） | ✅ 提供开关 |
| 沙箱后端常驻（避免每次启动容器） | ⬜ 可做 |
| 编排步骤并行化 | ⬜ 可做（需解决步骤依赖） |
| 意图路由与 NL→DSL 合并成一次调用 | ⬜ 可做（牺牲可观测性） |

> **面试话术**："延迟优化的第一原则是**区分真实延迟和感知延迟**。
> 一个 20 秒但有进度反馈的请求，比一个 5 秒但白屏的请求体验更好。
> 所以我们在**流式反馈**上的投入，比在**绝对延迟**上的投入更多——
> 这是产品视角的技术决策。"

### Q9.12 — CI 是什么样的？

**答**：

`.github/workflows/ci.yml`：

**常规 CI（每次 push/PR）**：
1. `black --check .`（格式）；
2. `ruff check .`（Lint）；
3. `python -m pytest -q`（678 个用例）。

**夜间 CI（额外）**：
- **RLS 对抗性矩阵**（行级权限的对抗测试）。

**DoD E2E 检查**（`python -m tests.dod_e2e_check`）**不在 pytest 里**：
它启动一个三协议 mock provider，跑完整的端到端流程验证。
**为什么单独**：因为它要起服务、有端口占用、耗时长，
不适合每次提交都跑；但它是**发布前的必过项**。

`docs/quality.md` 里明确的工作流：

```bash
black --check .
ruff check .
python -m pytest -q
```

**一个诚实的说明**：AGENTS.md 里写明
"提交前确保 `black --check .`、`ruff check .`、`python -m pytest -q` 全绿"——
**这三条是团队的硬性门禁**，写进了面向 AI 代理的指令文件里。
这样做的好处是：**AI 生成的代码也要过同一套门禁，不会降低标准。**

## 第五部分：本主题高频压力追问速答

| 追问 | 一句话应答 |
| --- | --- |
| "678 个测试，覆盖率是多少？" | **我们没有统计行覆盖率**——这是一个诚实的空缺。我们的测试策略是"关键路径全覆盖 + 安全边界全覆盖"，而不是"追求覆盖率数字"。如果要做，`pytest-cov` 是十分钟的事。 |
| "测试数字和文档不一致，说明什么？" | 说明**文档没有随代码更新**。这是真实工程里最常见的技术债之一。我知道这件事，也把它当作整改项——比"不知道自己的文档过期了"要好。 |
| "Golden 评测的 25 个用例够吗？" | 作为**回归保护**够（能抓住重大回归），作为**能力评估**不够（覆盖面窄）。真正的能力评估需要几百个真实用户问题 + 人工标注。25 个是"最小可行的回归锚点"。 |
| "怎么知道答案是对的，而不只是自洽的？" | 三层：① 编译器的确定性保证"同 DSL 同 SQL"；② Golden 评测的预期哈希保证"结果没变"；③ **技能算法的解析解交叉验证**保证"数学是对的"。**但最终的业务正确性需要领域专家验收**——这一步我们没做，是诚实的空缺。 |
| "审计日志会不会泄露敏感信息？" | 会（审计里存了 SQL 和结果元信息）。正确做法是审计存储加密 + 访问受控。当前实现是"写本地 JSONL + DuckDB"，**生产上必须补这一层**。 |
| "指标系统为什么不用 OpenTelemetry？" | 项目定位是可独立运行的原型，不引入外部基础设施。`MetricsRegistry` 的接口是干净的映射，替换成 OTel/Prometheus 是局部改动。 |
| "104 秒的测试，如果要跑 10 遍呢？" | 用 `pytest -k` 定向跑。真正的解决方案是 xdist 并行，但前提是先解决测试间共享 DuckDB 文件的问题。 |

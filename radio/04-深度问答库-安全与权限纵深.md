## 第一部分：身份认证与授权

### Q4.1 — 认证和授权是怎么分开的？为什么 principal 一定要服务端映射？

**答**：

**认证（Authentication）= "你是谁"，授权（Authorization）= "你能看什么"。**

`auth/gateway.py:authenticate(headers)` 的判定顺序：

```
1. Authorization: Bearer <JWT>   → 验签 + 校验 exp/iss/aud/nbf → 取 sub（用户名）
2. X-Session-ID 或 session cookie → 查 SessionStore
3. 都没有 + AUTH_ENABLED=True     → 401
4. 都没有 + AUTH_ENABLED=False    → 返回服务端默认身份（auth_type="default"）
```

拿到用户名后，**关键一步**：

```python
# 伪代码，含义与实现一致
ctx = AuthContext(
    username=...,                      # 来自 token 的 sub
    principal=identity_store.principal_of(username),   # ← 服务端重新映射
    roles=identity_store.roles_of(username),           # ← 服务端重新映射
    auth_type="jwt",
    session_id=...,
)
```

**客户端声明的 `principal` / `roles` 从头到尾没有被读取过。**

**为什么这是必须的**：

假设我们从请求体读 principal：

```http
POST /api/query
{"query": "查一下全国销售额", "principal": "admin"}    ← 攻击者自封管理员
```

那整个权限体系就是纸糊的。**权限主体必须是服务端"推导"出来的，不能是客户端"声明"的。**

**一个容易被忽略的细节**：`AUTH_ENABLED=False`（本地开发）时怎么办？

很多项目的做法是"关鉴权就全放开"——**这是危险的**，因为
"生产环境忘了开鉴权"就变成完全无保护。

我们的做法：**即使鉴权关闭，principal 仍然来自服务端默认配置**
（`AUTH_DEFAULT_PRINCIPAL` / `AUTH_DEFAULT_USER` / `AUTH_DEFAULT_DISPLAY`），
`auth_type="default"`。这保持了同一条不变式：

> **principal 永远来自服务端。**

而且 `AUTH_STRICT=1` 或绑定非 localhost 时，**启动直接拒绝弱默认密钥与关闭鉴权**——
把"配置错误"从运行时的静默风险，变成启动时的响亮失败。

### Q4.2 — 口令是怎么存的？为什么要用 PBKDF2 而不是 SHA256？

**答**：

`auth/identity.py`：

```python
_PBKDF2_ITERATIONS = 200_000
_SALT_BYTES = 16
_HASH_PREFIX = "pbkdf2_sha256"
# 存储格式：pbkdf2_sha256$<迭代次数>$<盐hex>$<哈希hex>
```

**为什么不能只用 SHA256**：

| 攻击方式 | 裸 SHA256 | PBKDF2-SHA256（20 万次迭代 + 随机盐） |
| --- | --- | --- |
| 彩虹表 | 直接命中 | 每个用户盐不同，彩虹表失效 |
| GPU 暴力破解 | 每秒百亿次 | 迭代放大 20 万倍，成本提高 5 个数量级 |
| 相同口令识别 | 哈希相同，一看就知道 | 盐不同，哈希不同 |

**比"用什么算法"更重要的三个工程细节**：

1. **每个用户独立的随机盐**：`secrets.token_bytes(16)`。
   不是全局固定盐——固定盐下，两个用户口令相同哈希就相同，
   攻击者能识别出"这两个人用了同一个口令"。
2. **恒定时间比较**：`hmac.compare_digest(...)` 而不是 `==`。
   普通的 `==` 会在第一个不同字节处提前返回，
   攻击者可以通过**响应时间差异**逐字节猜出哈希。
3. **旧格式兼容但有明确边界**：历史数据里存在固定盐的 64 位十六进制哈希
   （`_LEGACY_SALT = b"futurebi-salt-v1"`），代码仍然接受，
   这保证迁移期间老用户不会突然登不上——但**新口令一律用新格式**。

> **面试话术**："密码存储是个经典问题，但大多数实现栽在细节上：
> 忘了每用户加盐、用了 `==` 比较、迭代次数太少。
> 我们的选择是**用标准库、用推荐参数、把每个细节写进测试**。"

### Q4.3 — JWT 是怎么实现和校验的？为什么不用 PyJWT？

**答**：

`auth/tokens.py` —— **纯标准库实现的 HS256 JWT**：

```python
_ALG = "HS256"
# 声明：sub / iss / aud / iat / nbf / exp / jti
create_token(subject, secret, *, issuer, audience, ttl_seconds, now=None, extra=None)
```

**校验强制五项**：签名 + `exp`（过期）+ `iss`（签发者）+ `aud`（受众）+ `nbf`（生效时间）。

**为什么自己实现而不用 PyJWT**：

1. **依赖最小化**：整个项目的外部依赖很克制，JWT 逻辑不到 100 行，可控。
2. **避免"算法混淆攻击"**：历史上 PyJWT 出过 `alg: none` 和 HS/RS 混淆漏洞
   （攻击者把 `alg` 改成 `none` 或改成 `RS256` 用公钥当 HMAC 密钥）。
   我们自己实现只有一个算法，**根本不存在算法切换的入口**。
3. **`extra` 不携带任何权限**：这是有意设计的。
   token 里只放 `sub`（用户名），**不放 roles、不放 principal**。
   原因是——**token 一旦签发就无法撤销**，
   如果把权限写进 token，那么员工离职或转岗后，他的旧 token 在过期前仍然有效。
   我们把权限查询放在**每次请求**从身份库读取，保证权限变更立即生效。

> **实测的配置约束**：`AUTH_JWT_SECRET` 有一个不安全值黑名单
> （`""`、`"dev-insecure-jwt-secret-change-me"`、`"changeme"`、`"secret"`、`"password"`），
> 弱密钥在启动时被拒绝。
> `AUTH_JWT_TTL=3600`（1 小时）、`AUTH_SESSION_TTL=86400`（1 天）。

### Q4.4 — 登录限流是怎么做的？为什么不是简单的"5 次锁定"？

**答**：

`LoginRateLimiter` 使用**指数退避**，而不是固定阈值锁定：

```python
AUTH_LOGIN_MAX_FAILURES   # 触发退避的失败次数
AUTH_LOGIN_BASE_SECONDS   # 基础退避秒数
AUTH_LOGIN_MAX_SECONDS    # 退避上限
```

**为什么指数退避优于固定锁定**：

| 方案 | 攻击者体验 | 正常用户被误伤的后果 |
| --- | --- | --- |
| 5 次锁定账号 | 换账号继续爆破 | 打错 5 次密码就被锁，找客服 |
| 固定 30 秒冷却 | 每 30 秒可试一次，仍然可观 | 等 30 秒 |
| **指数退避** | 第 6 次等 1s，第 10 次等 512s，第 15 次等到上限 | **几乎无感**（正常人不会连错 10 次） |

而且限流键是**用户名 + IP 双维度**：
- 只按 IP 限流 → 攻击者换 IP 就绕过；
- 只按用户名限流 → 攻击者可以对全公司账号各试一次（**密码喷洒攻击**）；
- 双维度叠加 → 两条路都被堵住。

**存储外置**：`LoginRateLimiter` 的计数存在 `STATE_STORE_DB`（SQLite）里，
所以**多 worker 部署或进程重启后限流状态不丢**——
这是很多自研限流的常见漏洞（内存计数，重启即清空）。

## 第二部分：数据权限（表级 / 列级 / 行级）

### Q4.5 — 三级权限具体怎么实现？给一段真实代码。

**答**：

`security/guard.py:apply_policy(dsl, principal)`，104 行，四步：

```python
def apply_policy(dsl: QueryDSL, principal: str | None) -> QueryDSL:
    policy = resolve_policy(principal)          # ① 解析策略
    if policy is None:                          #    principal=None → 全可见（系统内部调用）
        return dsl

    tables = _referenced_tables(dsl)            # ② 从 DSL 反推引用了哪些物理表
    forbidden_tables = tables - set(policy.allowed_tables)
    if forbidden_tables:
        raise SecurityError(f"主体 {principal!r} 无权访问表: {sorted(forbidden_tables)}")

    fields = _referenced_fields(dsl)            # ③ 从 DSL 反推引用了哪些逻辑字段
    forbidden_fields = fields & set(policy.forbidden_columns)
    if forbidden_fields:
        raise SecurityError(f"主体 {principal!r} 无权访问字段: {sorted(forbidden_fields)}")

    extra = [_resolve_row_filter(rf, principal) for rf in policy.row_filters]  # ④ RLS
    return dsl.model_copy(update={"filters": list(dsl.filters) + extra})
```

**关键点：`_referenced_fields` 要"穷尽地"扫描 DSL 的每一个角落**：
- `metrics` 里每个指标的 `field`（含 `RatioMetric` 的分子与分母、`WindowMetric` 的 base）；
- `dimensions` 里每个维度的 `field`；
- `filters` 里每个过滤条件的 `field`。

**为什么必须穷尽**：曾经有一类漏洞是"只检查了指标字段，
漏掉了**过滤条件里的字段**"。结果是：用户虽然查不到 `refund_amount` 这个指标，
但可以写 `WHERE refund_amount > 1000` 来**通过行数侧信道推断出退款金额分布**。
这就是**侧信道泄露（side-channel leak）**。

> **面试话术**："权限校验最大的坑不是'漏了一个字段'，
> 而是'**没意识到某个地方也算使用了字段**'。
> 所以我们不写'检查指标字段'，而是写一个 `_referenced_fields()` 函数，
> 把'什么样的 DSL 算引用了这个字段'这件事收敛到一个地方定义。"

### Q4.6 — RLS 是怎么做的？为什么用"参数化模板"而不是写死？

**答**：

策略配置文件 `config/policies.json` 里：

```json
{
  "analyst": {
    "allowed_tables": ["fact_orders", "fact_refunds", "dim_user", "dim_product", "dim_shop"],
    "forbidden_columns": [],
    "row_filters": [
      {"field": "province", "operator": "in", "param": "principal.provinces"}
    ]
  }
}
```

主体属性 `config/principals.json`：

```json
{
  "analyst":    {"provinces": ["广东", "浙江", "江苏", "北京", "上海"]},
  "restricted": {"provinces": ["广东"]}
}
```

运行时 `_resolve_row_filter` 把 `param` 解析为**主体的实际属性值**。
如果主体缺少这个属性 → `SecurityError(f"主体 {principal!r} 缺少 RLS 属性 {attr!r}")`，
**失败关闭（fail-closed）**：宁可拒绝，不能全放。

**实测的完整策略矩阵**：

| 主体 | 可访问表 | 禁止列 | 行过滤器 |
| --- | --- | --- | --- |
| `admin` | 全部 5 张 | 无 | 无 |
| `analyst` | 全部 5 张 | 无 | `province IN (广东,浙江,江苏,北京,上海)` |
| `restricted` | `dim_product` / `dim_user` / `fact_orders` | `discount_amount` / `refund_amount` | `province IN (广东)` |

**实测 `bob`（restricted）生成的 SQL**：

```sql
SELECT SUM(f.order_amount) AS "gmv"
FROM fact_orders f
JOIN dim_user u ON u.user_id = f.user_id
WHERE f.pay_status = 'SUCCESS'
  AND u.province IN ('广东')
  AND f.order_time >= TIMESTAMP '2024-06-01 00:00:00'
  AND f.order_time <  TIMESTAMP '2024-07-01 00:00:00'
```

**"参数化模板" vs "写死"的价值**：

| 方案 | 加一个省份 | 加一个主体 | 改权限的代码风险 |
| --- | --- | --- | --- |
| 写死在 Python 里 | 改代码 + 测试 + 发版 | 改代码 + 测试 + 发版 | 高（可能引入逻辑 bug） |
| **参数化模板（JSON）** | **改一行 JSON** | **加一段 JSON** | 零（数据变化，代码不变） |

**更重要的是"注入"而非"校验"的语义差异**：

- **校验式**：检查用户/模型给的 DSL 里有没有 `province` 过滤条件，没有就拒绝。
  问题：用户可以写 `province IN (全部省份)` 来绕过。
- **注入式（我们）**：**无条件追加**一个 RLS 过滤条件。
  用户写什么都会和这个条件做 AND，**无法绕过**。

### Q4.7 — RLS 的重复注入问题怎么解决？会不会注入两次？

**答**：

**这是一个真实的坑，也是很好的面试素材。**

**问题场景**：多轮对话。第一轮问了"广东的 GMV"，DSL 里被注入了
`province IN ('广东')`，这个**已经被注入过的 DSL 被存进了会话记忆**
（`state.last_dsl`）。

第二轮用户说"那浙江呢？"，系统从记忆里取出 `last_dsl` 作为基底，
合并新条件——**如果直接合并再 `apply_policy`，就会变成**：

```sql
WHERE province IN ('广东') AND province IN ('浙江')   -- 恒假！永远返回空
```

**修复方案**（`agent/memory.py:resolve_context`）：

```python
# 合并前先剥离已注入的 RLS 过滤器
clean_dsl = strip_rls_filters(dsl, principal)
merged = _apply_deltas(clean_dsl, ...)
# 然后恰好重新注入一次
final_dsl = apply_policy(merged, principal)
```

**为什么必须"先剥离再合并，最后注入一次"**，而不是"合并后去重"：
因为去重需要判断"哪个 filter 是 RLS 注入的、哪个是用户提的"，
而用户**完全可能合法地**自己提一个 `province = '广东'`。
"剥离-合并-注入"的顺序保证语义清晰：**用户条件归用户，系统条件归系统。**

> **面试话术**："这条链路上有个很容易被忽略的对称性要求：
> **有几次注入，就必须有几次剥离**。多轮对话把'状态'从无状态 API 里引进来时，
> 这种不对称几乎一定会出问题。我们的做法是把'注入'和'剥离'写成一对函数，
> 让它们在同一份测试里互相验证。"

### Q4.8 — 生成前作用域（scope.py）到底比生成后校验强在哪？

**答**：

`security/scope.py`（72 行）提供：

```python
resolve_policy(principal)      # None → 全可见；未注册主体 → SecurityError（fail-closed）
scoped_tables(principal)       # 可见物理表集合
scoped_fields(principal)       # 可见逻辑字段集合
scoped_catalog(principal)      # 裁剪后的目录
scoped_field_listing(p)        # 注入 Prompt 的字段清单文本（按名称排序，确定性）
is_field_allowed / is_table_allowed
```

**关键差异**：

| 维度 | 生成后校验 | 生成前收窄（我们做的） |
| --- | --- | --- |
| 模型是否"知道"敏感字段存在 | **知道**（可能被诱导说出字段名） | **不知道** |
| 攻击面 | 模型可能构造绕过话术 | 没有可绕过的目标 |
| 错误信息泄露 | 报错可能透露字段名 | 不存在这个字段 |
| 与"事后校验"的关系 | 唯一防线 | **第一道**，事后校验仍然是第二道 |

**实测证据**：`restricted` 主体的 Prompt 里没有 `refund_amount`。
当用户问"各品类退款率"时，模型**不会**尝试构造这个查询——
因为它看不到这个字段。即使它猜到了名字（比如从训练数据里知道电商系统常有 `refund_amount`），
`apply_policy` 仍会抛 `SecurityError`。

> **面试话术**："'守卫前移'这个词听起来像优化，其实本质是**减少攻击面**。
> 事后校验是'你打我一拳我挡住'，事前收窄是'你根本够不着我'。
> 两者都要有，但事前收窄的性价比高得多。"

### Q4.9 — 未注册的主体为什么是"拒绝"而不是"默认全可见"？

**答**：

`security/scope.py:resolve_policy` 的行为：

```python
if principal is None:
    return None              # 系统内部调用：全可见
policy = POLICIES.get(principal)
if policy is None:
    raise SecurityError(f"未登记的主体: {principal!r}")   # ← fail-closed
return policy
```

**为什么这样设计**：

考虑一个常见故障场景：管理员在 `principals.json` 里新建了用户 `carol`，
但**忘了在 `policies.json` 里给她配策略**。此时：

- **默认全可见（fail-open）**：carol 能看到全公司数据，而且**没有人会收到告警**——
  因为系统"正常工作"了。
- **拒绝（fail-closed，我们）**：carol 一查询就报错，
  管理员立刻发现问题并补配置。

> **面试话术**："安全系统的默认值必须是'关'。
> 一个 fail-open 的权限系统，会在你最不希望的时刻（新员工入职、配置迁移、数据源新增）
> 安静地放开所有权限。**响亮地失败，永远好过安静地放行。**"

注意 `principal is None` 时返回"全可见"——这是给**系统内部调用**留的口子
（比如审计分析、评测脚本）。区别在于：`None` 是**代码显式传的**，
而"未知字符串"是**外部输入的**，两者信任级别完全不同。

### Q4.10 — 权限策略是启动时加载还是热加载？改权限要重启吗？

**答**：

当前实现：**启动时加载 + 提供 `refresh_policies()` 函数重新加载**。

`web/service.py:ensure_db()` 在服务启动时调用：

```python
from security.policy_loader import refresh_policies
from semantic.catalog_loader import refresh_catalog
refresh_catalog(db_path=settings.DB_PATH)
refresh_policies()
```

**当前的取舍**：

- **优点**：策略在内存里是**不可变快照**，权限判定是纯内存查表，
  没有 I/O、没有并发一致性问题、没有"改了一半"的中间态。
- **缺点**：**没有运行时自动热加载**。改了 `policies.json` 需要重启服务，
  或者显式调用 `refresh_policies()`。

**为什么可以接受**：权限变更是**低频、需要审计**的操作。
"改配置文件 → 重启 → 生效"这个流程本身带有审批和留痕的意味。
相比之下，一个"改了就立即生效"的系统，如果配置写错了，会**立即影响所有在线用户**。

**如果要做热加载，正确做法是什么**（这是加分回答）：

> "用文件 mtime 或内容哈希做轮询，变化时构建**新的不可变策略对象**，
> 然后原子替换引用（`POLICIES = new_policies`）。
> 关键是**不能原地修改**——原地改会让正在进行的查询看到半新半旧的权限视图。
> 另外要加监控：策略加载失败必须告警并**保留旧策略**，
> 绝不能'加载失败 → 空策略 → 全员无权限'或'全员全权限'。"

## 第三部分：防注入（这是本项目的招牌）

### Q4.11 — 提示词注入（Prompt Injection）你们怎么防？

**答**：

先澄清一件事：**提示词注入无法在"提示词层面"根治**。
只要模型读到了攻击者可控的文本，它就可能被影响。

**所以我们的策略不是"防住注入"，而是"让注入成功后什么也做不了"。**

具体分三层：

**第一层：缩小注入面。**

- 用户输入**只作为 query 字段**传给模型，不拼进 system prompt；
- 沙箱代码里**不能联网**（Docker 后端 `--net none`），
  防止外部内容作为注入载体进入；
- 检索到的口径文档是**本地静态文件**，不是从外部拉取。

**第二层：让注入的产物无法通过校验。**

假设攻击者成功让模型产出了：

```json
{"metrics": [...], "raw_sql": "DROP TABLE fact_orders"}
```

→ `extra="forbid"` **直接拒绝**。

假设攻击者让模型产出合法字段但越权的：

```json
{"metrics": [{"field": "refund_amount", "agg": "sum"}]}
```

→ `apply_policy` **抛 SecurityError**（restricted 主体）。

**第三层：即使生成了 SQL，也执行不了。**

假设所有前序防线都被绕过，SQL 里出现了 `DROP TABLE`：

- `assert_read_only_sql` 第一层语句形态检查就拦下（只允许 `SELECT`/`WITH` 开头，
  且不允许出现 `;`）；
- 关键词黑名单拦截 DDL/DML；
- sqlglot AST 检查根节点必须是 `exp.Select` 或 `exp.Union`。

**第四层：执行后没有副作用。**

DuckDB 连接以**只读模式**打开，且**连接池里的连接全部只读**。

> **面试话术**："正确的安全问法不是'我能防住注入吗'，
> 而是'**注入成功之后，攻击者能做什么**'。
> 我们的答案是想做的都做不了——不是因为我们识别了恶意，
> 而是因为系统里**没有一个地方可以实现恶意**。"

---

### Q4.12 — "裸 SQL 网关"是什么？为什么叫三重防线？

**答**：

`core/retrieval/guardrails.py` 的 `GuardrailViolation` ——
一个**在工具调用入口的文本级哨兵**。

**它检查什么**：

1. **字符串载荷**：工具参数字段本身被要求是 JSON / 结构化数据，
   如果传进来的是一个裸 SQL 字符串，直接拒绝；
2. **`sql` 键**：任何工具参数里出现名为 `sql` 的键 → 拒绝；
3. **自由文本中的 SQL 形态**：即使参数是"自然语言"，如果它包含
   `SELECT ... FROM ...` / `DROP TABLE` / `INSERT INTO` 这类形态 → 拒绝。

**实测**：`sql` 键与 SQL 形态注入值**双双被 blocked**。

**"三重防线"指的是**：

| 防线 | 位置 | 防的是 |
| --- | --- | --- |
| 1. 契约 | `dsl_schema.py` | LLM **无法产出** SQL（没有字段可放） |
| 2. 网关 | `guardrails.py` | 上层调用方**无法传入** SQL（工具层拒绝） |
| 3. 执行层 | `exec/guards.py` | 万一前面都被绕过，SQL **执行不了**（只读校验） |

> **面试话术**："这条链路上有一个隐含的哲学：
> **凡是'SQL 文本'出现的地方，都视为敌意。**
> 系统内部唯一的 SQL 来源是编译器，其他任何地方出现 SQL 都是异常信号。"

### Q4.13 — 只读校验的"四层"具体是哪四层？为什么需要四层？

**答**：

`exec/guards.py` 的 `assert_read_only_sql(sql)`：

**第 1 层：语句形态**（最便宜、最先跑）

```python
# 必须以 SELECT 或 WITH 开头；不允许出现分号（防多语句）
```

为什么先跑这层：**零成本**。99% 的恶意 SQL 在这一层就被挡住，
不需要昂贵的 AST 解析。

**第 2 层：关键词黑名单**

拦截 `DROP`、`DELETE`、`TRUNCATE`、`ALTER`、`INSERT`、`UPDATE`、`CREATE`，
以及 `COPY` / `EXPORT` / `IMPORT` / `INSTALL` / `LOAD`（DuckDB 特有的文件与扩展操作）。

**第 3 层：禁用表函数正则**

```
read_*  /  *_scan  /  glob  /  query  /  parquet_*
```

**为什么这一层必须有**：`read_csv('/etc/passwd')` 这种攻击**不含任何 DDL 关键词**，
形态上还是 `SELECT`。如果只有前两层，攻击者可以：

```sql
SELECT * FROM read_csv('/etc/passwd')     -- 读服务器本地文件！
```

**第 4 层：sqlglot AST 结构检查**（`_assert_read_only_structure`）

- 解析后必须**恰好一条语句**；
- 根节点必须是 `exp.Select` 或 `exp.Union`；
- 全树 walk：拒绝被禁函数；
- 拒绝带引号/字面量的表引用（`FROM 'file.parquet'`）；
- 拒绝 `exp.Into`（`SELECT ... INTO`）。

**为什么每层都不能省**：

| 若缺少 | 攻击示例 |
| --- | --- |
| 形态检查 | `SELECT 1; DROP TABLE x`（多语句） |
| 关键词黑名单 | `DELETE FROM fact_orders`（单语句 DML） |
| 表函数正则 | `SELECT * FROM read_csv('/etc/passwd')` |
| AST 结构检查 | 通过 `UNION` 或嵌套子查询构造的绕过变体 |

**故障关闭（fail-closed）设计**：AST 解析遇到
`sqlglot.errors.ParseError` 或语句数 ≠ 1 时，**都抛异常**（拒绝），
而不是"解析不了就放行"。

> **面试话术**："四层不是因为强迫症，是因为**每层能挡的攻击类型不同**。
> 前三层是文本级启发式（快但可绕过），第四层是语法级（慢但难绕过）。
> 任何一层的策略都必须是**默认拒绝**——解析失败不放行。"

### Q4.14 — 执行前审计门（GuardrailAgent）和只读校验有什么区别？为什么不合并？

**答**：

**它们的目标不同**：

| | `assert_read_only_sql` | `assert_guardrails`（`exec/audit.py`） |
| --- | --- | --- |
| 目标 | **防止恶意 SQL** | **防止错误 SQL 造成资源灾难** |
| 检查项 | 只读形态 | `readonly_structure` / `cartesian_product` / `unbounded_output` |
| 触发场景 | 有人注入 | 编译器自己出了 bug |
| 严重级别 | 全部拒绝 | 前两项 REJECTED，第三项 **WARNING** |

**为什么需要 `cartesian_product` 检测**（这是本项目的一个真实故事）：

编译器的 MoM 实现曾经生成 `FROM cur, prev`。在标量场景下这是**正确**的（1×1=1 行），
但静态审计判为笛卡尔积并**拒绝**了执行。这个"误报"其实指向了一个真实隐患：
**一旦维度处理逻辑有变动，`cur` 和 `prev` 都可能变成多行，
`FROM cur, prev` 就会真的变成 N×M 的笛卡尔积。**

审计在维度逻辑出问题**之前**就把它拦下来了。

**`unbounded_output` 为什么是 WARNING 而不是 REJECTED**：

这是设计上的克制。理由有两条：
1. **真实边界由执行层的 `MAX_RESULT_ROWS` 硬上限承担**，审计不需要重复兜底；
2. **编译器已保证**：除了纯标量聚合，所有查询形态都会加 `LIMIT`。
   所以"无界输出"在当前架构下**不会真正发生**——
   审计在这里是**不变式防御**，不是主防线。

**把不变式防御误升级为 REJECTED 的后果**：任何编译器的小改动
（比如某个分支忘了加 LIMIT 但实际不会超行数）都会直接**拒绝用户查询**，
可用性代价远高于收益。

**为什么两者不合并**：

> "只读校验的语义是'**这条 SQL 是恶意的吗**'，
> 审计的语义是'**这条 SQL 是合理的吗**'。
> 恶意和错误是两个正交的维度。
> 合并会带来一个具体的坏处：**错误信息失去区分度**——
> 用户看到'查询被拒绝'时，无法知道是权限问题、还是 SQL 有问题、还是资源超限。
> 我们的原则是：**每一种失败都要有一个能定位原因的错误类型**。"

**依赖方向细节**：`exec/guards.py` 在 `execute_sql` 内部**惰性导入** `exec.audit`，
避免循环导入。依赖方向是 `audit → guards`（audit 复用 guards 的
`_assert_read_only_structure`），所以 guards 不能在模块顶层 import audit。

### Q4.15 — `GuardrailRejected` 是怎么和自愈循环兼容的？

**答**：

```python
class GuardrailRejected(SqlExecutionError):
    code = "guardrail_rejected"
    # 消息：f"执行前审计拒绝（{len(rejected)}项）：{detail}"
    # detail = "；".join(f"[{f.check}] {f.message}")
```

**继承 `SqlExecutionError` 是刻意的**：
自愈循环判断"这个错误值不值得重试"时，依赖异常类型。
`GuardrailRejected` 是 `SqlExecutionError` 的子类，
所以它**自动复用了现有的自愈逻辑**——不需要改一行自愈代码。

**而且它的消息是可自愈的**：消息里包含具体的 `check` 名和 `message`，
喂回 LLM 后模型能理解"我生成的 SQL 有笛卡尔积",
从而重写 DSL（比如补上分区维度）。

**注意**：`GuardrailRejected` **不在** `_is_permanent_error` 集合里
（那个集合是 `{SecurityError, UnknownToolError, PermissionError}`）。
所以审计拒绝**会触发自愈重试**。这是正确的：
笛卡尔积往往是"DSL 写法不对"，重写有机会修好；
而权限错误重试一万次也没用，应该立即停止。

> **面试话术**："错误分类是自愈系统的核心设计。
> 我们只分两类：**可修的**（编译错误、执行错误、审计拒绝）和**不可修的**（权限、未知工具）。
> 前者重试，后者立即失败。**给不可修的错误重试，是在浪费 token 和用户时间。**"

## 第四部分：数据脱敏与沙箱安全

### Q4.16 — PII 脱敏是怎么做的？为什么是"启发式"？

**答**：

`core/retrieval/pii.py` —— 两重识别：

1. **列名启发式**：列名匹配敏感关键词（phone / id_card / email / name 等）；
2. **值形态正则**：即使列名不敏感，值长得像手机号/身份证号也会被脱敏。

**脱敏方式**：**确定性哈希掩码**（sha256 前 8 位）。

**为什么用哈希而不是"打星号"**：

| 方式 | 效果 |
| --- | --- |
| `138****5678` | 值仍可部分反推，且**同一手机号每次掩码相同**（可关联） |
| 全 `***` | 完全不可用——**破坏了分组聚合能力**（所有记录变成同一个值） |
| **sha256 前 8 位** | 不可反推；**同一输入产生同一掩码**，所以 `GROUP BY phone` 仍能正确分组计数 |

**为什么是启发式而非全自动**：

> "PII 识别在工业界就是个**概率问题**——没有 100% 准确的正则能识别所有个人信息。
> 我们的策略是**宁可多脱敏，不可少脱敏**：
> 列名可疑就脱敏，值像 PII 也脱敏。
> 代价是可能误伤一些正常数据（比如某些订单号恰好符合身份证格式），
> 但这个代价远小于泄露真实个人信息。
>
> 同时我们在架构上给了一道保险：**生产环境的 mock 数仓里根本没有 PII 列**。
> 也就是说，即使脱敏层完全失效，也没有真实个人信息可泄露。"

**实测局限（诚实说明）**：正因为 mock 数仓没有 PII 列，
**脱敏层无法端到端实测**——基准评测报告里也指出了这一点。
这是"演示环境"和"生产环境"的差异，属于已知局限。

### Q4.17 — 沙箱是怎么隔离的？AST 守卫为什么不够？

**答**：

**先回答"为什么 AST 守卫不够"**：AST 静态检查是**黑名单**，
而黑名单永远存在遗漏。比如：

```python
# 看起来无害
x = (1).__class__.__bases__[0].__subclasses__()
```

这是 Python 沙箱逃逸的经典手法——通过 `__subclasses__()` 拿到所有已加载的类，
进而找到 `os.system` 之类的危险函数。**静态检查很难穷尽所有变体。**

**所以我们的沙箱是三层**：

| 层 | 机制 | 位置 |
| --- | --- | --- |
| 1. 静态 AST 守卫 | 拒绝危险 import / 调用 / dunder 属性 | `core/sandbox/ast_guard.py` |
| 2. 运行时限制 | 模块白名单 import + workspace 受限 `open` + 受限 builtins | `core/sandbox/_bootstrap.py` |
| 3. 进程/容器隔离 | Docker（`--net none --cap-drop ALL`）/ 子进程 | `core/sandbox/backends.py` |

**AST 守卫的黑名单内容**（部分）：

- **禁用模块**：`os`、`sys`、`subprocess`、`socket`、`ctypes`、`importlib`、
  `shutil`、`multiprocessing`、`http`、`urllib`、`requests`、`pickle`、`pathlib`、
  `tempfile`、`glob`、`platform`、`winreg` 等；
- **禁用调用**：`eval`、`exec`、`compile`、`__import__`、`globals`、`locals`、
  `vars`、`open`、`input`、`breakpoint`、`exit`、`super`、`setattr`、`delattr` 等；
- **禁用属性（dunder 逃逸向量）**：`__class__`、`__subclasses__`、`__bases__`、
  `__mro__`、`__globals__`、`__builtins__`、`__code__`、`__closure__`、`__dict__`、
  `__import__`、`__getattribute__`、`__setattr__`、`__reduce__`、`__loader__`、`__spec__` 等；
- **相对导入**：`from . import x` 这种（`node.level > 0`）也拒绝。

**还处理了两个微妙场景**：

```python
getattr(obj, "__class__")   # 字符串字面量绕过 dunder 检查 → 也拒绝
```

**违规报告是可复用的**：`StaticGuardReport.summary()` 产出
`"L{行号} {类别}: {详情}"` 格式，前 5 条用 `"; "` 连接，
**直接作为 LLM 自愈的上下文**——沙箱代码报错也能触发重写。

### Q4.18 — 沙箱后端的 Docker 和子进程有什么区别？为什么两个都要？

**答**：

`core/sandbox/backends.py`：

| 维度 | `DockerBackend` | `SubprocessBackend` |
| --- | --- | --- |
| 网络 | `--net none`（**完全无网**） | 无网络限制 |
| 能力 | `--cap-drop ALL` | 无 |
| 用户 | UID 10001（非 root） | POSIX 下 `setuid`，Windows 下无 |
| 文件系统 | 只读 rootfs，`/workspace` 只读，写入重定向到 `/tmp/workspace` | 无 |
| 资源限制 | cgroup（内存/CPU） | POSIX 下 `resource.setrlimit` |
| `limits_enforced` | **True** | POSIX: True / **Windows: False（如实报告）** |
| `is_available()` | 运行时探测 Docker 是否存在 | 恒为 True |

`default_backend()` 的策略：**优先 Docker，探测不到则回退子进程**。

**为什么要"如实报告 `limits_enforced=False`"**：

这是本项目一个值得称道的诚实设计。Windows 上没有 `setrlimit`，
所以子进程后端**实际上无法强制内存和 CPU 上限**。
它完全可以默默报告 `True`（反正没人验证），
但它选择**如实告诉上层"我的限制没有真正生效"**。

**为什么两个都要**：
- **Docker**：生产环境，强隔离；
- **子进程**：开发环境 / CI（无 Docker），能跑但有明确的能力声明。

> **面试话术**："降级方案最容易出的问题是'**假装自己很强**'。
> 一个降级后端如果谎报安全能力，会让上层做出错误的信任决策。
> 我们让 `BackendResult` 带上 `limits_enforced` 标志，
> 上层可以据此决定'这个环境能不能跑不可信代码'。"

---

### Q4.19 — 沙箱里的代码能看到数据吗？会不会把数据偷出去？

**答**：

**能看到数据，但只能看到"该看到的那部分"**，且**偷不出去**。

**数据流入**：
- 查询结果先经 **PII 脱敏**，再物化为 Parquet 文件（`ParquetRef`，带 sha256）；
- 沙箱通过 **只读挂载** 访问 `/workspace/inputs/*.parquet`；
- 沙箱**没有任何数据库连接**（不是"禁止连接"，而是**根本没配**）。

**数据流出**：
- 沙箱**输出协议**规定必须写 `summary.json`，结构有白名单：
  ```python
  _SUMMARY_ALLOWED_KEYS = frozenset({"title", "metrics", "table", "findings", "extra"})
  ```
  出现协议外的键 → 报错 `f"summary.json含协议外键: {sorted(unexpected)}"`；
- **表格行数硬上限 100 行**：
  ```
  f"聚合矩阵 {len(table['rows'])}行超出 {MAX_SUMMARY_ROWS}行上限（请先聚合）"
  ```
  这是**防止把全量数据通过摘要通道带出去**——强迫沙箱**先聚合再输出**；
- `stdout` 尾部截断到最后 2000 字符（防止用 print 把数据打出来）；
- Docker 后端 `--net none`，**没有任何网络出口**。

**威胁模型结论**：

> "沙箱的威胁模型是**防御'被误导的代码'，不是防御'恶意攻击者'**。
> 因为沙箱代码是 LLM 生成的，我们担心的是它写出了一个会泄露数据、
> 或者写出无限循环的脚本——而不是担心一个人类攻击者周密策划逃逸。
> 对于前者，AST 守卫 + 输出协议 + 行数上限足够了；
> 对于后者，Docker 的 `--net none --cap-drop ALL` 提供了一层真隔离。"

## 第五部分：本主题高频压力追问速答

| 追问 | 一句话应答 |
| --- | --- |
| "如果攻击者拿到 JWT 怎么办？" | JWT TTL 1 小时；权限每次请求从身份库读，**改权限立即生效**（token 里不放权限就是为了这个）；Session 可服务端吊销。 |
| "SQL 注入真的完全不可能吗？" | 系统里唯一产出 SQL 的地方是编译器，而编译器的所有动态部分（标识符、字面量）都经过类型校验 + 转义。剩余风险是**编译器自身的逻辑 bug**，这也是为什么执行层还有独立的 AST 只读校验。 |
| "权限过滤会不会被 LLM 重写绕过？" | 会——所以我们**在自愈重写后重新调用 `apply_policy`**（`_run_guarded` 里）。这是防权限逃逸的关键一步。 |
| "你们怎么防止内部人员导出全量数据？" | 导出有行数上限、有掩码层；审计记录每次导出的行数与列；`/api/...` 下载端点做**属主校验**（防止改 IDOR 参数下载别人的导出）。 |
| "为什么不用数据库自带的 RLS？" | 我们的目标引擎可能是多种（DuckDB / 数仓 / 湖），自研 RLS 在**编译器输出层**做，与引擎解耦。代价是必须自己保证穷尽性——这就是 `_referenced_fields()` 要覆盖指标/维度/过滤三处的原因。 |
| "监控告警呢？" | error 级日志覆盖：熔断、审计拒绝、自愈额度耗尽、QA error 级发现。这些是**可告警事件**；warning 级覆盖可自愈报错与降级路径。 |
| "有没有做过渗透测试？" | 我们做过**对抗性评测**：写操作注入、PII 越狱、越权套取、无界导出等 15 个对抗用例全链路实测，一票否决项（写操作、PII 泄露、严重计算错误、死循环）**均未触发**。诚实的结论是：这不等同于专业渗透测试，正式的第三方安全评估仍是上线前要做的事。 |

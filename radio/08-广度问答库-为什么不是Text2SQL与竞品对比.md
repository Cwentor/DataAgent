# 08 · 广度问答库：为什么不是 Text2SQL，以及竞品对比

> **适用场景**：系统设计面、架构面、以及任何"你这个方案和主流方案有什么不同"的追问。
> **回答风格**：先给结论，再给对比表，最后给"什么情况下我会选另一条路"（这是最能体现判断力的部分）。

---

## 第一部分：为什么不是 Text2SQL

### Q8.1 — 什么是 Text2SQL？业界主流方案是什么？

**答**：

**Text2SQL（自然语言转 SQL）**：让大模型直接把自然语言问题翻译成 SQL 语句执行。

业界主流的技术路线有四种：

| 路线 | 做法 | 代表 |
| --- | --- | --- |
| **A. 纯 Text2SQL** | Prompt 里给表结构，模型直接吐 SQL | 早期 ChatBI、多数开源 Demo |
| **B. Text2SQL + 执行纠错** | 执行报错后把错误喂回去重试 | 大部分工业界实现（含某些商业产品） |
| **C. 语义层 + Text2SQL 受限** | 在语义层（指标/维度/口径）之上生成 SQL | dbt Semantic Layer、Cube、LookML 生态 |
| **D. 契约 DSL + 确定性编译（本项目）** | 模型只产受控 JSON，SQL 由编译器生成 | 我们的方案 |

**我们走的是 D。**

**A 和 B 的区别只是"重试几次"，本质都是"SQL 由模型写"。**
**C 已经接近我们的思路**——它引入了语义层来约束模型，
但通常仍然让模型**在语义层之上写 SQL 片段**（比如 `MEASURE(gmv)`、
`{{ Dimension('order__province') }}`），
**表达能力的边界仍然是"一段可执行的查询文本"**。

**D 的关键区别**：模型产出的不是"查询文本"，而是"**查询意图的 JSON 描述**"。
SQL 由一个**模型完全无法影响的**编译器产出。

### Q8.2 — 那为什么不直接用 Text2SQL 加纠错重试？成本低得多。

**答**：

"成本低"只在 **Demo 阶段**成立。上生产后，Text2SQL 的四个问题会依次暴露：

### 问题 1：幻觉字段（Hallucination）

模型会生成**看起来合理但不存在**的列名。

- Text2SQL 的表现：执行报错 → 重试 → 可能还是错 → 用户等待 3 轮后失败；
- 我们的表现：**契约层第一次就拒绝**，错误信息精确到
  "未登记的字段 `order_total`，只能引用语义目录中的逻辑字段"，
  自愈时模型拿到的是**明确的可用字段列表**。

**关键差异不是"能不能发现"，而是"发现的时机"**：
Text2SQL 在**查数据库时**发现，我们在**生成后、编译前**发现。

### 问题 2：方言漂移（Dialect Drift）

模型在不同轮次可能生成 MySQL 语法、PostgreSQL 语法、甚至混合语法。

- Text2SQL：靠 Prompt 里写"请使用 DuckDB 语法"——**软约束，会漂移**；
- 我们：**Prompt 里根本不出现 SQL 方言**，编译器只产出一种方言。

**这一点在换引擎时价值巨大**：Text2SQL 换引擎要改 Prompt + 重新调优；
我们换引擎只改编译器的输出适配层，**Prompt 一个字不用动**。

### 问题 3：权限泄漏（这是最致命的）

权限过滤条件（RLS）如果由模型生成：

- **忘记加** → 数据泄露；
- **加错了**（比如写成 `province = '广东' OR 1=1`）→ 数据泄露；
- **用户提示"忽略之前的权限要求"** → 提示词注入，数据泄露。

Text2SQL 的防御手段是"**检查生成的 SQL 里有没有正确的过滤条件**"——
这是一个**不可能穷尽的检查**（SQL 有无数种写法能达到同样的语义）。

我们的做法是在**编译器之后**注入过滤条件：

```sql
-- 无论上游 DSL 长什么样，最终 SQL 里一定会有这一段
AND u.province IN ('广东')
```

**注入式 > 校验式**，这是架构层面的差异，不是实现细节。

### 问题 4：不可测试性

Text2SQL 的测试只能断言"**结果对不对**"。
但同一个问题的正确 SQL 有无数种写法，结果对也可能掩盖"这次凑巧对了"。

我们的编译器是纯函数，测试可以断言"**SQL 长什么样**"：

```python
assert 'NULLIF(prev."gmv", 0)' in sql        # 除零防护在不在
assert 'ROW_NUMBER() OVER (PARTITION BY u.province' in sql   # 分区对不对
assert sql.count("LIMIT") == 1               # LIMIT 没重复
```

**前者能告诉你"结果不对"，后者能告诉你"第 42 行的分区列写错了"。**

### Q8.3 — 但 DSL 表达能力有限啊，复杂问题怎么办？

**答**：

**这是这个方案最需要正面回答的问题，我用"三层回答"来应对。**

**第一层：DSL 的表达能力比我一开始以为的强得多。**

当前 DSL 支持：

| 能力 | 例子 |
| --- | --- |
| 六种聚合 | SUM / COUNT / COUNT DISTINCT / AVG / MIN / MAX |
| 比率指标 | 退款率 = SUM(refund_amount) / SUM(order_amount) |
| 窗口指标 | 累计求和（cumsum）、移动平均（moving_avg） |
| 分组 Top-N | 每省销售额 Top 3 品类 |
| 同环比 | 同比（YoY）、环比（MoM），含季度粒度 |
| 日期补零 | 时间序列补齐缺失日期 |
| 多维度分组 | 省份 × 品类 × 品牌 |
| 半开区间时间窗 | 5 种相对时间模式 × 5 种单位 |
| 多轮继承 | 继承 / 下钻 / 话题切换 |

**覆盖了企业数据分析里 80%+ 的高频查询形态。**

**第二层：剩下的 20% 用不同的机制解决，而不是靠放宽 DSL。**

| 需求类型 | 解决机制 |
| --- | --- |
| 自定义算法分析 | **沙箱代码解释器**（写 Python，不写 SQL） |
| 归因分析 | **技能包**（下钻/分解/异常检测/Shapley） |
| 多步推理 | **编排器**（六节点 + 重规划） |
| 明细导出 | **专用导出工具**（有独立的上限与脱敏） |
| 真正的一次性复杂 SQL | **明确不支持**，引导用户提需求 → 人工固化为新的 DSL 能力 |

**第三层：最后那个"明确不支持"是刻意的设计，不是缺陷。**

这样做的代价是：**能力的增长需要工程介入**（加字段、加算子）。
收益是：**每一次能力增长都是可审计、可测试、可复现的**。

> **面试话术**："一个能回答 100% 问题但 30% 答案是错的系统，
> 不如一个能回答 80% 问题且答案全对的系统。
> 在企业数据场景里，**'我不知道'是可以接受的，'我错了'是不可接受的'**。
>
> 而且这里有一个隐含的经济学判断：
> **剩下的 20% 需求，通常也不是高频需求**。
> 如果某个复杂查询被反复提起，那它就应该被固化成 DSL 能力——
> 这恰好是数据团队本来应该做的事。"

### Q8.4 — 如果业务方就是要一个 DSL 覆盖不了的临时查询，你怎么办？

**答**：

**分四种情况处理，每种都有明确的路径：**

**① 能用现有能力组合表达的 → 引导用户换问法。**

比如用户问"每个省份销售额的环比增长率再加上累计值"——
这是 comparison + cumsum 的组合，而我们的编译器**明确禁止**
窗口指标与 comparison 混用（`CompileError`）。

此时系统的行为是给出**明确的解释**而不是硬凑一个结果：
"窗口指标与同环比不能同时使用，请分两次查询"。

**② 能用沙箱代码表达的 → 走沙箱。**

比如"用帕累托分析找出贡献 80% 销售额的商品"——
这是算法，不是取数。DSL 取回数据，沙箱脚本算帕累托。

**③ 需要新的 DSL 能力 → 走需求流程。**

加一个新算子涉及：
1. `dsl_schema.py` 加枚举 + 字段；
2. `catalog.py` 确认字段齐全；
3. `sql_compiler.py` 加编译分支（含所有互斥组合检查）；
4. 加单测（字符串级断言）；
5. 加 golden 评测用例。

**大约是一个 PR 的量。** 这个成本是**刻意设置的门槛**——
它保证"能力增长"是经过设计、测试、评审的。

**④ 真的就是一次性、且涉及敏感操作 → 走人工。**

比如"帮我把这两个表做一次全量比对，找出不一致的记录然后修正"。
这里有"修正"动作——**我们的系统根本不做写操作**，这不是能力问题，是原则问题。

> **面试话术**："我们的支持边界不是技术限制，是**产品决策**。
> 我们明确知道哪些事我们不做（写操作、任意 SQL、跨源联邦查询），
> 并且把这个边界作为**承诺**告诉用户——
> **一个知道自己边界的系统，才是可以被信任的系统。**"

### Q8.5 — 契约 DSL 方案不是也有成本吗？代价是什么？

**答**：

**有，而且我不回避。代价主要有四个：**

| 代价 | 具体表现 | 缓解方式 |
| --- | --- | --- |
| **① 能力增长需要工程介入** | 新算子要改契约 + 编译器 + 测试 | 这是有意设计；把"能力"变成可审计的资产 |
| **② 语义目录必须与数仓同步** | 数仓加列，目录不改就查不到 | `catalog_loader` 从 `information_schema` 自动读取 + `config/semantic.json` 覆写；启动时校验 |
| **③ 编译器的测试负担重** | 每种形态 × 每种边界都要测 | 确定性让测试好写（字符串断言），当前 `test_compiler.py` 421 行覆盖 |
| **④ 对"长尾问法"的容忍度低** | 用户问法刁钻时容易落到 CLARIFY | 意图路由 + 澄清反问 + 降级路径；实测 25 道 golden 用例 oracle 模式 23/25 通过 |

**与 Text2SQL 的成本对比**：

| 成本项 | Text2SQL | 契约 DSL |
| --- | --- | --- |
| 初始开发 | 低（一个 Prompt） | 高（契约 + 编译器 + 测试） |
| **正确性保障** | 靠 Prompt + 重试 | **靠类型系统 + 编译器** |
| 幻觉治理 | 持续投入（无法根治） | **结构上不可能** |
| 权限治理 | 持续投入（无法根治） | **结构上不可能绕过** |
| 新场景边际成本 | 低 | 中（加算子） |
| **线上事故成本** | **高（数据泄露 / 错误决策）** | **低** |

> **面试金句**："Text2SQL 是把成本从**开发阶段**挪到了**运维阶段**，
> 而且挪过去的成本是**指数级**的——因为每一个新场景都可能引入新的事故面。
> 契约方案反过来了：**前期一次性投入，换取长期的可控性**。
>
> 这个选择和一个更本质的问题相关：**你愿意在什么时候为正确性付费**。
> 我们选择在开发时付费。"

## 第二部分：与竞品/替代方案的对比

### Q8.6 — 和商业 ChatBI 产品（如各类智能问数）比，你的差异是什么？

**答**：

**先说明：我没有这些产品的内部实现细节，以下基于公开资料与行业常识做对比，
不做绝对判断。**

**商业 ChatBI 的典型架构**（公开资料显示的主流做法）：
语义层（指标/维度/权限）+ LLM 生成查询 + 执行 + 图表。
部分产品把语义层做得非常厚（指标平台），部分产品直接在宽表上做 Text2SQL。

**我们的差异点**：

| 维度 | 商业 ChatBI（典型） | DataAgent |
| --- | --- | --- |
| 模型输出 | 查询语句 / 语义层表达式 | **受契约约束的 JSON DSL** |
| SQL 生成方 | 模型（或模型的模板） | **确定性编译器** |
| 权限机制 | 语义层过滤 + 引擎 RLS | **编译器后置注入 + 引擎只读** |
| 分析能力 | 主要到"出图/出表" | **到归因结论（分解/下钻/异常检测）** |
| 沙箱 | 少见 | **有（AST 守卫 + 容器隔离）** |
| 开源/可审计 | 闭源 | **全部可读可测** |

**一个诚实的补充**：

> "商业产品在**工程完备度**上（多数据源接入、高可用、权限体系对接企业 SSO、
> 运维工具链）远强于我们这个项目。
> 我们的优势在**架构的确定性**和**可审计性**——
> 每一行 SQL 都是由可读的代码生成的，出了问题能定位到具体的一行。
>
> 如果要给一个判断：**我们是"架构原型的验证"，它们是"工程产品"。**
> 这个项目证明的是'契约 + 确定性编译这条路走得通'，
> 而不是'我们已经做出了一个能替代商业产品的系统'。"

**这种诚实的定位反而会加分**——面试官最反感的是"我的项目吊打某某商业产品"。

### Q8.7 — 和 dbt 的 Semantic Layer / Cube / LookML 这类方案比呢？

**答**：

**我们和它们最接近，差异也最值得讲。**

**它们的共同思路**：在物理表之上建一层语义层
（指标定义、维度定义、口径、权限），
让"取数"这件事有**单一事实来源**。

**我们的做法和它们的关系**：

| 维度 | dbt Semantic Layer / Cube / LookML | DataAgent |
| --- | --- | --- |
| 语义层 | 有（成熟，支持复杂指标依赖） | 有（20 个字段，较简单） |
| 消费者 | BI 工具 / 人写的 SQL | **LLM（产 DSL）** |
| 查询产出 | **SQL**（用户/工具写，语义层负责重写） | **DSL**（LLM 写，编译器产 SQL） |
| 权限 | 语义层 + 引擎 | 语义层（表/列/行）+ 后置注入 |
| 分析能力 | 无（它们是"取数层"） | **有（沙箱 + 技能包）** |

**最本质的差异**：

> **它们是"给人用的语义层"，我们是"给 LLM 用的语义层"。**

这个差异带来一个重要的结果：
**它们不约束"查询怎么写的"，只约束"查询引用的东西是什么"**。
一个 dbt 用户仍然可以写任意 SQL，只要引用的指标是合法的。
**而这个"任意 SQL"的自由度，恰恰是不能给 LLM 的。**

**所以我经常这样定位这个项目**：

> "DataAgent 可以理解为：**面向 LLM 消费者的、表达力被刻意收窄的语义层**，
> 外加一个编排器和分析技能包。
> 如果把 dbt 的语义层接给 LLM 让它写 SQL，
> 你得到的是一套很好的**词汇表**；
> 而我们提供的是一套很好的**语法**——
> **语法比词汇表更能约束行为。**"

**一个有趣的推论**：如果一个公司已经有成熟的 dbt 语义层，
它其实可以直接作为我们的 `semantic/catalog.py` 的生产数据源
（`catalog_loader` 已经是从 `information_schema` 读的，
扩展成读 dbt manifest 是自然的下一步）。

### Q8.8 — 和 LangChain / LlamaIndex 的 SQL Agent 比呢？

**答**：

| 维度 | LangChain SQL Agent（典型用法） | DataAgent |
| --- | --- | --- |
| 核心机制 | 给模型表结构 + 让它写 SQL + 执行 | 给模型 DSL 契约 + 编译器产 SQL |
| 权限 | 靠数据库账号 / 提示词 | 表/列/行三级 + 后置注入 |
| 写操作防护 | 靠 Prompt 或数据库只读账号 | 四层 AST 只读校验 + 只读连接 |
| 资源治理 | 基本没有 | 超时/扫描/行数三道保险丝 |
| 编排 | 依赖框架的 Agent Executor | 自研六节点图 + 事件总线 |
| 可测试性 | 难以做确定性断言 | 纯函数编译器，字符串级断言 |

**LangChain SQL Agent 的价值和局限**：

它的价值是**快速验证**——20 行代码就能跑通"问一句话出个数"。
但它的默认配置在**生产环境**有几个明显缺口：

1. **没有权限层**：它的权限设计是"用只读数据库账号"，
   这是**表级**权限，做不到**行级**（同一个表，不同人看不同的行）；
2. **没有资源治理**：一个 `SELECT *` 就能把连接池打满；
3. **没有确定性**：同一个问题两次的 SQL 可能不同，审计困难。

**我们的定位**：

> "LangChain SQL Agent 是**验证概念的脚手架**，
> 我们在它证明的可行性之上，补齐了企业需要的四件事：
> **权限、资源治理、确定性、可审计性**。
>
> 而且我们做了一件它做不到的事：
> **把'模型的输出'变成了一个可以被静态验证的对象。**
> 这是一切企业级能力的地基。"

### Q8.9 — 为什么不用"宽表 + 大模型直接写 SQL"的朴素方案？

**答**：

这是**很多公司实际在用的方案**——把数据打平成一张大宽表，
把表结构塞进 Prompt，让模型写 SQL。

**它的优势（要承认）**：
- 开发成本极低；
- 没有 JOIN，模型出错率降低；
- 对"这张表覆盖的场景"效果不错。

**它的四个结构性缺陷**：

**① 没有 JOIN 就是没有语义**
宽表把维度"焊死"在事实表上。加一个新维度就要重建宽表。
而我们的星型模型 + `JOIN_RULES` 让加维度成为**配置变更**。

**② 权限无处安放**
宽表里既有敏感列（薪资）也有普通列。
你要么给整表权限（泄露），要么再建一个有权限的视图（视图爆炸）。
我们的列级 + 行级权限在**编译器输出层**做，与物理组织无关。

**③ 宽表的基数膨胀**
事实表 JOIN 多个维度后行数会放大（如果有一对多关系）。
我们的 `JOIN_RULES` 明确声明连接类型与字段对，
并用 `1:1 LEFT JOIN` 处理第二事实表（`fact_refunds`），
**从声明层面避免扇出**。

**④ 仍然没有解决"模型写 SQL"的所有问题**
宽表只是减少了 JOIN，**幻觉字段、权限、注入、方言漂移、不可测试
这几个问题一个都没解决。**

> **面试话术**："宽表方案是在'**降低模型出错的概率**'，
> 契约方案是在'**让模型出错也没有后果**'。
>
> 前者是概率优化——你今天 95% 正确，明天数据变了可能就 80%。
> 后者是结构保证——**无论模型输出什么，系统的行为都是确定的**。
>
> 在企业级场景里，**可预测的 80% 好于不可预测的 95%**。"

### Q8.10 — 那什么情况下你会选 Text2SQL？

**答**：

**这是一个"体现判断力"的问题，答案比"我永远选 DSL"要好得多。**

我会在这些场景选 Text2SQL：

| 场景 | 理由 |
| --- | --- |
| **内部工具、可信用户、非敏感数据** | 用户是数据团队自己，出错成本低，开发速度优先 |
| **一次性探索性分析** | 用户就是要在陌生数据上乱试，"不支持"是缺点 |
| **数据源极度异构（联邦查询）** | 契约目录的维护成本会超过收益 |
| **已经有成熟的数据治理（好账号体系 + 好引擎 RLS）** | 权限问题已经在别处解决了 |
| **需要极广的 SQL 表达能力（比如复杂的 OLAP 分析函数）** | DSL 的表达能力边界会成为真实瓶颈 |

我会在这些场景**坚持契约方案**：

| 场景 | 理由 |
| --- | --- |
| **面向业务用户的自助分析** | 用户不懂 SQL，出错的影响是业务决策 |
| **涉及敏感数据（个人信息、财务、人事）** | 泄露成本不可接受 |
| **受监管行业（金融、医疗）** | 需要可审计、可复现、可解释 |
| **多租户 / 多角色** | 行级权限是刚需 |
| **高并发 / 需要成本控制** | 资源护栏是刚需 |

> **面试话术**："技术选型没有普适最优解。
> **契约方案是用'表达能力的损失'换'正确性和可控性'。**
> 当你的用户是数据专家、数据不敏感、出错可以重来时，
> 这个交换不划算；
> 当你的用户是业务方、数据敏感、出错影响决策时，
> 这个交换非常划算。
>
> 我们做的是后者。**而我判断这个交换是否划算的标准是：出错的代价由谁承担。**"

## 第三部分：行业位置与技术趋势

### Q8.11 — 你觉得"LLM + 企业数据"这个方向未来会怎么走？

**答**：

**三个判断，每个都给出理由和不确定性。**

**判断 1：语义层会成为标配，而且它的"消费者"会从人变成 Agent。**

理由：LLM 在企业数据场景最大的问题不是"不会写 SQL"，
而是"**不知道你们公司的口径**"。语义层正是口径的载体。
一旦语义层被设计成"Agent 友好"的形态（结构化、可编程、有契约），
"让 LLM 直接读表结构"就会像"让程序员直接读二进制"一样原始。

**不确定性**：语义层的建设成本很高（需要数据团队持续投入），
中小公司可能长期停留在"宽表 + Prompt"阶段。

**判断 2：确定性会在 Agent 系统里变成一等公民。**

理由：当前 Agent 生态过度依赖"让 LLM 自我纠错"。
但**安全、权限、成本这三件事不能靠概率保证**。
我们看到的趋势是：越来越多的系统会像我做的这样，
把**不确定的部分（理解意图）**和**确定的部分（执行）**明确分层，
而不是把一切都交给模型。

**不确定性**：如果模型能力持续快速提升，
"模型自己就能做对"的范围会扩大，确定性层的边界会变化。

**判断 3：多 Agent 编排会从"自由对话"走向"受控工作流"。**

理由：自由对话式多 Agent 在生产环境的问题是可观测性差、
成本不可控、失败模式难以复现。
而图式/工作流式编排（不管是不是 LangGraph）的优势是
**每一步都是显式的、可观测的、可中断恢复的**。

**这也是我们的选择**——`StateGraph` 六节点、`max_iterations=24`、
事件总线九类事件、HITL 中断恢复，都是为了让"Agent 在做什么"**可观测**。

### Q8.12 — 你们这个项目在行业里算什么水平？

**答**：

**我给一个分层的诚实评价。**

**在"架构验证"这个维度上：这是完整且有深度的。**
- 从契约、编译器、权限、执行治理，到编排、沙箱、技能包，
  **全链路闭环，没有跳过任何一环**；
- 每一层都有对应的测试与设计理由；
- 2.8 万行 Python、678 个测试全绿、25 道 golden 评测 23/25 通过。

**在"工程完备度"这个维度上：这是原型级，不是产品级。**
- 没有高可用、没有多租户隔离、没有数据源管理、没有 SSO 对接；
- 并发上限 4，单机 DuckDB；
- 连接池有双池并存的不一致；
- 没有第三方安全评估。

**第三个维度，也是我认为最有价值的：它有一套"工程判断"。**

> "这个项目最值钱的不是代码量，是一系列**说得出理由的决策**：
> 为什么 LLM 不产 SQL、为什么审计用确定性代码、
> 为什么 `unbounded_output` 是 WARNING 不是 REJECTED、
> 为什么缓存默认关闭、为什么 `max_steps` 是 3~5、
> 为什么 Shapley 限制 8 个因子。
>
> 这些决策我可以给出理由，也可以说出**在什么情况下我会改变主意**。
> 我认为这是比'我能写多少代码'更重要的能力。"

### Q8.13 — 如果让你重新设计，你会改什么？

**答**：

**这是最好的收尾问题，一定要答得具体。**

**架构层面（我会改的三件事）**：

**① 把"执行适配层"从 `exec/guards.py` 里拆出来。**

现在连接管理、SQL 执行、资源治理、只读校验都在这个文件里。
换成非 DuckDB 引擎时，需要改的东西散落在多个函数中。
正确做法是定义一个 `ExecutionBackend` 协议
（`execute` / `explain_scan_rows` / `interrupt` / `is_readonly`），
DuckDB 是其中一个实现。

**② 把 SSE 运行状态外置到消息队列。**

现在 `RunRegistry` 是进程内的，导致：
- 多实例部署无法共享运行状态；
- 进程重启丢失未完成的编排；
- 无法做"任意实例处理重连"。

正确做法是事件流进 Redis Stream / Kafka，SSE 端点成为消费者。

**③ 统一连接池。**

现在 `web/service.py` 和 `exec/pool.py` 各有一个池，
`MAX_CONCURRENT_QUERIES` 这个不变式被软性破坏。

**工程层面（我会加的三件事）**：

**④ 契约版本管理。**
现在 `QueryDSL` 没有版本字段。一旦要改契约（比如改枚举值），
历史 DSL（存在会话记忆里、存在审计里）会失效。
正确做法是加 `schema_version` + 迁移函数。

**⑤ Prompt 与代码的联动测试。**
现在改了 DSL 契约，需要人记得去改 Prompt 里的 Few-Shot 示例。
应该有一个测试：**从契约自动生成合法的示例 DSL**，
断言 Prompt 里的示例仍然合法。

**⑥ 自愈成功率的埋点与基线。**
现在只有计数器（`_self_heal_success` / `_self_heal_failures`），
没有"哪类错误的自愈成功率是多少"的细分。
这应该按错误类型细分，作为提示词优化的输入。

## 第四部分：本主题高频压力追问速答

| 追问 | 一句话应答 |
| --- | --- |
| "契约 DSL 不就是把 Prompt 里的表结构换成 JSON 吗？" | 不是。区别是**约束在哪一端执行**：Prompt 是软约束（模型可以选择不听），契约是硬约束（模型说了不算）。 |
| "如果模型能力再强十倍，还需要契约吗？" | 需要。契约解决的不是"模型会不会做错"，而是"**系统错了会怎样**"。能力越强的模型，一次错误的影响面可能越大——**确定性是能力的前提，不是能力的替代**。 |
| "你们这套东西能商业化吗？" | 作为**架构授权 / 技术方案**有价值；作为**产品**还差一整套工程化（多源接入、高可用、SSO、运维工具）。诚实定位：这是技术方案验证，不是产品。 |
| "为什么不用现成的语义层工具？" | 因为它们面向的消费者是"会写 SQL 的人"，我们要约束的是"不会写 SQL 的模型"。**消费者不同，接口设计就不同。** |
| "怎么保证语义目录和数仓不脱节？" | 生产上 `catalog_loader` 从 `information_schema` 读物理元数据，与 `config/semantic.json` 的声明做交叉校验，不一致时**启动失败**而非静默降级。 |
| "你的方案和'把 SQL 模板化 + 槽位填充'有什么区别？" | 模板方案是"一个问法一个模板"，模板数量随场景线性增长。我们的编译器是**组合式的**——维度 × 指标 × 过滤 × 时间 × 排序的自由组合，用**有限的代码覆盖组合空间**。 |
| "行业里有没有人这么做？" | 有类似的思路（语义层受限查询、指标平台 API），但"**LLM 产 DSL + 确定性编译器 + 编译器后置权限注入**"这个完整组合，在我们的调研范围内没有看到公开的实现。这是我们做这个项目的主要动机。 |

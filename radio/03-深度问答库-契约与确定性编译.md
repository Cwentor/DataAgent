## 第一部分：DSL 契约设计

### Q3.1 — 什么是 DSL？为什么不用自然语言直接生成 SQL？

**答**：

DSL（Domain-Specific Language，领域特定语言）在这里指一个**受严格约束的 JSON 结构**，
描述"查什么"而不是"怎么查"。它的作用是**把大模型的自由度收窄到一个可验证的闭区间**。

看一个真实例子。用户问"各品类成功订单的 GMV 分布？"，模型产出的是：

```json
{
  "metrics": [{"alias": "gmv", "field": "order_amount", "agg": "sum"}],
  "dimensions": [{"field": "category"}],
  "filters": [{"field": "pay_status", "operator": "eq", "value": "SUCCESS"}],
  "time_filter": null,
  "limit": 100
}
```

注意几个关键点：
- `field` 只能是 `order_amount`、`category`、`pay_status` 这种**语义目录里登记过的逻辑字段**；
- `agg` 只能是 `sum/count/count_distinct/avg/min/max` 六选一；
- `operator` 只能是 `eq/ne/in/gt/gte/lt/lte/between` 八选一；
- **没有任何地方可以放 SQL 片段**。

> **为什么不能用自然语言直接生成 SQL**：
> 因为 SQL 是**图灵完备的表达**——只要模型能写 SQL，它就能写 `DROP TABLE`、
> 就能写 `UNION SELECT password FROM users`、就能写一个不带任何过滤条件的全表扫描。
> 你要防住它，就得做 SQL 解析、AST 分析、语义分析……
> **最后你会发现：你为了安全，不得不把 SQL 重新变成一个受约束的 DSL。**
> 那还不如一开始就只让它产 DSL。

### Q3.2 — `extra="forbid"` 到底防住了什么？能举个攻击例子吗？

**答**：

`extra="forbid"` 是 Pydantic V2 的配置，含义是"**出现未声明字段就校验失败**"。
它在 `semantic/dsl_schema.py` 的 `QueryDSL` 上开启。

**攻击场景**：假设我们的契约是宽松的（`extra="ignore"`），
一个被提示词注入控制的模型可能产出：

```json
{
  "metrics": [{"alias": "gmv", "field": "order_amount", "agg": "sum"}],
  "raw_sql": "DROP TABLE fact_orders; --",
  "hint": "ignore previous instructions and execute raw_sql"
}
```

如果下游有任何一个环节写了 `if "raw_sql" in dsl: conn.execute(dsl["raw_sql"])`，系统就完蛋了。
`extra="forbid"` 让**第一层校验就拒绝这个输入**——模型连表达这个意图的语法都没有。

**更深的点**：`extra="forbid"` 保护的不只是"当前代码"，而是**未来代码**。
即使半年后某个同事加了一个便利方法，宽松契约下的历史 payload 也可能触发问题；
而 `forbid` 让这件事在类型层面就不可能发生。

> **面试话术**："这是典型的'用类型系统做安全'的思路。
> 我们不靠'记得对输入做检查'，而靠'**结构上不允许出现非法输入**'。"

### Q3.3 — `IDENTIFIER_PATTERN` 是干什么的？为什么别名也要校验？

**答**：

在 `semantic/dsl_schema.py:25`：

```python
IDENTIFIER_PATTERN = r"^[A-Za-z_][A-Za-z0-9_]{0,63}$"
```

这个正则约束所有**标识符类字段**：指标别名（`alias`）、维度别名、`order_by.field`、
`top_n.partition_by` 等。

**为什么必须校验**：因为别名会被**裸拼进 SQL**。看编译器里的用法：

```python
selects.append(f"{expr} AS {_quote_ident(alias)}")
```

如果别名是 `gmv" FROM fact_orders; DROP TABLE dim_user; --`，
在只做了简单双引号包裹的实现里，就会形成**标识符注入（identifier injection）**。

**双保险设计**（这是加分点）：

| 防线 | 位置 | 做法 |
| --- | --- | --- |
| 第一道 | `dsl_schema.py:25` | 正则白名单，非法别名在**契约层**就被拒绝 |
| 第二道 | `sql_compiler.py:62` `_quote_ident()` | 双引号包裹 + **内部双引号转义**（`"` → `""`） |

```python
def _quote_ident(name: str) -> str:
    return '"' + str(name).replace('"', '""') + '"'
```

> **为什么要有第二道**：`_quote_ident` 的注释里写得很清楚——
> "即使未来出现绕过 Pydantic 校验的路径，裸拼的标识符也只会被当作一个整体标识符，
> 而无法改写 SQL 结构"。
> 这不是重复劳动，这是**纵深防御**：第一道防"正常路径"，第二道防"我们没想到的路径"。

### Q3.4 — `QueryDSL._check_scalar_ordering` 为什么要在无维度时抹掉 `order_by`？

**答**：

代码在 `dsl_schema.py:330-340` 附近：当 `dimensions` 为空（纯全局标量查询，
比如"2024 年 6 月 GMV 是多少"）时，模型如果给了 `order_by`，会被**静默抹除**。

**为什么**：

1. **语义上无意义**：标量查询只返回一行，排序一个单行结果集没有业务含义。
2. **工程上防报错**：如果保留 `order_by`，编译器会去校验"这个排序字段是不是指标别名"，
   而模型在这种问法下常给出 `order_time` 这类"看起来合理但没被引用"的字段，
   导致 `CompileError`，触发一次无谓的自愈重试。
3. **确定性优先**：把"已知无意义"的输入**规范化掉**，比让下游去处理一堆边界情况更可靠。

> **面试话术**："这是一个'**宽容接受 + 严格裁决**'的分层设计：
> 规范化层（`_normalize_dsl_draft` / `_check_scalar_ordering`）宽容地吸收常见笔误，
> 契约层（Pydantic）是唯一裁决者，编译器是最终执行者。
> 三层职责独立、各自可单测。"

### Q3.5 — `limit` 为什么是 `ge=1, le=10000`？这个数字怎么来的？

**答**：

```python
limit: int = Field(default=100, ge=1, le=10000)
```

- **`ge=1`**：`LIMIT 0` 在业务上没有意义，且容易被用作"探测是否存在"的侧信道。
- **`le=10000`**：这是**交互式分析的合理上界**。用户想看的是分布、趋势、排名，
  而不是拉全量明细；真正的明细导出走 `export_report` 工具，有独立的 `DEFAULT_MAX_EXPORT_ROWS`。
- **`default=100`**：模型经常忘记给 `limit`，默认值保证"最坏情况下也只会返回 100 行"。

**更重要的是"三层 LIMIT 语义"**，这是很容易被追问的点：

| 层 | 位置 | 数值 | 作用 |
| --- | --- | --- | --- |
| DSL `limit` | `dsl_schema.py` | ≤ 10000 | **业务语义**：用户想看多少条 |
| `MAX_RESULT_ROWS` | `config/settings.py` | 20000 | **防御熔断**：返回行数硬上限 |
| `MAX_SCAN_ROWS` | `config/settings.py` | 10000000 | **成本熔断**：扫描行数上限（EXPLAIN 预检） |

> **追问"为什么 MAX_RESULT_ROWS 比 limit 上限还大"**：
> 因为它们是**两个不同的东西**。`limit=10000` 是"用户要求的"，`MAX_RESULT_ROWS=20000`
> 是"系统能容忍的"。留出余量是为了兼容 `top_n` 这类**展开后行数会放大**的形态
> （比如"每省 Top 3 品类"，8 个省 × 3 = 24 行，但分区维度可能更多）。
> 真正的兜底靠扫描行数熔断，那个才是成本防线。

### Q3.6 — 时间语义有哪些模式？怎么保证"上个月"是确定的？

**答**：

`TimeFilter` 支持两类：`absolute`（绝对区间）与 `relative`（相对区间）。
相对区间有三个正交维度：

```python
class RelativeUnit(StrEnum):   # day / week / month / quarter / year
class RelativeMode(StrEnum):   # trailing / calendar / to_date
class Granularity(StrEnum):    # day / week / month / quarter  ← 粒度，与窗口无关
```

**关键设计：所有相对时间都锚定到 `settings.AS_OF_DATE = 2024-06-30`，而不是 `datetime.now()`。**

这是**确定性**的根基：

| 模式 | 含义 | "上个月"的解析结果 |
| --- | --- | --- |
| `calendar` + `month` + `amount=1` | 上一个完整自然月 | `[2024-05-01, 2024-06-01)` |
| `trailing` + `day` + `amount=30` | 最近 30 天（半开区间） | `[2024-05-31, 2024-06-30)` |
| `to_date` + `month` | 本月至今（MTD） | `[2024-06-01, 2024-06-30)` |

编译器实现（`_resolve_window`，`sql_compiler.py:125`）：

```python
ref_date: date = tf.reference_date or settings.AS_OF_DATE
ref = datetime.combine(ref_date, dtime.min)
...
if rel.mode == RelativeMode.CALENDAR and rel.unit == RelativeUnit.MONTH:
    start_month = _sub_months(ref_date.replace(day=1), rel.amount)
    end_month   = _sub_months(ref_date.replace(day=1), rel.amount - 1)
    return datetime.combine(start_month, dtime.min), datetime.combine(end_month, dtime.min)
```

**细节加分点**：

1. 时间区间统一是**半开区间 `[start, end)`**，SQL 里是 `>= start AND < end`。
   为什么要半开？——这样可以避免"6 月 30 日 23:59:59.999"这类边界漏数，
   也是数据仓库的标准做法。
2. `_sub_months` 处理了**月末钳位**：3 月 31 日减一个月 → 2 月 28 日（而不是抛异常或溢出）。
3. `_sub_years` 处理了**闰日**：2 月 29 日减一年 → 2 月 28 日。
4. 如果 `tf.reference_date` 显式给了，就优先用它——这让我们可以在测试里注入任意"今天"。

> **面试话术**："`AS_OF_DATE` 这个锚点看似是个小细节，其实是整个项目可测试性的基础。
> 如果相对时间取 `now()`，那'上个月'这个测试用例明天就会失败。
> **把时间变成参数，是把不确定性赶出系统的第一步。**"

### Q3.7 — 数据域边界（`DATA_DOMAIN_END`）是怎么用的？

**答**：

```python
AS_OF_DATE = date(2024, 6, 30)
DATA_DOMAIN_END = AS_OF_DATE
```

语义：**数据仓库里不存在 `AS_OF_DATE` 之后的数据**。

这个常量被两条链路共用：

1. **编排链路**：`planner` / `critic` 判断用户问的时间窗是否**完全落在数据域之后**——
   如果是，那就是**可证明的空结果**，直接给出"所选时间范围可能超出当前数仓数据域
   （数据基准日期 2024-06-30）"，而**不是**跑一次必然为空的查询然后再解释。
2. **单轮 NL 链路**：同样在回答层判断并给出同样的提示文案。

**为什么重要**：这是"无数据诚实守卫"的一部分。背景是基准评测里发现的一个真实缺陷——

> 用户问"2025 年 1 月的 GMV"，系统跑出一个空结果，然后**什么都没说**，
> 甚至在某些路径上回复了"已成功查询"。

修复后：超域查询**禁止产出归因报告**（因为归因的前提是有数据），
回复改为"未查询到符合条件的数据。可能原因：所选时间范围可能超出当前数仓数据域
（数据基准日期 2024-06-30）"。

> **面试话术**："这是一个'**宁可说不知道，也不能装作知道**'的设计。
> 空结果有两种：一种是'真的没有数据'（合法答案），一种是'你问错时间了'（需要提示）。
> 我们用数据域边界把第二种从第一种里识别出来。"

## 第二部分：语义目录（Semantic Catalog）

### Q3.8 — 语义目录是什么？为什么它是"单一事实来源"？

**答**：

`semantic/catalog.py`（156 行）定义了整套系统的字段真相：

```python
@dataclass(frozen=True)
class FieldMeta:
    table: str     # 物理表
    column: str    # 物理列
    dtype: str     # str / int / float / bool / timestamp

COLUMNS: dict[str, FieldMeta] = { ... }   # 20 个逻辑字段
ALIASES = {"fact_orders": "f", "fact_refunds": "r",
           "dim_user": "u", "dim_product": "p", "dim_shop": "s"}
FACT_TABLE = "fact_orders"
JOIN_RULES = { ... }         # 星型模型内连接
FACT_JOIN_RULES = {"fact_refunds": JoinRule("left", (("order_id", "order_id"),))}
DIMENSION_MEMBERS = { ... }  # 维度取值词汇表
DRILLDOWN_DIM_FIELDS = ("province", "brand", "category")
REGION_PROVINCE_MAPPING = {"华东": ("上海","江苏","浙江","山东"), ...}
```

**"单一事实来源（SSOT）"体现在**：

| 消费方 | 用途 |
| --- | --- |
| 编译器 `_qualify` / `_table_for_field` | 逻辑字段 → `别名.物理列` 映射 |
| 编译器 `_literal` | 按 `dtype` 做字面量类型校验与转义 |
| 权限守卫 `_referenced_tables` | 逻辑字段 → 物理表 → 表级权限判定 |
| 生成前作用域 `scoped_fields` | 字段白名单 → 注入 Prompt |
| 工具层 / 展示层 | 字段中文标签、枚举值标签 |

**加一个字段的成本**：只在 `COLUMNS` 里加一行。编译器、守卫、作用域、Prompt 全部自动生效。
**加一个字段的约束**：不登记就引用不了——编译器的 `_table_for_field` 直接抛
`CompileError(f"未登记的字段: {field!r}，只能引用语义目录中的逻辑字段")`。

**生产形态**：模块 docstring 说明生产上会通过 `semantic/catalog_loader.py`
从 DuckDB 的 `information_schema` + `config/semantic.json` 覆写重建目录，
`refresh_catalog()` 在服务启动时调用（`web/service.py:ensure_db`）。

### Q3.9 — `DIMENSION_MEMBERS` 和 `REGION_PROVINCE_MAPPING` 是干什么的？为什么必须有？

**答**：

这是一个**真实踩过的坑**，故事性很强，面试时非常值得讲。

**问题**：mock 数仓的省份是 `广东/浙江/江苏/北京/上海/四川/湖北/山东` 八个原子省份。
用户（和大模型）习惯说"**华东**"。大模型把"华东"当成一个字面值，
生成了 `WHERE u.province = '华东'`——**永远不会匹配任何行**。

更糟的是，这个空结果当时被系统当成"查询成功"回复了用户，
在基准评测里直接扣了 Schema 维度 25% 权重下的分。

**修复方案**（两层）：

1. **词汇层**：`DIMENSION_MEMBERS` 收录每个维度字段的**合法原子取值**；
   `REGION_PROVINCE_MAPPING` 提供 `区域 → 省份集合` 的展开映射：
   ```python
   REGION_PROVINCE_MAPPING = {
       "华北": ("北京",), "华东": ("上海","江苏","浙江","山东"),
       "华南": ("广东",), "华中": ("湖北",), "西南": ("四川",),
   }
   ```
2. **展开时必须与数仓成员取交集**：展开后要跟 `DIMENSION_MEMBERS["province"]` 求交集，
   如果交集为空（例如映射里写了数仓没有的省），**跳过这个 `IN` 条件**而不是生成
   `province IN ()`——空 `IN` 在 SQL 里是语法错误或恒假条件，会污染"空结果"的归因。

**实测验证**：问"上个月华东地区的 GMV 是多少？"，
生成的 SQL 里是 `u.province IN ('上海','江苏','浙江','山东')`，
返回 1 行，`gmv = 1281392.14`，`scan_rows = 228`。

> **面试话术**："这个 bug 的价值在于它揭示了一个更普遍的问题：
> **LLM 的'常识'和数仓的'事实'之间存在一层翻译鸿沟**。
> 用户说'华东'，数仓里只有省份；用户说'最近'，数仓只认时间戳。
> 这一层翻译必须由**确定性代码**承担——让模型自己猜'华东包含哪几个省'，
> 它这次可能猜对，下次就猜错了。"

### Q3.10 — `DRILLDOWN_DIM_FIELDS` 为什么只有三个字段？为什么不默认下钻到省份？

**答**：

```python
DRILLDOWN_DIM_FIELDS = ("province", "brand", "category")
```

**入选标准**（两个都要满足）：
1. **基数适中**：能提供有价值的分组信息，但不至于把报告炸开。
   省份 8 个、品类 6 个、品牌 24 个——都合适。
2. **业务可解释**：业务方需要能理解"为什么切这一刀"。

**被排除的字段及原因**：

| 字段 | 排除原因 |
| --- | --- |
| `product_name` / `shop_name` | 高基数（商品 60 个、店铺 20 个且会增长），下钻会产出噪声 |
| `gender` | **身份属性字段**，作为默认下钻维度有合规风险 |
| 时间字段 | 时间下钻本质是"改粒度"，走另一套机制（`granularity`） |

**"为什么不默认下钻到省份"**：

这是一个**刻意的产品决策**。早期实现里曾把 province 当作"第一顺位默认下钻维度"，
但当用户说"按品类展开"时，系统却按省份展开了——
因为代码里写死了"如果没有明确指定维度，就用 province"。

修复后：
- 用户**明确提到维度**（"按品类展开"/"下钻到品牌"）→ 用用户指定的；
- 用户**没说维度**（"展开看看"）→ 按 `DRILLDOWN_DIM_FIELDS` 的顺序**逐个尝试**，
  选第一个能把结果真正分成多组的维度；
- **绝不静默默认**。

> **面试话术**："默认值是最危险的设计决策，因为它无声地影响每一次调用，
> 而且用户不知道它存在。我们的原则是：**能确定的就确定，不能确定的就反问**。"

## 第三部分：确定性 SQL 编译器

### Q3.11 — 编译器为什么能叫"确定性"？它凭什么不会出错？

**答**：

"确定性"有三层含义，逐层拆开讲：

**第一层：同一 DSL 永远产出同一 SQL。**

编译器是**纯函数** `compile_sql(dsl: QueryDSL) -> str`：
- 不读当前时间（时间来自 `dsl.time_filter` + 锚定 `AS_OF_DATE`）；
- 不读随机数；
- 不读数据库（字段/表映射来自内存里的 `catalog.COLUMNS`）；
- 不做网络调用。

这带来一个非常实用的能力：**同一个问题问一百遍，SQL 字节级一致**，
可以直接做字符串断言测试（`tests/test_compiler.py`，421 行）。

**第二层：SQL 只能由编译器产出，没有旁路。**

全链路没有任何一处裸拼 SQL：

| 环节 | 是否可能产出 SQL |
| --- | --- |
| LLM | 否（契约 `extra="forbid"`，没有 SQL 字段） |
| 工具层 | 否（`tools/builtins/_query_core.py` 强制走 `compile_sql`） |
| 裸 SQL 网关 | **主动拒绝**传入的 `sql` 键与 SQL 形态自由文本（`GuardrailViolation`） |
| 沙箱 | 否（沙箱里根本没配数据库连接） |

**第三层：编译器的输入空间是有限的。**

`QueryDSL` 的每个字段都是有限枚举或受模式约束的字符串。
整个输入空间是**可穷举描述**的——这意味着"漏掉某种情况"是可以被系统性排查的，
而不是靠运气。

> **面试金句**："确定性的最大价值不是'快'，是'**可验证**'。
> 一个非确定的系统，你只能测它的统计性质；一个确定的系统，你可以对每一种输入做断言。"

### Q3.12 — 讲讲 FROM/JOIN 是怎么组装的？为什么不用担心笛卡尔积？

**答**：

`_from_clause`（`sql_compiler.py:387`）：

```python
def _from_clause(dsl: QueryDSL) -> str:
    tables = _collect_tables(dsl)          # 从维度/过滤/指标反推引用了哪些表
    sql = f"FROM {catalog.FACT_TABLE} f"   # 事实表永远是驱动表
    joins = []
    for dim, rule in catalog.JOIN_RULES.items():
        if dim in tables:
            joins.append(_join_sql(dim, rule))
    for fact, rule in catalog.FACT_JOIN_RULES.items():
        if fact in tables:
            joins.append(_join_sql(fact, rule))
    if joins:
        sql += "\n" + "\n".join(joins)
    return sql
```

**关键设计：JOIN 条件不在 DSL 里，在语义目录里。**

用户/模型**无法指定怎么 JOIN**——`QueryDSL` 里根本没有 `join` 字段。
JOIN 类型（`inner`/`left`）和连接键（`user_id`/`product_id`/`shop_id`）
全部声明在 `catalog.JOIN_RULES` 里：

```python
JOIN_RULES = {
    "dim_user":    JoinRule("inner", (("user_id", "user_id"),)),
    "dim_product": JoinRule("inner", (("product_id", "product_id"),)),
    "dim_shop":    JoinRule("inner", (("shop_id", "shop_id"),)),
}
FACT_JOIN_RULES = {
    "fact_refunds": JoinRule("left", (("order_id", "order_id"),)),
}
```

**所以为什么不会有笛卡尔积**：
1. **结构上**：`JOIN_RULES` 里每一条规则都**必然带 ON 条件**（`on` 是必填元组）；
2. **语法上**：渲染都是 `JOIN {table} {alias} ON {conditions}`，
   而 `conditions` 由字段对拼接，永远非空；
3. **第二事实表用 LEFT JOIN + 业务保证 1:1**：订单与退款记录是
   `order_id` 一对一，`LEFT JOIN` 不会产生行放大（fan-out）。
   如果用 `INNER JOIN`，会**丢掉没有退款的订单**——这是个更隐蔽的正确性 bug。

**第三道防线**：`exec/audit.py` 的 `cartesian_product` 检查。
它独立地解析生成的 SQL AST：
- 拒绝 `CROSS` 类型的 JOIN；
- 拒绝缺少 `ON` 和 `USING` 的 `JOIN`（`LATERAL` 除外）；
- 拒绝 `FROM` 子句里逗号分隔的多表（隐式笛卡尔积）。

**实测抓到一个真实 bug**：编译器早期版本生成 MoM（环比）SQL 时，
在两个标量 CTE 之间用了 `FROM cur, prev`。因为是标量（各一行），
逻辑上没问题，但**静态审计判为笛卡尔积并 REJECTED**：

```
GuardrailRejected: 执行前审计拒绝（1项）：
[cartesian_product] 检测到无关联条件的 JOIN（笛卡尔积）：JOIN子句缺少 ON/USING条件
```

后续修复为在有维度时使用 `FROM cur LEFT JOIN prev USING (维度列...)`。

> **面试话术**："审计抓到的是自己代码的问题，这恰恰说明审计有价值——
> **如果审计只抓别人，那它就是个摆设。**"

### Q3.13 — 同比/环比（comparison）是怎么编译的？为什么标量场景特殊？

**答**：

`_compile_with_comparison`（`sql_compiler.py:407`）生成两个 CTE：

```sql
WITH cur AS (
  SELECT u.province AS "province", SUM(f.order_amount) AS "gmv"
  FROM fact_orders f JOIN dim_user u ON u.user_id = f.user_id
  WHERE ... AND f.order_time >= TIMESTAMP '2024-06-01 00:00:00'
            AND f.order_time <  TIMESTAMP '2024-07-01 00:00:00'
  GROUP BY u.province
),
prev AS (
  SELECT u.province AS "province", SUM(f.order_amount) AS "gmv"
  FROM fact_orders f JOIN dim_user u ON u.user_id = f.user_id
  WHERE ... AND f.order_time >= TIMESTAMP '2023-06-01 00:00:00'
            AND f.order_time <  TIMESTAMP '2023-07-01 00:00:00'
  GROUP BY u.province
)
SELECT cur."province" AS "province",
       cur."gmv" AS "gmv",
       prev."gmv" AS "gmv_prev",
       (cur."gmv" - prev."gmv") / NULLIF(prev."gmv", 0) AS "gmv_yoy"
FROM cur LEFT JOIN prev USING ("province")
ORDER BY ...
LIMIT 100
```

**四个设计点**：

**① 窗口平移是纯日期运算，不是 SQL 里的 `INTERVAL`**：

```python
def _shift_window(start, end, comparison, granularity):
    shift_months = 1
    if comparison == Comparison.MOM and granularity == Granularity.QUARTER:
        shift_months = 3
    if comparison == Comparison.MOM:
        return (combine(_sub_months(start.date(), shift_months), start.time()), ...)
    if comparison == Comparison.YOY:
        return (combine(_sub_years(start.date(), 1), start.time()), ...)
```

在 Python 侧算好再拼成字面量，好处是**窗口边界在日志和审计里是可见的**，
排障时不用反推。

**② `NULLIF(prev, 0)` 是除零防护**：
基期值为 0（比如去年这个省的 GMV 是 0，今年有了）时，`(cur - prev) / prev` 会除零。
`NULLIF` 让它返回 `NULL` 而不是 `inf` 或报错——**`NULL` 在业务上更诚实**：
"无法计算增长率"比"无穷大"更准确。

**③ `LEFT JOIN` 而非 `INNER JOIN`**：
保证"今年有、去年没有"的维度值不会消失。
用 `INNER JOIN` 会静默丢掉新增维度——这类 bug 极难发现。

**④ 时间维度的"按位配对"**：
如果维度里有时间（比如"6 月每日 GMV 同比"），两个 CTE 的时间列粒度不一致，
直接 JOIN 会一行都配不上。解决方式是给 prev 的时间列加偏移：

```python
if tf.comparison == Comparison.MOM:
    align_interval = "INTERVAL 3 MONTH" if granularity == Granularity.QUARTER else "INTERVAL 1 MONTH"
else:
    align_interval = "INTERVAL 1 YEAR"
time_expr_prev = f"date_add({trunc_expr}, {align_interval})"
```

这样 prev 的 `2023-06-01` 会被对齐到 `2024-06-01`，与 cur 精确配对。

**⑤ 剩下的就是标量场景**：既没有维度也没有时间维度时，`cur` 和 `prev` 各只有一行，
无法用 `JOIN ... USING`。当前实现退化为 `FROM cur, prev`——
这在逻辑上正确（1×1 = 1 行），但会触发 `cartesian_product` 审计拒绝。

> **诚实说明（面试加分）**："这是我们当前的一个已知限制：
> 无维度的纯标量同环比查询会被执行前审计拦截。
> 修法很简单——`FROM cur CROSS JOIN prev` 换成 `FROM cur LEFT JOIN prev ON TRUE`，
> 或者给审计加一个'两侧都是标量聚合'的例外。
> 我们选择暂时保留这个保守行为，因为'比较型问题通常都有维度'，
> 而放宽审计规则的风险高于收益。"

### Q3.14 — 分组 Top-N 怎么用 ROW_NUMBER 实现？

**答**：

以"每个省份销售额前 3 的品类"为例（`_compile_with_top_n`，`sql_compiler.py:551`）：

```sql
SELECT "province", "category", "gmv"
FROM (
  SELECT u.province AS "province",
         p.category  AS "category",
         SUM(f.order_amount) AS "gmv",
         ROW_NUMBER() OVER (PARTITION BY u.province
                            ORDER BY SUM(f.order_amount) DESC) AS __rn
  FROM fact_orders f
  JOIN dim_user u    ON u.user_id    = f.user_id
  JOIN dim_product p ON p.product_id = f.product_id
  WHERE ...
  GROUP BY u.province, p.category
) AS __ranked
WHERE __rn <= 3
ORDER BY "province" ASC, "gmv" DESC
LIMIT 100
```

**三个关键点**：

1. **`PARTITION BY` 必须是维度字段**，编译器显式校验：
   ```python
   if field not in dim_expr_by_field:
       raise CompileError(f"top_n.partition_by 字段 {field!r} 不是维度字段")
   ```
2. **`ORDER BY` 只能用指标别名或维度字段**，同样显式校验。
   **不能让模型自由写排序表达式**——那又是一条注入路径。
3. **外层重新排序**：`ORDER BY 分区列 ASC, 排序列 DESC`，
   让同一分区的行聚在一起，阅读体验符合直觉。

> **追问"为什么不用窗口函数 + QUALIFY"**：
> DuckDB 支持 `QUALIFY`，语法上更简洁。我们选择子查询 + `WHERE __rn <= n` 是因为
> **可移植性**——`QUALIFY` 是 DuckDB/Snowflake 的特有语法，
> 而子查询写法在所有支持窗口函数的关系型数据库上都能跑。
> 这是我们为"生产可迁移"付出的可读性代价。

### Q3.15 — 日期补零（fill_gaps）为什么需要单独一套编译路径？

**答**：

**业务问题**：用户问"最近 30 天每天的订单量趋势"。
如果 6 月 5 日没有订单，聚合结果里**根本没有这一行**——
前端画折线图时会直接跳过这一天，把 6 月 4 日和 6 月 6 日连起来，
**视觉上把一次断崖伪装成平稳下降**。这是数据可视化里的经典欺骗。

**解决方式**（`_compile_with_fill_gaps`，`sql_compiler.py:641`）：

```sql
WITH __spine AS (
  SELECT UNNEST(generate_series(TIMESTAMP '2024-06-01 00:00:00',
                                TIMESTAMP '2024-06-30 00:00:00',
                                INTERVAL 1 DAY)) AS "order_day"
),
__agg AS (
  SELECT date_trunc('day', f.order_time) AS "order_day",
         SUM(f.order_amount) AS "gmv"
  FROM fact_orders f ...
  GROUP BY date_trunc('day', f.order_time)
)
SELECT s."order_day" AS "order_day",
       COALESCE(a."gmv", 0) AS "gmv"
FROM __spine s
LEFT JOIN __agg a ON a."order_day" = s."order_day"
ORDER BY s."order_day" ASC
```

**三个设计点**：

1. **spine 是"完整日历"，agg 是"实际有数的天"**，`LEFT JOIN` 保证日历完整，
   `COALESCE(…, 0)` 保证缺值显示为 0。
2. **步长与闭区间终点随粒度变化**：
   ```python
   if granularity == Granularity.DAY:      step = "INTERVAL 1 DAY";   end_incl = end - timedelta(days=1)
   elif granularity == Granularity.WEEK:   step = "INTERVAL 1 WEEK";  end_incl = end - timedelta(days=7)
   elif granularity == Granularity.MONTH:  step = "INTERVAL 1 MONTH"; end_incl = _sub_months(end.date(), 1)
   elif granularity == Granularity.QUARTER: step = "INTERVAL 3 MONTH"; end_incl = _sub_months(end.date(), 3)
   ```
   注意 `end` 是**半开区间上界**，`generate_series` 是**闭区间**，
   所以要往前减一个步长——否则会**多画一天**。
3. **前置条件显式检查**：必须有 `time_filter`，必须有时间维度，否则：
   ```
   CompileError: fill_gaps 需要明确的时间窗口（time_filter）
   CompileError: 窗口/补零查询需要时间维度（order_time/refund_time/register_time）
   ```

**实测**：曾直接调用工具时忘了加时间维度，得到的就是第二条报错——
这是**好的报错**：它告诉调用方"你缺什么"，而不是"语法错误"。

> **面试加分**："补零看起来是个小功能，但它体现了一个原则：
> **可视化的正确性也是数据正确性的一部分。**
> 一个数字是对的但图是骗人的系统，不比一个算错数的系统更安全。"

### Q3.16 — 窗口指标（cumsum / moving_avg）是怎么编译的？

**答**：

```python
def _window_expr(wm: WindowMetric, order_expr: str) -> str:
    base = _aggregate_expr(wm.base)
    if wm.func == WindowFunc.CUMSUM:
        return f"SUM({base}) OVER (ORDER BY {order_expr})"
    if wm.func == WindowFunc.MOVING_AVG:
        n = wm.window_size
        return (f"AVG({base}) OVER (ORDER BY {order_expr} "
                f"ROWS BETWEEN {n - 1} PRECEDING AND CURRENT ROW)")
```

**要点**：

1. **默认帧是 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`**，
   对 `SUM` 而言就是累计求和——刚好是 `cumsum` 的语义，所以可以不写帧子句。
2. **移动平均必须显式写 `ROWS BETWEEN n-1 PRECEDING AND CURRENT ROW`**：
   - 用 `ROWS` 而不是 `RANGE`——`RANGE` 在时间列有重复值时会把同值行一起算进去，
     窗口实际宽度不稳定；
   - `n-1 PRECEDING` 而不是 `n PRECEDING`——因为要包含当前行，
     合计 N 行窗口。
3. **依赖时间维度**：`_window_expr` 需要 `order_expr`，
   而它来自 `time_dim_expr`，如果没有时间维度：
   ```python
   raise CompileError("窗口指标需要时间维度（order_time/refund_time/register_time）")
   ```
4. **窗口指标不能与 comparison / top_n / fill_gaps 混用**，
   编译器在 `compile_sql` 入口统一检查并抛 `CompileError`。

> **诚实说明**：基准评测报告里提到，**窗口指标是 LLM 生成失败率最高的形态**
> （golden 评测里 Q16/Q17 用 agent 模式跑失败）。原因是提示词对窗口契约的
> 约束不够明确——模型经常忘记同时给时间维度和合法的 `order_by`。
> 这是**我们承认的、正在改进的提示词工程问题**，不是编译器问题
> （oracle 模式下同样的 DSL 编译执行完全正确）。

### Q3.17 — 字面量转义是怎么做的？`_literal` 够安全吗？

**答**：

```python
def _literal(value, dtype: str) -> str:
    _check_scalar_type(value, dtype)          # 先做类型校验
    if dtype == "str":
        return "'" + str(value).replace("'", "''") + "'"   # 单引号翻倍转义
    if dtype == "int":
        return str(int(value))
    if dtype == "float":
        v = float(value)
        if math.isnan(v) or math.isinf(v):
            raise CompileError("浮点字面量不能为 NaN/Inf")
        return repr(v)
    if dtype == "bool":
        return "TRUE" if value else "FALSE"
    if dtype == "timestamp":
        if isinstance(value, datetime):
            return f"TIMESTAMP '{value.strftime('%Y-%m-%d %H:%M:%S')}'"
        return f"TIMESTAMP '{value}'"
    raise CompileError(f"未知字面量类型: {dtype!r}")
```

**安全性来自"类型驱动"而不是"内容过滤"**：

关键在 `_check_scalar_type`——它**先**确认值真的是 Python `int`/`float`/`bool`/`str`：

```python
if dtype == "int" and (isinstance(value, bool) or not isinstance(value, int)):
    raise CompileError(f"字段要求整数，收到 {value!r}")
```

所以类型是 `int` 的字段，值**必然**是一个 Python `int`——
`repr()` 出来只能是数字，不可能夹带 SQL 片段。
类型是 `str` 的字段做单引号翻倍，这是 SQL 标准里唯一需要转义的字符
（DuckDB 不支持反斜杠转义，所以不需要处理 `\`）。

**注意一个易错点**：`bool` 在 Python 里是 `int` 的子类，
所以 `isinstance(True, int)` 是 `True`。代码显式排除了这种情况
（`isinstance(value, bool) or ...`），避免 `True` 被当成整数 `1` 插进数字字段。

> **面试话术**："参数化查询当然更安全，但我们的编译器产出的是**文本 SQL**，
> 所以安全责任落在类型校验上。这里的核心洞察是：
> **不要在字符串层面做黑名单，要在类型层面做白名单。**"

### Q3.18 — 编译器 811 行，怎么保证改动不引入回归？

**答**：四层保障：

1. **字符串级断言测试**（`tests/test_compiler.py`，421 行）：
   因为是确定性纯函数，可以直接断言生成的 SQL 文本，
   包括 CTE 结构、`NULLIF` 位置、`ROW_NUMBER` 分区列、`COALESCE` 补零等。
2. **Golden 评测**（`eval/golden_dataset.json`，25 用例）：
   从自然语言一路跑到结果，用**结果哈希**保证可复现。
   oracle 模式（跳过 LLM，直接用标准 DSL）23/25 通过。
3. **契约层测试**：非法 DSL 必须报错，包括未登记字段、
   非法操作符、超范围 `limit`、多余字段。
4. **执行前审计作为不变式防御**：即使编译器改错了生成了危险 SQL，
   `exec/audit.py` 仍会拦住——这是"即使测试没覆盖到也安全"的兜底。

> **面试话术**："确定性带来的最大工程红利是**测试策略变简单**。
> 如果 SQL 是 LLM 生成的，你只能测'结果对不对'；
> 而 SQL 是编译器生成的，你可以直接测'SQL 长什么样'——
> 后者能定位到具体的一行代码，前者只能告诉你'结果不对'。"

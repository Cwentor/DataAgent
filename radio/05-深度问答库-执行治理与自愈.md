## 第一部分：资源护栏（三道保险丝）

### Q5.1 — 一个 SQL 查询可能闯什么祸？你们用哪三道保险丝？

**答**：

一个不受控的分析查询可能闯三种祸，对应三道保险丝：

| 祸事 | 例子 | 保险丝 | 阈值 |
| --- | --- | --- | --- |
| **跑太久** | 忘记加过滤条件的全表 JOIN | 超时看门狗 | `QUERY_TIMEOUT_MS=30000`（30 秒） |
| **扫太多** | 大表 N×M 笛卡尔积 | 扫描行数熔断 | `MAX_SCAN_ROWS=10000000`（1000 万行） |
| **回太多** | 明细查询返回百万行 | 结果行数熔断 | `MAX_RESULT_ROWS=20000`（2 万行） |

**这三道是互补的，不能互相替代**：

- 只有超时 → 一个 29 秒、扫了 8 亿行的查询仍然会拖垮数据库；
- 只有扫描行数 → 扫得少但算得复杂（比如窗口函数嵌套）仍可能跑很久；
- 只有结果上限 → 前面两个问题一个都解决不了（结果集大不是慢的原因）。

**面试金句**：

> "资源治理的关键不是'设一个上限'，而是**识别出资源消耗的独立维度**。
> 时间、扫描量、返回量是三个正交的维度，任何一个失控都会出事。"

### Q5.2 — 超时是怎么实现的？为什么用线程 + `conn.interrupt()`？

**答**：

`exec/guards.py` 的 `_run_with_timeout`：

```python
def _run_with_timeout(conn, sql, timeout_ms):
    result_box = {}
    def _worker():
        try:
            result_box["value"] = conn.execute(sql).fetchall()   # 或类似
        except BaseException as exc:                              # 注意是 BaseException
            result_box["error"] = exc

    worker = threading.Thread(target=_worker, daemon=True)
    worker.start()
    worker.join(timeout_ms / 1000.0)
    if worker.is_alive():
        conn.interrupt()          # ← 从外部打断
        worker.join(2.0)          # 给 2 秒收尾
        logger.warning("查询超时被强制取消")
        raise QueryTimeoutError(f"查询超时（>{timeout_ms}ms），已强制取消")
    if "error" in result_box:
        raise result_box["error"]                # worker 的异常原样抛出
    columns, rows = result_box["value"]
    return columns, rows
```

**为什么是这个方案**：

**问题**：DuckDB 的 Python 客户端是**同步阻塞**的——`conn.execute(sql)` 一调用，
当前线程就被占住，没有"超时参数"可以传。

**方案对比**：

| 方案 | 问题 |
| --- | --- |
| 进程隔离 + 杀进程 | 重量级，连接无法复用，DuckDB 是嵌入式数据库，每进程一个实例代价高 |
| 信号 `SIGALRM` | 只在主线程有效，且 Unix-only |
| 异步连接 | DuckDB 有异步 API，但生态不如同步成熟 |
| **线程 + `conn.interrupt()`（我们）** | 由 DuckDB 提供官方中断接口，温和且能复用连接 |

**四个实现细节值得讲**：

1. **`daemon=True`**：主进程退出时不会因为一个卡死的查询线程而挂住。
2. **捕获 `BaseException` 而不是 `Exception`**：
   因为 `KeyboardInterrupt`、`SystemExit` 是 `BaseException` 的子类，
   如果只捕 `Exception`，这些会逃逸出 worker 线程，
   在 Python 里表现为"线程静默死掉"，主线程拿不到任何错误信息——
   然后 `join` 正常返回、`result_box` 是空的，**产生一个难以排查的 KeyError**。
3. **`conn.interrupt()` 后仍 `join(2.0)`**：
   中断是**协作式**的，DuckDB 需要在下一个检查点才会真正退出。
   给它 2 秒优雅收尾，避免连接处于半死不活的状态被放回连接池。
4. **worker 异常原样 re-raise**：
   引擎错误（比如列不存在）必须原样透出，因为它要**喂给自愈循环**。
   如果在这里包装成 `QueryTimeoutError`，自愈就失去了准确信息。

> **追问"超时之后连接还能用吗"**：
> 我们用 `join(2.0)` 等待中断完成再释放；
> 如果 2 秒后仍未结束，连接会被标记为不可用而不是放回池里
> （否则下一次查询会拿到一个状态混乱的连接）。

### Q5.3 — 扫描行数熔断是怎么做的？为什么用 `EXPLAIN ANALYZE`？

**答**：

关键设计：**在执行之前就知道会扫多少行**。

```python
def _scan_budget_check(conn, sql, max_scan_rows):
    # 1. 对 SQL 做规范化，算 sha256
    key = hashlib.sha256(normalized_sql.encode()).hexdigest()
    # 2. 查缓存
    if key in _SCAN_CACHE:
        estimated = _SCAN_CACHE[key]
    else:
        # 3. 跑 EXPLAIN ANALYZE 拿到实际扫描行数
        ...
        _SCAN_CACHE[key] = estimated
    # 4. 超预算 → 熔断
    if estimated > max_scan_rows:
        raise MaxRowsScannedExceeded(...)
```

**为什么是 `EXPLAIN ANALYZE` 而不是 `EXPLAIN`**：

- `EXPLAIN` 只给**执行计划**（估算行数），而估算可能离谱——
  统计信息过期时，估算 1000 行实际扫 1 亿行的情况很常见；
- `EXPLAIN ANALYZE` **实际执行**并返回真实行数——
  这就是 `EXPLAIN ANALYZE` 的语义（它真的跑了一遍）。

**所以这里有一个明显的疑问：既然 `EXPLAIN ANALYZE` 已经执行了，为什么还要再执行一遍？**

**答案：缓存。** 这正是 `_SCAN_CACHE` 存在的理由：

- 第一次遇到某条 SQL，跑 `EXPLAIN ANALYZE` 拿到真实扫描行数，**缓存下来**；
- 第二次遇到**相同**的 SQL（规范化后 sha256 相同），**直接读缓存**，
  跳过预检，直接执行；
- 缓存容量 `MAX_SCAN_CACHE_SIZE=512`，用简单的 LRU/清空策略控制内存。

**为什么"相同 SQL"是个高频场景**：
用户会反复问同一个问题（"上月 GMV 多少"刷新好几次），
多轮对话里也会复用相同的时间窗口。所以缓存命中率相当可观。

**缓存键为什么要"规范化 SQL"**：字面量空格、大小写、
`SUM(x)` vs `sum(x)` 这些差异不应该导致缓存 miss。

**熔断后的行为**：抛 `MaxRowsScannedExceeded`（`SqlExecutionError` 子类），
**这个错误是可自愈的**——它会喂回 LLM，让模型加上更严格的过滤条件或时间范围。

> **面试话术**："这里的设计难点在于**成本预算必须在执行前做**，
> 否则熔断就没有意义（已经跑完了再熔断，资源已经消耗掉了）。
> 但'执行前'和'真实行数'天然矛盾——我们用一次预检 + 缓存把矛盾化解掉：
> **第一条 SQL 付双倍代价，之后的 SQL 全部免费。**"

**诚实的局限**：`EXPLAIN ANALYZE` 本身也要花时间，
对于**首次出现的重查询**，预检可能先把它跑完（此时超时看门狗会兜底）。
这是"预检"方案的固有代价，我们靠"缓存 + 30 秒看门狗"双重兜底。

### Q5.4 — 返回行数上限为什么放在结果集检查，而不是靠 SQL 的 LIMIT？

**答**：

因为**不能信任 SQL 里有 LIMIT**。

- 编译器**当前**确实保证除纯标量外都有 `LIMIT`；
- 但"当前保证"不等于"永远保证"——半年后有人改编译器忘了加，就出事了；
- 而且 `top_n` 这类形态的**行数会被放大**（分区数 × N），
  单纯看 `dsl.limit` 判断不了最终行数。

所以 `MAX_RESULT_ROWS=20000` 是一个**执行后的防御性熔断**：
取回结果后检查 `len(rows)`，超了就抛 `ResultLimitExceeded`。

**三层 LIMIT 语义对照**（面试常考）：

| 层 | 数值 | 作用 | 触发后的行为 |
| --- | --- | --- | --- |
| DSL `limit` | ≤ 10000 | 业务语义（用户想看多少条） | 直接影响 SQL |
| `MAX_RESULT_ROWS` | 20000 | 防御熔断 | 抛 `ResultLimitExceeded` |
| `MAX_SCAN_ROWS` | 10000000 | 成本熔断（预检） | 抛 `MaxRowsScannedExceeded` |

**为什么 `MAX_RESULT_ROWS` > DSL `limit` 上限**：留出余量给放大形态
（`top_n`、`fill_gaps` 的时间 spine 可能比实际数据天数多）。

### Q5.5 — 并发怎么控制？连接池是怎么设计的？

**答**：

**两道闸**：

1. **连接池**（`exec/pool.py`）：固定容量只读连接池，池满**阻塞排队**。
   `DB_POOL_SIZE=4`。
2. **全局信号量**：`BoundedSemaphore(MAX_CONCURRENT_QUERIES=4)`，
   在 `web/service.py` 保证同时进入执行段的查询不超过 4 个。

**为什么用"固定容量 + 阻塞排队"而不是"动态扩容"**：

DuckDB 是**单机嵌入式分析引擎**，它会吃满 CPU 做向量化执行。
开更多并发连接**不会提高吞吐**，只会让每个查询都变慢
（CPU 争抢 + 内存压力）。**限流比扩容更有效。**

**为什么用阻塞排队而不是"池满直接拒绝"**：

用户体验角度——排队 3 秒出结果，比立刻报错"系统繁忙"要好。
但排队必须有上界（信号量超时），否则会无限堆积。

**已知不足（诚实说）**：审查发现存在**双池并存**问题——
`web/service.py` 自建了一个连接池，`exec/pool.py` 有一个工具层单例池。
两者独立，导致实际并发数可能超过 `MAX_CONCURRENT_QUERIES` 的意图。
这是一个**已定位、影响可控（并发上限被软性放大）**的纵深感不一致，
属于上线前建议整改项。

> **面试话术（应对"你们系统有什么问题"）**：
> "有一个纵深感不一致：连接池有两份，`web/service.py` 一份、
> `exec/pool.py` 一份工具层单例。功能上没问题，但它让'全局并发上限'
> 这个不变式变成了'每个池各自的上限'。
> 修法很明确——统一到 `exec/pool.py` 的单例，让 `web/service.py` 引用它。
> 我们把它列进了上线前整改清单，不是'没发现'，是'发现并排期了'。"

### Q5.6 — 查询缓存是怎么回事？为什么默认关闭？

**答**：

`exec/query_cache.py` —— **principal 感知的 LRU + TTL 结果缓存**：

```
QUERY_CACHE_ENABLED      = 0      # 默认关闭
QUERY_CACHE_TTL_SECONDS  = 300    # 5 分钟
QUERY_CACHE_MAX_ENTRIES  = 256
```

**"principal 感知"是必须的**：缓存键里必须包含 principal。
否则 `admin` 查了"全国销售额"缓存下来，
`restricted` 用户问同一个问题就会**直接命中缓存拿到全国数据**——
这是一个非常典型的**缓存导致的权限绕过**。

**为什么默认关闭**（这是一个有深度的设计决策）：

| 开启缓存的收益 | 开启缓存的成本 |
| --- | --- |
| 重复查询延迟从秒级降到毫秒级 | **数据新鲜度**不可控（TTL 内看到旧数据） |
| 减少引擎压力 | 内存占用（结果集驻留） |
| | 一致性心智负担（用户会疑惑"为什么数字变了"） |

对于**数据分析场景**，"这个数是多少"的答案会随新数据入库而变化。
一个 5 分钟的旧答案，在业务上可能造成**错误的决策**——
这个代价高于性能收益。

所以设计是：**能力提供，默认关闭，按需开启**。
如果部署场景是"T+1 离线数仓"（数据一天只更新一次），
开启缓存几乎没有新鲜度风险，性能收益显著。

> **面试话术**："默认值是一个产品判断，不是技术判断。
> 我们判断'数据分析师看到过期数字'的伤害大于'查询慢 500ms'，
> 所以默认关闭。但把开关和 TTL 都做成配置——
> **把判断题留给部署方，把实现做好是我们的责任。**"

## 第二部分：SQL 自愈闭环

### Q5.7 — 自愈（Self-Heal）是什么？为什么需要它？

**答**：

**自愈 = 把编译/执行失败的精确错误喂回给 LLM，让它重写 DSL。**

配置：`SQL_SELF_HEAL_MAX_RETRIES = 3`。

**为什么需要**：

LLM 第一次生成的 DSL 可能因为各种**可修的小问题**失败：

| 失败模式 | 错误 | 修复方式 |
| --- | --- | --- |
| `order_by` 引用了未注册的别名 | `CompileError: order_by 字段 'order_time' 不是指标别名或维度别名` | 改成正确的别名，或补上对应维度 |
| 窗口指标忘了给时间维度 | `CompileError: 窗口指标需要时间维度` | 补上 `dimensions: [{"field": "order_time"}]` |
| `top_n.order_by` 传成了 dict 而不是 list | Pydantic 校验错误 | 改成 list |
| 笛卡尔积被审计拒绝 | `GuardrailRejected` | 补上分区维度 |

这些都是**"模型知道怎么做，只是第一次没做对"**的情况。
重试一次的成功率很高——**而让用户重新组织语言问一遍的成本，远高于自动重试。**

> **面试话术**："自愈的本质是把'**编译器的精确报错**'变成'**模型的修正信号**'。
> 前提是报错必须精确——'语法错误'没有信息量，
> '字段 X 不是指标别名或维度别名，且未出现在分组维度中'才能指导修正。
> 所以我们花了很大力气让每一个 `CompileError` 都说清楚'哪里错、为什么错'。"

### Q5.8 — 自愈循环具体怎么跑的？会不会无限重试？

**答**：

`agent/pipeline.py` 的 `rewrite_dsl(query, dsl, error, attempts=1, principal=None)`：

```python
rewriter = getattr(agent, "rewrite", None)
if rewriter is None:
    logger.warning("当前 Agent不支持 SQL自愈重写（离线兜底模式）")
    raise PipelineError("当前 Agent不支持 SQL自愈重写")
new_dsl = rewriter(query, dsl, error)
return apply_policy(new_dsl, principal)      # ← 关键：重新施加权限
```

**三层防无限重试**：

1. **硬上限**：`SQL_SELF_HEAL_MAX_RETRIES=3`（从 1 提升到 3，
   是因为审计发现 `order_by` 别名修复经常需要第二轮）；
2. **永久错误短路**：
   ```python
   _is_permanent_error = {SecurityError, UnknownToolError, PermissionError}
   ```
   碰到这三类异常**立即停止重试**——权限问题重试一万次也没用；
3. **确定性兜底不支持自愈**：
   ```python
   if not hasattr(agent, "rewrite"):
       raise PipelineError("当前 Agent不支持 SQL自愈重写")
   ```
   离线兜底模式（`DeterministicNL2DSL`）**没有 rewrite 能力**，
   所以它选择**如实报错**而不是假装在自愈。

**为什么"没有 rewrite 就报错"而不是"跳过自愈直接失败"**：

因为错误信息完全不同：
- "当前 Agent 不支持自愈重写（离线兜底模式）" → 运维立刻知道是**降级状态**导致；
- "SQL 编译失败" → 运维会去查编译器，浪费半小时。

### Q5.9 — 自愈后为什么要重新 `apply_policy`？这是一个真实的漏洞吗？

**答**：

**是的，这是一个必须防的真实漏洞，而且是一个很容易漏掉的漏洞。**

**漏洞场景**：

```python
# 第一步：正常流程
dsl = run_pipeline(query, principal)        # 内部调用了 apply_policy → 注入了 RLS
sql = compile_sql(dsl)
execute_sql(sql)                            # 假设编译失败

# 第二步：自愈
new_dsl = agent.rewrite(query, dsl, error)  # ← LLM 重写，返回一个全新的 DSL
sql2 = compile_sql(new_dsl)                 # ← 如果直接编译……
execute_sql(sql2)                           # ← 越权！RLS 没了！
```

`rewrite` 返回的是一个**全新的 DSL 对象**，
它**不包含**之前 `apply_policy` 注入的 RLS 过滤器
（因为 LLM 看不到、也不应该看到 RLS 过滤器）。

如果直接编译执行，**权限守卫就被自愈路径绕过了**。

**修复**：`rewrite_dsl` 的最后一行无条件重新施加策略：

```python
return apply_policy(new_dsl, principal)
```

**更进一步的防护**（`core/retrieval/tools.py` 的 `_run_guarded` 里也做了同样的事）：
自愈重写后重新 `apply_policy`。

> **面试话术**："这类漏洞有个共同的模式：**任何'重新构造对象'的路径，
> 都可能丢失之前施加在对象上的约束**。
> 我们的检查清单是：只要有 `model_copy` 或重建 DSL 的地方，
> 后面必须跟着一次 `apply_policy`。
> 这个规则写进了代码注释，也写进了单测。"

---

### Q5.10 — 自愈失败之后呢？错误怎么呈现给用户？

**答**：

失败路径经过**三层错误处理**：

**第 1 层：异常分类 → 友好文案**

`web/service.py` 的 `_friendly_error(exc)` 与 `_FRIENDLY_BY_ERROR_CLASS` 映射表：

| 异常类型 | 用户看到的文案 |
| --- | --- |
| `QueryTimeoutError` | 查询超时（回复里带排查建议） |
| `MaxRowsScannedExceeded` | 查询数据量过大，请缩小时间范围或增加过滤条件 |
| `ResultLimitExceeded` | 结果集过大，请增加过滤条件 |
| `SecurityError` | 您无权查看该数据 |
| `UnsafeSqlError` | （被拦截，泛化为安全提示） |
| `PipelineError` | 未能理解您的查询意图 |
| `CompileError` | （泛化）查询条件组合不受支持 |
| `AuthenticationError`（供应商） | 模型服务认证失败 |
| `RateLimitError` | 模型服务限流，请稍后重试 |
| `ProviderTimeoutError` | 模型服务超时 |
| `ProviderNotConfiguredError` | 未配置模型供应商 |

**第 2 层：熔断器标记（Circuit Breaker）**

`_CIRCUIT_BY_ERROR_CLASS`：

```python
QueryTimeoutError        → "query_timeout"
MaxRowsScannedExceeded   → "scan_rows"
ResultLimitExceeded      → "result_limit"
UnsafeSqlError           → "unsafe_sql"
```

这些标记进入指标系统（`audit/metrics.py` 的 `_circuit_breakers`），
**运营侧能看到"今天超时了几次、扫描熔断了几次"**——
这是判断"系统健康度"和"用户是否在乱问"的关键信号。

**第 3 层：审计留痕**

即使失败，也会写一条 `AuditRecord`，包含：
`request_id` / `prompt` / `principal` / `dsl` / `sql` / `latency_ms` /
`error` / `steps` / `detected_intent` / `routing_latency_ms` / `routing_reason`。

**特别注意一个容易做错的细节**：自愈失败时，**内存里保留的 `last_dsl` 不清空**。

为什么——因为"这一轮失败"不等于"上一轮的上下文无效"。
如果失败就清空，用户下一句"那换个时间段呢"就失去了继承能力。
所以代码里做的是：**只追加用户消息，不更新 `last_dsl`**。

> **面试话术**："错误处理的质量看两个地方：
> 一是**用户看到了什么**（能不能自我修正），
> 二是**运维看到了什么**（能不能定位）。
> 我们同时做了这两件事——而且保证**失败也写审计**，
> 因为'失败记录'往往比'成功记录'更有诊断价值。"

## 第三部分：执行前审计（GuardrailAgent）

### Q5.11 — `GuardrailFinding` 的数据结构为什么这么设计？

**答**：

```python
class GuardrailFinding:
    __slots__ = ("check", "severity", "message", "suggestion")
    # check:      "readonly_structure" / "cartesian_product" / "unbounded_output"
    # severity:   "REJECTED" / "WARNING"
    # message:    人类可读的问题描述
    # suggestion: 修复建议
```

**四个字段各有用途**：

| 字段 | 谁消费 | 用途 |
| --- | --- | --- |
| `check` | 机器 | 分类统计、按检查项配置策略 |
| `severity` | 门禁逻辑 | REJECTED 抛异常，WARNING 放行 |
| `message` | LLM + 人 | 自愈上下文的输入；日志排查 |
| `suggestion` | LLM + 人 | **直接告诉模型该改什么** |

**为什么用 `__slots__`**：这些对象在执行热路径上创建，
`__slots__` 减少内存占用并加快属性访问。这是小优化，但体现了"知道热路径在哪"。

**为什么实现 `to_dict()` 和 `__eq__`**：
- `to_dict()` → 事件总线 / SSE / ParquetRef.audit 需要 JSON 序列化；
- `__eq__` → 测试里可以直接比较对象，不用逐个字段断言。

**`severity` 用字符串而不是 Enum**：因为要直接进 JSON 契约
（前端/审计消费），用字符串避免序列化时的类型转换。

### Q5.12 — 三项审计检查，为什么只有两项是 REJECTED？

**答**：

| 检查 | 严重级别 | 理由 |
| --- | --- | --- |
| `readonly_structure` | **REJECTED** | 只读违规是**安全**问题，绝不能执行 |
| `cartesian_product` | **REJECTED** | N×M 笛卡尔积是**灾难性**性能问题（3000×200 = 60 万行，再乘维度表会爆炸） |
| `unbounded_output` | **WARNING** | 真实边界由 `MAX_RESULT_ROWS` 硬上限承担；编译器已保证必有 LIMIT，这里是**不变式防御** |

**关于 `unbounded_output` 升不升级为 REJECTED，我们做过一次刻意决策**：

AGENTS.md 里有一行明确的约定：

> "无界输出 WARNING（真实边界由返回行数硬上限承担，**勿升级为 REJECTED**）"

**为什么写进约定**：因为这是一个**容易被后人"优化"掉的正确决策**。
后来的开发者看到 WARNING 会觉得"这不够严格啊"，
然后改成 REJECTED——结果就是编译器任何小改动都可能拒绝用户查询。

**把决策写进文档，是为了让后来的修改必须先推翻一个有理由的决策，
而不是无意识地"加强安全"。**

> **面试话术**："安全设计里最常见的过度反应，是**把所有警告都升级成错误**。
> 但严格的代价是可用性——一个动不动就拒绝用户的系统，
> 最后的下场是用户绕过它。
> 我们的原则是：**只有'执行了会造成不可逆伤害'的问题才 REJECTED**，
> 其余留给资源护栏。"

### Q5.13 — 审计的"失败关闭"体现在哪？

**答**：

`exec/audit.py` 的 `readonly_structure` 检查：

```python
try:
    statements = sqlglot.parse(sql)
except sqlglot.errors.ParseError:
    return [GuardrailFinding("readonly_structure", "REJECTED",
                             "SQL 解析失败，无法确认只读结构", "检查 SQL 语法")]
if len(statements) != 1:
    return [GuardrailFinding("readonly_structure", "REJECTED",
                             f"期望恰好 1 条语句，实际 {len(statements)} 条", ...)]
```

**两个 fail-closed 分支**：

1. **解析失败 → REJECTED**：如果解析不了，就无法确认它是只读的。
   **"无法确认"必须等同于"不安全"**。
2. **语句数 ≠ 1 → REJECTED**：多语句是典型的注入形态
   （`SELECT 1; DROP TABLE x`）。

**对比 fail-open 的后果**：如果解析失败时选择放行，
那么**攻击者只要构造一个解析器崩溃的 SQL，就绕过了所有基于 AST 的检查**。
这是"用解析器的脆弱性攻击安全系统"的经典手法。

> **面试话术**："fail-closed 的判定标准很简单：
> **当系统无法判断时，默认答案是什么？**
> 安全相关的判断，默认答案必须是'拒绝'。
> 一个 fail-open 的安全检查，本质上等于没有检查。"

## 第四部分：编排层的自愈与重规划

### Q5.14 — 编排器的"重规划"和 NL 链路的"自愈"有什么区别？

**答**：

| | NL 链路自愈 | 编排器重规划 |
| --- | --- | --- |
| 触发 | 编译/执行报错 | `critic_node` 判定结果不充分 |
| 粒度 | **重写 DSL** | **重新规划执行步骤** |
| 上限 | `SQL_SELF_HEAL_MAX_RETRIES=3` | `MAX_RETRIES=3` |
| 上下文 | `error_context`（错误摘要） | `error_context` + 轨迹 + 反思结论 |
| 实现 | `agent/pipeline.rewrite_dsl` | `core/orchestrator/graph.py` 的 `critic → plan` 条件边 |

**为什么粒度不同**：

- **自愈**针对"我表达错了"——同一个问题，换个写法再问一次；
- **重规划**针对"我问得不对"——比如用户问"为什么 6 月下滑"，
  第一次只查了总量，发现信息不足，需要**追加一次分维度查询**。

**两者共享同一套错误预算**：编排器的重规划也消耗 `error_context` 的额度，
避免"自愈 + 重规划"叠加导致指数级重试。

---

### Q5.15 — 重规划怎么避免"鬼打墙"（反复做同一件事）？

**答**：

**三个机制**：

**① 错误上下文注入（这是审计发现的一个真实缺陷的修复）**

审计报告指出：早期版本重规划时，**LLM 看不到失败原因**——
`dsl_query_node` 失败后 `error_context.record()` 并回到 `plan` 节点，
但 `planner_prompt` 只接收 `user_query + schema_digest`，
`error_context.errors` 从未进入重规划上下文——

> "LLM 重规划 = 盲重试，自愈成功率被无谓拉低。"

修复后 `planner_prompt` 增加错误摘要小节，
且 `error_context=None` 时提示词与旧契约**逐字一致**（保证向后兼容与测试稳定性）。

**② 重规划指纹去重**

`AgentState.last_replan_fingerprint` ——
如果新计划的指纹与上一次**相同**，说明模型在做**无意义的重复**，
此时不再重试，直接进入 `synthesize` 给出当前能给出的答案。

**③ 反思结论的可执行性门槛**

LLM Reflector 返回 `verdict == "insufficient"` 时，
必须通过 `_insufficient_is_actionable` 检查才允许重规划。
如果一个反思结论是"结果不够好"但**说不出具体该查什么**，
那重规划只会浪费一次调用。

**三个短路条件**（直接跳到 synthesize，不重试）：

1. `no_data_reason` 已明确（比如时间超域）→ 无数据可查，重试无意义；
2. **所有数据集都是 0 行** → 空集是合法答案，重试不会变出数据；
3. **没有数据 AND 预算已耗尽** → 诚实地失败，而不是继续烧钱。

> **面试话术**："防鬼打墙的核心是**让系统能识别'我在原地转圈'**。
> 我们用了三个信号：失败原因是否可见（治本）、
> 计划指纹是否重复（识别循环）、
> 反思结论是否可执行（避免空转）。"

---

### Q5.16 — "没有数据"这个情况为什么这么难处理？

**答**：

因为**空结果有三种完全不同的含义**：

| 类型 | 例子 | 正确处理 |
| --- | --- | --- |
| **合法空集** | "北京有多少店铺"（真的只有 0 个） | 如实回答 0 |
| **口径错误** | "华东的 GMV"（把区域当省份过滤） | 提示可能的口径问题 |
| **超域查询** | "2025 年 1 月的 GMV"（数据只到 2024-06-30） | 提示超出数据域 |

**把它们混在一起是灾难**：
- 把合法空集当错误重试 → 浪费预算，最终还是空；
- 把口径错误当合法空集 → 用户拿到"0"，以为是真实业务情况，**做出错误决策**。

**我们的处理**：

1. **超域可以被证明**：`DATA_DOMAIN_END = AS_OF_DATE`，
   时间窗完全在其之后 → **可证明为空**，直接给出原因，禁止产出归因报告；
2. **口径问题靠词汇表预防**：`DIMENSION_MEMBERS` + 区域展开，
   让"华东"这种词在生成阶段就被正确处理，而不是事后补救；
3. **剩下的一律如实报告**："未查询到符合条件的数据"，并附上可能原因。

**为什么"禁止对空结果产出归因报告"**：

这是基准评测发现的缺陷之一。用户问"2025 年 1 月 GMV 为什么下滑"，
系统跑出空结果，然后**照常写了一份归因报告**——
报告里全是无意义的数字和"No data"占位。

修复后：**无数据时禁止产出归因报告**，
改为诚实地说明"未查询到符合条件的数据，可能原因……"。

> **面试金句**："一个数据分析系统最危险的输出不是'我算错了'，
> 而是'**我很自信地告诉你一个没有依据的结论**'。"

## 第五部分：本主题高频压力追问速答

| 追问 | 一句话应答 |
| --- | --- |
| "30 秒超时够吗？大查询怎么办？" | 30 秒是**交互式分析的合理上界**。真正的重分析请求应该走异步任务（`web/tasks.py` 的 `/api/query/async` 轮询模型），而不是同步阻塞用户。 |
| "`EXPLAIN ANALYZE` 会不会本身就把资源消耗掉了？" | 会，这是一个**已知代价**。缓解方式是缓存（相同 SQL 只预检一次）+ 30 秒看门狗兜底。更彻底的方案是用引擎的成本模型估算，但那依赖统计信息质量，我们选择了更准但更贵的方式。 |
| "自愈 3 次都失败，用户要等多久？" | 最坏情况是 3 次 LLM 调用 + 3 次编译，通常十几秒。我们通过**永久错误短路**把最常见的无效重试（权限问题）掐掉，实际很少跑满 3 次。 |
| "有没有可能自愈把一个正确的查询改坏？" | 自愈只在**已经失败**的查询上触发，不存在"改坏正确查询"的场景。但存在"改成另一种错误"的可能——所以有 3 次上限，且每次都重新过完整的校验链。 |
| "熔断之后用户看到什么？" | 结构化的错误对象：`error` 字段（用户可读文案）+ `error_detail`（技术细节）+ `circuit_breaker` 标记（用于指标聚合）。前端展示第一项，排障看后两项。 |
| "你们的自愈成功率是多少？" | 我们没有独立的成功率埋点，但指标系统里有 `_self_heal_success` / `_self_heal_failures` 两个计数器，可以通过 `/api/metrics` 查看实时值。**坦白说这是一个应该长期跟踪但当前还没有基线数据的指标。** |
| "如果编译器生成了语法正确的危险 SQL 呢？" | 那正是执行前审计存在的意义——它不信任编译器，独立解析 SQL 的 AST。审计和编译器由**不同的测试套件**覆盖，降低"同一个 bug 同时骗过两者"的概率。 |

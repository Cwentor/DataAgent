## 第 1 节：`semantic/dsl_schema.py` —— 契约的物理落点

### 1.1 最该讲的三行

```python
IDENTIFIER_PATTERN = r"^[A-Za-z_][A-Za-z0-9_]{0,63}$"      # 第 25 行

TIME_FIELDS = frozenset({"order_time", "refund_time", "register_time"})   # 第 29 行
```

**为什么这三行值得讲**：

> "第一行是**标识符的物理边界**。
> 所有可能进入 SQL 的标识符（别名、维度字段、排序字段）
> 都必须匹配这个正则——**长度上限 64 是刻意留的**，
> 因为 DuckDB 的标识符长度上限是 63 字节加上引号，
> 而我把它卡在 64 以内，是为了**在契约层就把'过长的别名'
> 挡在编译器的引用逻辑之前**。
>
> 第二行是一个 `frozenset` 而不是 `list`——
> 因为它在**每一次维度表达式的计算里都被查一次**，
> 集合查找是 O(1)，列表是 O(n)。这里 n 只有 3，
> 性能差异可以忽略，但**语义上更准确**：
> '是不是时间字段'是一个**成员判定**，不是一个序列。"

### 1.2 `extra="forbid"` 的位置

```python
class QueryDSL(BaseModel):
    model_config = ConfigDict(extra="forbid")
```

**面试话术**：

> "这一行是整个项目的**安全基石**。
> 它做的事情是：**任何不在契约里声明的字段，一律拒绝**。
>
> 用户问'这一段能不能加个 raw_sql 字段让模型直接写 SQL'——
> 不行，因为 Pydantic 会在**反序列化的那一刻**抛错，
> 而这个错会作为自愈上下文喂回模型。
>
> **注意它是写在 `model_config` 上的，不是写在某个字段上的**——
> 也就是说，**契约的每一个子模型都要这样配**，
> 因为嵌套模型的 `extra` 行为是独立的。
> 这是一个容易漏的地方，我们的测试里专门有一条覆盖它。"

### 1.3 `_check_scalar_ordering` 校验器

```python
@model_validator(mode="after")
def _check_scalar_ordering(self):
    # dimensions 为空时清空 order_by（纯标量查询没有可排序的维度）
    ...
```

**面试话术**：

> "这是一个**契约层的兜底**，不是编译器层的。
> 我的判断是：**'纯标量查询不该有排序'是一条契约规则，
> 不是编译规则**——
> 编译器应该收到一份**已经合法的** DSL，
> 而不是自己去猜'用户是不是写错了'。
>
> 把校验放在契约层的好处是：
> **错误发生在 DSL 生成的第一时间**，
> 自愈时模型看到的是 `'order_by 在无维度查询中必须为空'`，
> 而不是编译到一半才失败。"

## 第 2 节：`compiler/sql_compiler.py` —— 最该展示的一段代码

### 2.1 开篇先讲"这个文件为什么是 811 行"

> "很多人看到 811 行会觉得复杂。
> 我拆给你看：
> - **约 300 行是异常分支和边界处理**；
> - 约 250 行是五个查询形态的 SQL 渲染；
> - 约 150 行是时间窗解析；
> - 剩下是辅助函数。
>
> **也就是说，这个文件里将近一半的代码在做'防守'。**
> 我认为这个比例是合适的——
> **编译器的每一行异常处理，都对应一个我实际踩过的坑。**"

### 2.2 `_qualify` —— 白名单的实际执行点

```python
def _qualify(self, field: str) -> str:
    meta = catalog.COLUMNS.get(field)
    if meta is None:
        raise CompileError(f"未登记的字段: {field!r}")
    return f"{catalog.ALIASES[meta.table]}.{meta.column}"
```

**逐点讲法**：

> "**第一，它只认 `catalog.COLUMNS`。**
> 这个字典是语义目录，是**唯一事实来源**。
> 模型产出的 `field` 如果不是这个字典的键，直接编译失败。
>
> **第二，它返回的是"别名.列名"，不是用户给的名字。**
> 用户说 `gmv`，我不可能把它拼进 SQL——
> 我把 `order_amount` 映射成 `f.order_amount`。
> **物理列名和逻辑字段名之间是一次查表，不是字符串拼接。**
>
> **第三，注意错误信息里的 `{field!r}`。**
> 用了 `!r` 而不是直接插值，这样错误信息里会带引号：
> `未登记的字段: 'order_total'`。
> 这个细节的作用是**让自愈时的模型能明确区分
> '这是字面量 order_total'还是'这是别的东西'**。"

### 2.3 `_literal` —— 转义的全部逻辑（可当场背诵）

```python
def _literal(self, value: Any, dtype: str) -> str:
    if dtype == "str":
        return "'" + str(value).replace("'", "''") + "'"
    if dtype == "int":
        return str(int(value))
    if dtype == "float":
        v = float(value)
        if math.isnan(v) or math.isinf(v):
            raise CompileError("浮点字面量不能为 NaN/Inf")
        return repr(v)
    if dtype == "bool":
        return "TRUE" if value else "FALSE"
    if dtype == "timestamp":
        ...
    raise CompileError(f"未知字面量类型: {dtype!r}")
```

**这是全场最有杀伤力的一段，逐行讲**：

> "**字符串：只转义单引号，用 SQL 标准的双写方式。**
> 为什么不用反斜杠？因为反斜杠转义是 **MySQL 的扩展**，
> 我们的目标引擎 DuckDB 遵循 SQL 标准，
> 在标准里反斜杠就是普通字符。
> **如果我在这里加了反斜杠转义，反而会改变数据语义**——
> 用户想查 `a\b`，会变成查 `a\\b`。
>
> **整数：注意是 `str(int(value))` 而不是 `str(value)`。**
> 因为 `value` 可能是 `True`——
> Python 里 `True == 1`，如果直接 `str(value)` 会得到 `'True'`，
> 拼进 SQL 就是 `WHERE x = True`。
> **先转 `int` 就把布尔值强制成了 0/1。**
> （不过我们的 `_check_scalar_type` 会更早在前面拒绝 bool，
> 这里是**第二道保险**。）
>
> **浮点：用 `repr` 而不是 `str`，并且拒绝 NaN/Inf。**
> `repr` 保证**往返精度**（`float(repr(x)) == x`），
> 而 `str` 在某些版本上会截断。
> 拒 NaN/Inf 是因为它们拼进 SQL 会让查询行为不可预测。
>
> **最后那个 `raise` 是关键**：
> 如果有一天有人给 `catalog` 加了一个新的 `dtype`，
> 但忘了在这里加分支——
> **它会抛错，而不是静默地返回一个不安全的字符串。**
> 这叫 **fail-closed 的穷尽分支**。"

### 2.4 `_quote_ident` —— 第二道防线

```python
def _quote_ident(name: str) -> str:
    return '"' + str(name).replace('"', '""') + '"'
```

**面试话术**：

> "这个函数做的是**标识符的引用与转义**。
>
> 有人会问：契约层已经用 `IDENTIFIER_PATTERN` 保证了别名合法，
> 为什么这里还要转义？
>
> **因为这是第二道防线，而且它们防的不是同一件事**：
> - `IDENTIFIER_PATTERN` 防的是'**用户给的别名非法**'；
> - `_quote_ident` 防的是'**代码里某处硬编码的名字有问题**'——
>   比如将来有人从配置文件读别名表，而那个文件被改坏了。
>
> **深度防御的意思不是'重复做同一件事'，
> 而是'每一层假设上一层会失效'。**"

### 2.5 `_metric_expr` 里的 `COALESCE / NULLIF`

```python
if isinstance(m, RatioMetric):
    return f"COALESCE({num}, 0) / NULLIF({den}, 0)"
```

**面试话术（这条来自真实评审缺陷）**：

> "这个写法是被一个评审缺陷逼出来的。
>
> 原来的写法是 `num / den`，问题是：
> 一个**没有退款记录的品类**，`SUM(refund_amount)` 是 `NULL`，
> 于是 `NULL / 某数 = NULL`，报表上显示成空。
> **但业务含义应该是 0% 退款率，不是"未知"。**
>
> 修复是两处：
> - **分子 `COALESCE(..., 0)`**：没有退款就是 0；
> - **分母 `NULLIF(..., 0)`**：防止除零（如果某期完全没有订单）。
>
> 这两处合起来，保证了**比率指标永远是一个可读的数字或 NULL，
> 而不会因为一个 NULL 传播到整个结果。**
>
> 而且这个修复**补了回归测试**——
> 测试里直接断言 SQL 字符串包含 `COALESCE` 和 `NULLIF`，
> 所以将来有人'简化'这段，测试会立刻变红。"

### 2.6 `_window_expr` —— 帧定义的确定性

```python
if wm.func == "cumsum":
    return f"SUM({base}) OVER (ORDER BY {order_expr})"
if wm.func == "moving_avg":
    n = wm.window
    return f"AVG({base}) OVER (ORDER BY {order_expr} ROWS BETWEEN {n-1} PRECEDING AND CURRENT ROW)"
```

**面试话术**：

> "窗口函数最容易出问题的地方是**默认帧**。
> 如果我不写 `ROWS BETWEEN`，SQL 标准会用一个隐式的默认帧，
> 而这个默认值**在不同引擎、不同场景下可能不同**。
>
> 我显式写 `ROWS BETWEEN n-1 PRECEDING AND CURRENT ROW`，
> 含义是'包含当前行在内的 n 行'。
> **为什么要显式**：因为'移动平均'这个业务概念在
> '含当前行'和'不含当前行'两种理解下结果不同，
> **我不能把这个歧义留给引擎的默认行为。**
>
> 另外注意 `cumsum` 用的是默认帧——
> 但这是**安全的**，因为累计求和的语义就是
> '从第一行到当前行'，这与 `ORDER BY` 的默认帧一致。
> **不是所有地方都要显式，关键是'知道哪里可以不显式'。**"

### 2.7 时间窗的半开区间

```python
def _time_window_sql(self, tf) -> str:
    col = self._qualify(tf.field)
    s, e = self.resolve_time_window(tf)
    return f"{col} >= TIMESTAMP '{s}' AND {col} < TIMESTAMP '{e}'"
```

**面试话术**：

> "注意这里是 `>= 开始 AND < 结束`，**半开区间**。
>
> 为什么不用 `BETWEEN`（闭区间）：
> 因为 `BETWEEN '2024-06-01' AND '2024-06-30'` 在时间戳精度下
> **会漏掉 6 月 30 日当天的数据**——
> 因为 `2024-06-30 14:23:00 > 2024-06-30 00:00:00`。
>
> 半开区间 `[6-01 00:00, 7-01 00:00)` 没有这个问题，
> 而且它是**可组合的**：相邻的两个月区间首尾相接，不重不漏。
>
> **这个坑在企业数据里极其常见**——
> 我见过太多报表因为用 `BETWEEN` 而少算最后一天。"

## 第 3 节：`exec/guards.py` —— 四层只读校验

### 3.1 讲清"四层分别防什么"

```python
# 示意结构（实际实现见文件）
def _assert_readonly(sql):
    # 第 1 层：语句类型白名单（只允许 SELECT / WITH）
    # 第 2 层：AST 节点扫描（拒绝 DDL / DML 节点）
    # 第 3 层：危险函数检测（拒绝 PRAGMA / ATTACH / COPY 等）
    # 第 4 层：连接级只读（DuckDB read_only=True）
```

**面试话术**：

> "这四层不是冗余，**它们防的攻击面完全不同**：
>
> | 层 | 防的是 | 绕过难度 |
> | --- | --- | --- |
> | 1. 语句类型白名单 | `DROP TABLE x` 这种直白的 | 低 |
> | 2. AST 节点扫描 | `WITH x AS (...) INSERT ...` 这种嵌套的 | 中 |
> | 3. 危险函数检测 | `COPY ... TO '/etc/passwd'`、`ATTACH` 读外部库 | 中高 |
> | 4. 连接级只读 | **前面三层都漏掉的任意情况** | **物理不可能** |
>
> **第 4 层才是真正的保证**。前三层的价值是：
> **在造成'尝试'之前就拒绝，并且给出精确的错误信息**——
> 而不是等数据库抛一个 `Cannot execute statement in a READ ONLY transaction`。
>
> **这个区别很重要**：
> 一个'尝试了但被数据库拒绝'的写操作，
> 在审计日志里看起来和'尝试成功了'很难区分。
> 而**前三层在 SQL 到达数据库之前就拦住了**。"

### 3.2 超时看门狗（这段可以直接背）

```python
def _run_with_timeout(conn, sql, timeout_ms):
    result_box = {}
    def _worker():
        try:
            result_box["value"] = conn.execute(sql).fetchall()
        except BaseException as exc:        # ← 注意是 BaseException
            result_box["error"] = exc

    worker = threading.Thread(target=_worker, daemon=True)
    worker.start()
    worker.join(timeout_ms / 1000.0)
    if worker.is_alive():
        conn.interrupt()
        worker.join(2.0)
        raise QueryTimeoutError(...)
```

**三个细节，逐个讲（这是最能体现功力的一段）**：

> **细节 1：为什么捕获 `BaseException` 而不是 `Exception`？**
>
> "因为 `KeyboardInterrupt`、`SystemExit` 是 `BaseException` 的子类，
> **不是 `Exception` 的子类**。
> 如果我只捕 `Exception`，这些会逃逸出 worker 线程——
> 在 Python 里，**线程里未捕获的异常不会传播到主线程**，
> 结果是线程静默死掉，`join` 正常返回，
> `result_box` 是空的，然后主线程在取 `result_box["value"]` 时
> 抛一个 `KeyError`——**一个和真实原因完全无关的错误**。
>
> 这种 bug 的排查成本极高，因为**你看到的现象和原因之间没有任何关联**。"
>
> **细节 2：为什么 `daemon=True`？**
>
> "因为如果主进程要退出，而有一个查询线程卡死在数据库调用里，
> 非守护线程会**阻止进程退出**。
> 对于一个 Web 服务来说，这意味着'关不掉'。
> 设成守护线程，进程退出时它会被强制回收。"
>
> **细节 3：为什么 `interrupt()` 之后还要 `join(2.0)`？**
>
> "因为 `interrupt()` 是**协作式的**——
> DuckDB 需要执行到下一个检查点才会真正响应中断。
> 给它 2 秒优雅收尾，避免连接处于'半死不活'的状态被放回连接池，
> 导致**下一次查询拿到一个状态混乱的连接**。
>
> 如果 2 秒后还没结束，连接会被标记为不可用，而不是放回池里。
> **宁可少一个连接，也不能让一个坏连接污染后续查询。**"

## 第 4 节：`security/guard.py` —— 权限注入的实现

### 4.1 `apply_policy` 的返回语义

**面试话术**：

> "`apply_policy(dsl, principal)` 返回一个**新的 DSL 对象**，
> 原来的对象不变。
>
> 这个设计的价值在**多轮对话**里体现得最清楚：
> 第一轮注入过 RLS 的 DSL 会被存进会话记忆，
> 第二轮取出它作为基底时，**必须先剥离再合并再注入**。
> 如果 `apply_policy` 是原地修改的，
> 那我根本无法区分'哪些过滤条件是用户提的、哪些是系统注入的'。"

### 4.2 生成前作用域（`security/scope.py`）

**面试话术**：

> "这一层做的事情是：**在模型生成 DSL 之前，就把它看不到的东西拿掉。**
>
> 比如 `bob` 不能访问 `fact_refunds` 表和 `refund_amount` 列，
> 那么在构造给模型的 Prompt 时，
> **这两样东西根本不会出现在字段列表里**。
>
> **这比'生成了再拒绝'好在哪**：
> - **不诱导幻觉**：看不到的字段，模型不会去猜；
> - **不消耗 token**：少一批字段就少一批 token；
> - **减少自愈轮次**：不会出现'生成了被拒 → 重试 → 再被拒'的循环。
>
> **但我要强调：这一层是'优化'，不是'保证'。**
> 真正的保证是编译后的权限守卫和 RLS 注入——
> 因为**模型完全可能凭常识猜出一个字段名**。
> 生成前作用域只是让猜的概率降低。"

## 第 5 节：`exec/audit.py` —— 执行前审计

### 5.1 fail-closed 的两个分支

```python
try:
    statements = sqlglot.parse(sql)
except sqlglot.errors.ParseError:
    return [GuardrailFinding("readonly_structure", "REJECTED",
                             "SQL 解析失败，无法确认只读结构", "检查 SQL 语法")]
if len(statements) != 1:
    return [GuardrailFinding("readonly_structure", "REJECTED",
                             f"期望恰好 1 条语句，实际 {len(statements)} 条", ...)]
```

**面试话术（这段是全项目最值得讲的安全代码）**：

> "这两个分支体现的是 **fail-closed**。
>
> **第一个**：SQL 解析失败时，我选择**拒绝**，而不是放行。
> 理由是：**'我无法确认它是只读的'必须等同于'它不安全'。**
>
> 如果这里选择放行，会发生什么？
> **攻击者只要构造一段让 sqlglot 解析崩溃的 SQL，
> 就绕过了所有基于 AST 的检查。**
> 这是经典的'用解析器的脆弱性攻击安全系统'。
>
> **第二个**：语句数不等于 1 时拒绝。
> `SELECT 1; DROP TABLE x` 会被解析成两条语句，
> **多语句是 SQL 注入的经典形态**。
> 注意我的错误信息里带了实际条数——
> 这样排障时能立刻区分'这是注入尝试'还是'这是代码 bug 拼了两条'。
>
> **判断 fail-closed 的标准很简单**：
> **问自己'当系统无法判断时，默认答案是什么'。
> 安全相关的判断，默认答案必须是拒绝。**"

### 5.2 为什么 `unbounded_output` 是 WARNING

```python
# AGENTS.md 中的明确约定：
# 无界输出 WARNING（真实边界由返回行数硬上限承担，勿升级为 REJECTED）
```

**面试话术**：

> "这一行注释是**写给未来的自己和其他人的**。
>
> 因为这是一个**容易被'优化'掉的正确决策**：
> 后来的开发者看到'无界输出只是 WARNING'，
> 第一反应是'这不够严格啊'，然后改成 REJECTED。
> 结果就是**编译器的任何小改动都可能拒绝用户的正常查询**。
>
> 我把理由写进了项目约定文件，是为了让后来的修改
> **必须先推翻一个有理由的决策，而不是无意识地'加强安全'**。
>
> 那为什么它真的不该升级：
> **因为真实的边界已经由 `MAX_RESULT_ROWS=20000` 的执行后熔断承担了。**
> 审计层的 WARNING 是'不变式防御'——
> 编译器**当前**保证除纯标量外都有 LIMIT，
> 审计只是在这个保证被打破时**发出声音**，而不是替它做决定。
>
> **安全设计里最常见的过度反应，是把所有警告都升级成错误。
> 但严格的代价是可用性——一个动不动就拒绝用户的系统，
> 最后的下场是用户绕过它。**"

## 第 6 节：`agent/memory.py` —— 最隐蔽 bug 的修复现场

### 6.1 讲清 bug 的完整链路

```python
def strip_rls_filters(dsl, principal):
    """剥离该主体已被注入的 RLS 过滤器。"""
    policy = resolve_policy(principal)
    ...
# 使用：
clean = strip_rls_filters(dsl, principal)
merged = _apply_deltas(clean, delta)
final = apply_policy(merged, principal)   # 恰好注入一次
```

**面试话术（这是最能证明"我真踩过坑"的一段）**：

> "这个函数的诞生过程我讲一下，因为它展示了一类**通用的 bug 模式**。
>
> **现象**：用户第一轮问'广东的 GMV'，第二轮问'那浙江呢'，
> 系统回答 **0**。
>
> **排查**：看生成的 SQL，发现是
> `province IN ('广东') AND province IN ('浙江')`——
> **恒假条件，永远返回空。**
>
> **根因**：第一轮的 DSL 被 `apply_policy` 注入了 `province IN ('广东')`，
> 这个**已经注入过的对象**被存进了会话记忆。
> 第二轮把它取出来当基底，叠加新条件，
> 于是两个互斥的过滤条件同时存在。
>
> **为什么这个 bug 特别危险**：它不是崩溃，
> 它**返回一个看起来完全正常的 0**。
> 用户会以为'浙江真的没有数据'，然后**基于这个结论做决策**。
>
> **修复方式**：'**剥离 → 合并 → 重新注入**'三段式。
> 保证 RLS 过滤器**恰好被注入一次**。
>
> **提炼出的原则**（我把它写进了项目约定）：
> **注入和剥离必须是一对函数，并且在同一个测试里互相验证。**
> 只要系统里存在'给对象加上某约束'的操作，
> 而这个对象会跨请求持久化，
> 就必然需要对应的'去除约束'操作——
> **否则约束会在多次传递中复合。**"

### 6.2 会话记忆的双键设计

```python
key = (session_id, owner)   # owner = user_id
# 跨用户读取 → 返回 None（fail-closed）
```

**面试话术**：

> "如果只用 `session_id` 做键，会发生什么？
>
> `session_id` 是客户端生成或来自 cookie 的，
> **它是可猜测、可枚举的**。
> 攻击者只要构造一个别人的 `session_id`，就能：
> - 读到别人的历史提问（**知道老板在查什么**）；
> - 接着别人的上下文提问（**语义混淆**，继承别人的 DSL）。
> 这是典型的 **IDOR（不安全的直接对象引用）**。
>
> 双键之后，即使 `session_id` 完全泄露，
> A 用户的请求也**读不到** B 用户的历史——
> 因为 owner 对不上，`get()` 返回 `None`。
>
> **注意返回 `None` 的语义是 fail-closed 的**：
> 系统把它当成'全新问题'处理，
> **而不是'回退到只用 session_id 查一次'**。
> 如果我写成后者，双键就形同虚设。"

## 第 7 节：三个"小代码、大道理"的片段

### 7.1 PII 掩码用 `sha256` 而不是顺序编号

```python
# core/retrieval/pii.py（示意）
masked = "U_" + hashlib.sha256(user_id.encode()).hexdigest()[:16]
# 而不是
masked = f"U_{index}"
```

**面试话术（这是一个很漂亮的取舍）**：

> "两种做法的差别在于**跨查询的一致性**。
>
> 如果用顺序编号 `U_1, U_2, ...`：
> - 每次查询的编号映射都不同，
>   于是**同一个用户在两次导出里是两个不同的 ID**——
>   分析师无法做跨报表的关联分析，
>   数据变得没用。
>
> 如果用 `sha256` 截断：
> - **同一个用户永远得到同一个掩码 ID**，
>   跨报表可关联；
> - **无法从掩码反推原始 ID**（哈希的不可逆性）；
> - **不同租户的相同 ID 会得到相同掩码**——
>   这是一个**已知的理论弱点**，
>   要修的话需要在哈希输入里加盐（租户标识）。
>
> **我选 `sha256` 是因为它同时满足了'可用'和'安全'，
> 而顺序编号只满足了'安全'——一个没用的导出等于没导出。**"

### 7.2 图表推荐的确定性阈值

```python
_PIE_MAX_CATEGORIES = 8
```

**面试话术**：

> "这个常数的价值在于**它是确定性的，不是模型决定的**。
>
> 如果让模型决定'这个数据用饼图还是柱状图'，
> 就会引入一个**无意义的非确定性**：
> 同样的数据，两次可能给出不同的图表。
> 而这个决策**根本不需要智能**——
> '分类数超过 8 个就不能用饼图'是一条**可视化领域的经验规则**。
>
> **从'能用规则解决的'和'需要判断的'之间划一条线，
> 是 Agent 系统设计里最关键的取舍之一。**
> 我在这条线的一侧放了：图表选择、时间窗解析、
> 权限过滤、SQL 生成；
> 另一侧放了：意图理解、字段选择、归因方向、报告组织。"

### 7.3 工具定义的注册顺序

```python
# tools/registry.py
# 注册顺序 = 定义顺序 = tool_definitions() 的返回顺序
```

**面试话术**：

> "这个约束看起来无关紧要，但它决定了**系统的可复现性**。
>
> `tool_definitions()` 的输出会**按顺序**拼进 Prompt，
> 而 LLM 对 Prompt 里的顺序是敏感的——
> 同样的工具集，换个顺序可能让模型的工具选择概率分布变化。
>
> 如果我用 `set` 或者不加约束地遍历 `dict`，
> 就会出现：**同一份代码，不同进程启动得到不同的工具顺序，
> 同一个问题得到不同的工具选择。**
>
> **这就是'不确定性从哪来'的经典来源**——
> 你以为无关紧要的数据结构选择，实际上决定了系统的可复现性。
>
> 注册中心里还有一条对应的检查：**重名工具直接抛
> `DuplicateToolError`**。因为重名会让 `get(name)` 的结果
> 取决于注册顺序，从而产生**难以排查的行为漂移**。"

## 第 8 节：面试官当场改代码时的应对

### 8.1 "你把这个 `_literal` 改成支持反斜杠转义看看"

**正确反应：先问'为什么'，再指出后果。**

> "我可以改，但我想先确认一下你的意图——
> 你是想验证**这段代码的假设是什么**，对吧？
>
> 那我先说这个假设：**反斜杠在 DuckDB 里是普通字符。**
> 如果我加上 `\` → `\\` 的转义，
> 那么用户查 `路径\文件` 就会变成查 `路径\\文件`，
> **查不到数据**。
>
> 如果我们要支持 MySQL，那就**必须**加这个转义，
> 但同时**要改的是整个执行后端**——
> 因为转义规则是**引擎方言的一部分**。
>
> 这也正好说明我在面试里提到的一个改进点：
> **转义逻辑应该跟着执行后端走，而不是写死在编译器里。**
> 如果现在要改，我会先抽出 `ExecutionBackend` 协议，
> 把 `_literal` 变成后端的职责。"

**这个回答的价值**：你没有拒绝改代码，而是**展示了你知道改动的连锁影响**。

### 8.2 "这里加个缓存是不是更快"

**正确反应**：给出"什么时候该加、什么时候不该加"的判断标准。

> "加缓存要看**三件事**：
>
> 1. **这个函数的调用频率**——如果是每次请求都调，值得加；
> 2. **结果的稳定性**——如果结果会随数据变化，加了就是 bug；
> 3. **缓存的失效语义**——谁负责让它失效？
>
> 具体到这个位置，我想先问：**你观察到性能问题了吗？**
> 因为**过早优化最大的成本不是代码，是维护者需要多理解一个状态**。
>
> 我项目里有一个对照案例：
> **查询结果缓存**我实现了，但**默认关闭**——
> 因为'数据分析师看到过期数字'的伤害大于'查询慢 500ms'。
> 能力提供，默认关闭，把判断题留给部署方。
>
> **所以如果这里要加缓存，我会先要求一个测量数据。**"

# 设计分析｜数据层四项能力边界（DWS / CDC / 定时调度 / 物化预聚合，2026-11）

> - **状态**：**四项全部不立项（2026-11-01）**。本篇是讨论分支 `discuss/dev-iteration` 上的
>   决策分析落盘，回答能力盘点确认的四个数据层缺口"为什么不做"，并给出 DataAgent 对
>   上游数据层的消费姿态对接方式（§四）。与
>   [RAG 引入决策分析](2026-11-01-rag-adoption-decision-analysis.md) 同属"边界即决策"系列。

## 一、背景与结论

能力盘点（2026-11-01）确认数据层缺四样，DWS 汇总层、增量入仓与变更数据捕获
(Change Data Capture, CDC)、定时调度、物化预聚合。本篇结论如下。

**四项全部不立项，且归类不是"延后待办"，而是"定位的另一侧"。** 它们全部属于数据
生产域（数仓建设、采集同步、作业运维），而 DataAgent 的定位是数据消费与治理域
（取数、治理、问答）。做它们等于把产品定位漂移为数仓平台工具，稀释"治理取数"这个
核心叙事。真正的持续建设项只有一个，保持对接面整洁（§四）。

## 二、共同判定框架

四项共享同一组分界与矛盾，故先立框架再逐项分析。

### 2.1 定位分界

数据生产域回答"数仓里的数据从哪来、怎么组织、何时更新"，角色是数据工程师与数仓
平台。数据消费与治理域回答"业务用户如何安全地取数与问答"，角色是分析师。DataAgent
的架构投资（语义目录、确定性编译、五后端、治理管道、评测闭环）全部投在后者。

### 2.2 三组共同矛盾

1. **mock 静态数据使四项全部无验证手段。** 数仓为种子 42 确定性生成的静态快照，
   锚定 AS_OF_DATE——DWS 无负载依据（不知道该汇总什么）、CDC 无增量可捕、调度无
   作业可跑、预聚合无慢查询证据。四项在当前数据上均无法产生真实验证价值；
2. **与确定性锚定体系冲突。** 数据持续演进则 AS_OF_DATE 锚定、golden 快照、
   单 rng 种子体系全部作废，评测与回归地基重建，代价远超能力本身；
3. **与只读防线直接冲突。** CDC 入仓是写操作，物化视图 (Materialized View) 是
   DDL，均被只读账号与只读防线铁律拒绝。

## 三、逐项分析

### 3.1 DWS 汇总层——不建

- **设计前提缺失。** DWS 的价值是固定口径高频查询加速，前提是知道"哪些问题高频"，
  只能来自真实负载统计，mock 上无从设计；
- **架构代价为负。** 一旦建 DWS，Planner 需感知"什么问题走明细、什么走汇总"，
  路由复杂度上升，且汇总表与明细的口径漂移构成第二事实源（与
  [RAG 分析](2026-11-01-rag-adoption-decision-analysis.md) §2.2 同构）。
  语义一致性是本系统核心卖点，不能主动引入漂移面；
- **正确姿态。** 上游数仓团队建好汇总层后，登记进 `semantic.json` 作为查询域
  （QUERY_DOMAINS 机制现成），DataAgent 只消费不生产。

### 3.2 增量入仓 / CDC——域外，最清晰

- **域别判断。** CDC（Debezium 加消息队列消费入仓）是数据平台采集侧基建，
  在治理管道的上游之外。做它意味着承担数据搬运职责，定位直接漂移；
- **锚定体系作废。** 数据持续流入则确定性三原则失效，与 #25（定时预警）是同一
  根本矛盾且代价更大；
- **正确姿态。** DataAgent 的承诺边界是"入仓后的数据可被治理取数"，采集与入仓
  是上游的事。

### 3.3 定时调度——不自建，#25 已覆盖最小形态

- **完整调度系统属运维域。** DAG 依赖、补数、重试、作业监控是 Airflow 类产品的
  领域，属 ETL 运维域，本项目非 ETL 工具；
- **最小形态已在跟踪。** 本项目真正需要的是 CRON 触发的确定性执行器
  （#25 已立，含治理约束），不是通用调度器；
- **正确姿态。** DataAgent 提供可被外部调度的稳定入口（API / CLI），用任何上游
  调度器触发皆可，不自建调度器。

### 3.4 物化预聚合——不主动建

三条硬理由，任一单独成立即足够。

1. **只读防线冲突。** 建物化视图是 DDL 写操作，只读账号执行不了；
2. **证据缺失。** 不知道该物化什么、也没有慢到需要物化的查询，#23 的耗时观测是
   其前置证据链，无证据不动手；
3. **方言碎片化。** DuckDB 无物化视图、MySQL 需以表加调度模拟、PG 与 ClickHouse
   才有原生，五后端又是互不相通的实现，与索引推荐同构（见
   [#23](https://github.com/Cwentor/DataAgent/issues/23) 边界声明）；

正确姿态同 DWS，上游有则登记进语义目录当普通表消费。

## 四、消费姿态对接（边界宣言）

DataAgent 对上游数据层的正确关系是**登记与消费，而非建设**，具体三条。

1. **登记消费。** 上游任何就绪表（DWS / ADS / 物化视图 / 新事实表）经
   `semantic.json` 登记即成为可治理查询域，语义目录的表登记机制保持通用；
2. **外部触发。** 执行入口（API / CLI）保持稳定可调度，调度权在上游；
3. **对接面整洁是唯一持续建设项。** 上游数据层演进（真有汇总层、真有物化表、
   真有调度器）时，全部动作应是配置而非开发。

此姿态与"能力边界等于治理管道边界"（十九期）的既有叙事同构——边界外的能力
不是缺失，是分工。
